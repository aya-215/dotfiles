# somu-search スキル設計

総務パック（社内の eBASE、ミラー環境）を、質問に応じてボリュームを選んで検索し、結果を答えるための汎用スキル。

## 目的と背景

- 社内情報の多くは総務パックの各ボリュームにある。よく引くのは次の3つ:
  - 社内IPアドレス管理（サーバーやPCの内部IPを調べる。一番多い用途）
  - ルールDB（社内開発の知識）
  - 社内規定（規則。本体はたいてい添付ファイルの中にある）
- `eb-api-somu` MCP では検索ができない。MCP の `getItems` 系と `getFileText` は、ビューア側の JSP / `fileDownload` を経由していて、どちらもログインセッションが要る。総務パック向けの設定にはセッションが無いので 401 になる。
- 一方、eB-API 本体（`.mcp.json` の `ebase-api-url`）に XML を直接 POST すれば、セッション無しで全件の ID と値を取れる。添付ファイルも、ボリュームの公開パスからセッション無しで取れる。
- 2026-10-27 に手作業で「社内サーバーの内部IP」「テレワークの規定」を調べて、この経路で答えまで辿り着けることを確認済み。

## ゴール

- 「〇〇の内部IPは？」「〇〇の規定は？」「ルールDBに〇〇の知見ある？」といった質問に、どのボリュームを見るかを Claude が選び、検索結果をもとに答えられる。
- 対象は特定のボリュームに限らず、アクセスできる全ボリューム（約440）。
- 本文が添付にしか無いレコードは、必要なときだけ添付を取りに行って本文を読める。

## やらないこと

- 登録・更新・削除。読むだけ。
- MCP の修正やセッションの設定。MCP は使わない。
- 本番の総務パックへの接続。接続先は `.mcp.json` に書いてあるミラーのみ。

## やったら失敗（アンチゴール）

- サーバーの共有フォルダ（`c$` などの管理共有）を再帰的に走査すること。本番相当のストレージに負荷がかかる。実際に作業中、ユーザーに止められた。添付は HTTP の公開パスで1ファイルずつ取る。
- 接続先IP・ホスト名・アイテムIDなどの社内情報を、スキル本体やリポジトリに書くこと。dotfiles は PUBLIC。接続先は gitignore 済みの `~/.dotfiles/.mcp.json` から実行時に読む（kintai-check と同じ方式）。
- 検索するたびに大きなボリュームを全件取り直すこと。

## ユーザーと決めたこと

- **取得の負荷**: 1万件を超えるボリュームは、全件を取る前（初回・`--refresh` とも）に件数を出して止まり、ユーザーの確認を取る。スクリプトは確認用のフラグ（例: `--yes`）が無ければ取らない。1万件以下は黙って取る。リクエストの間に短い間隔を空けるかはビルダーの判断。
- **鮮度**: 手元に保存したデータで検索してよい。「違うな」と気づいたときだけ取り直す（`--refresh`）。自動の期限切れは設けない。
- **添付**: まず手元のデータで検索する。本文が要りそうなときだけ添付を取りに行く。
- **見せ方**: Claude が見やすいと思う形でよい。質問に対して検索し、結果を答えるだけ。
- **ボリュームの選び方**: ボリューム一覧を見て、質問に当てはまるものを選ぶ。

## 構成（ワイの判断を含む）

kintai-check と同じ形。判定・取得・検索は決定的なスクリプトが持ち、Claude はボリュームを選ぶこと、検索語を決めること、結果を読んで答えることを担う。

```
.claude-global/skills/somu-search/
├── SKILL.md            # いつ使うか、手順、よく使うボリューム、読み方の注意
└── scripts/
    └── somu.py         # 標準ライブラリだけで書く。python3 -I で実行
```

### スクリプトのサブコマンド（案。細部はビルダーに任せる）

| サブコマンド | 役割 |
|---|---|
| `volumes [語]` | ボリューム一覧（ID と名前）。語を渡せば名前で絞る。`_WK` / `_DEF` / `_WF` で終わる作業用ボリュームは既定で隠す |
| `specs <vol>` | そのボリュームの項目定義（spec_type / spec_title / データ型） |
| `search <vol> <語...> [--refresh]` | 手元のデータで AND 検索する。手元に無ければ全件を取って保存してから検索する |
| `files <vol> <item_id>` | 添付ファイルの一覧（タイトル、ファイル名、形式、コメント、状態） |
| `text <vol> <item_id> [file_id...]` | 添付を取ってテキストにする |

### 接続先の解決

- `~/.dotfiles/.mcp.json` の `mcpServers["eb-api-somu"].headers` から読む:
  - `ebase-api-url` → eB-API の検索エンドポイント
  - `ebase-viewer-url` → 画面のベース URL。詳細画面の URL の組み立てに使う。
- 添付のベースは、`ebase-viewer-url` のスキーム＋ホストに `/volume/` を付けたもの。

### データの取り方（実機で確認済みの挙動）

- **ボリューム一覧**: `getVolume`（`<data></data>` 空）でセッション無しに取れる。`voldbname` と `volname` が返る。
- **全 ID**: `getItems` に `<search target="SPEC"></search>`（空の search）を付ける。search 要素が無いと 0 件、条件付きの spec を入れると 404 か全件しか返らない。eB-API 本体での条件検索は使わない。
- **項目定義**: `getSpecInfo` に `<spec all="true" invisible="false"/>`。
- **値**: `getSpecDataLite` に item_id を 200 件ずつ渡し、spec_type ごとに `spec_title="*"` で取る。1回で 5891 件程度なら現実的な時間で終わる。
- `inv` で始まる spec_title（invデータ登録日など）は内部管理用なので保存しない。
- 基本情報（`target="basic"`）の item_name は空のことが多い。レコードの「名前」に当たる項目はボリュームごとに違う。
- 日本語を含む XML は UTF-8 のバイト列で送る。

### 手元の保存

- 置き場所は `~/.cache/somu-search/<vol>.json`（項目定義も同じ場所）。リポジトリの外。
- 保存した日時を記録し、検索結果に「いつ時点のデータか」を出す。

### 検索結果の出し方

- ヒットしたレコードごとに、item_id、ヒットした項目（前後を切り出した抜粋）、ほかの短い項目を出す。詳細画面の URL も添える。形式は eb-api-mcp の `buildDetailUrl` と同じく `<ebase-viewer-url>/DispDetail.do?volumeName=<vol>&itemID=<item_id>`（ワイの判断）。
- 件数が多いときは上限を設けて、総件数を出す。
- 半角/全角・大文字/小文字の違いは同一視する。IP のような記号入りの文字列もそのまま部分一致で当たること。

### 添付

- `getItemImage` で一覧を取る。添付の URL は `<添付ベース>/<vol>/imag/<filename の \ を / にしたもの>`。
- テキスト化:
  - PDF: `pdftotext -layout`（nix で入っている）
  - docx / xlsx: zip 内の XML を標準ライブラリで読む
  - 旧形式の .doc / .xls: 現環境にテキスト化の道具が無い。「読めない」と返し、URL を出して止める（ワイの判断）
- `link_comment` に `old` を含む添付は旧版として、既定で後ろに回すか除外する。
- 取ったファイルは一時ディレクトリに置き、テキストだけを返す。

## SKILL.md に書くこと

- 起動のきっかけ: 「〇〇のIP」「社内規定で〇〇」「ルールDBで〇〇」「総務パックで〇〇を調べて」など。
- よく使うボリュームの早見表（ボリューム名と用途だけ。ID はボリューム一覧で引けるので、書いても社内情報としては軽い。書くかどうかはビルダーの判断）。
- 手順: ボリュームを選ぶ → `search` → 足りなければ語を変える／別ボリューム → 本文が要るなら `files` → `text`。
- 読み方の注意: ミラーなので本番より遅れることがある。改定日と添付の版が食い違うことがある（例: 規定の改定日より添付PDFの版が古い）。
- 止まったときの表（`.mcp.json` が無い、社内ネットワークに繋がっていない、など）。

## ビルダーに任せること

- サブコマンドの名前・引数の細部、出力の書式。
- 検索結果の件数上限、抜粋の長さ。
- 項目数の多いボリュームでの取り方の工夫（spec_type ごとの分割など）。
- テスト方法。少なくとも「IP管理で既知の IP を引く」「社内規定でテレワークを引き、添付PDFの本文が出る」の2つは実機で通すこと。
