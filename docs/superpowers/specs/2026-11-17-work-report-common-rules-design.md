# work-report: 月・水・金の共通組み立てルール

## 意図

2026-11-17 の月曜モード（会議ずれ込みで火曜実施）で、スキル出力をユーザーが何度も組み直した。
直した方向は一貫しているので、スキル側のルールにして次回から最初の出力で近い形を出す。

- 見出しはリポジトリ単位ではなく **案件 → 流れ → 行**。案件を見れば読み手は何の話か分かる
- 作業量の多い PR を1行に詰め込まない（「作業量の割に報告がまとまりすぎ」）
- チャットで話しただけ・ほぼ手を動かしていない作業は出さない
- 月曜の会議は **チャットアプリの会議**。研修など無関係なものは出さない
- 月曜は「先週の作業実績」に加えて「現在対応中の作業」「今後の作業予定」を出す

## 目標 / 非目標 / 反目標

- 目標: 月・水・金で共通の組み立てルールを1か所に書き、モード差分は小さい表で持つ
- 非目標: 会議ずれ込み時のモード自動判定（口頭で指示する運用のまま）。todo.md からの対応中収集（todo が会議時点で更新されていないことが多い。整備されたら再検討）
- 反目標: 金曜週報が詳細すぎる形に戻ること（`feedback/work-report-detail-level.md` で7回差し戻し済み）

## 採用案（B: 共通ルールを1か所にまとめる）

検討した案:
- A. 各モードの節を個別に書き換え → 同じルールが3か所に重複し、片方だけ直してずれる
- **B. 共通の「組み立てルール」節＋モード差分表（採用）**
- C. B＋対応中・予定の収集をスクリプト化 → gh 検索2〜3本で済むため過剰。手順内のコマンドで足りる

## 共通ルール（月・水・金）

1. **階層は 案件 → 流れ → 行**。案件 = 顧客・プロダクト単位（プラス社デモ、シフトオン、eBASEサポートAI 等）。
   流れ = 案件内で目的が異なる作業のまとまり（例: シフトオンの「第1弾フィードバック対応」「APIキー管理のIDCF展開」「画面・機能の改修」）。
   流れが1本しかない案件は流れの見出しを省く。行は作業が進んだ順に並べる
2. **リポジトリ名は見出しにしない**。複数リポジトリにまたがる対応は同じ流れの下に並べる
3. **行の粒度**: 1PR は1行を超えて割らない（従来どおり）。逆に、作業量の多い PR 群を1行に詰め込まない。
   1つの対応が複数 PR にまたがり作業量が多いときは、対応名を見出しにして PR ごとの行を下に並べる
4. **出さないもの**: チャットでの相談・回答が中心で、コード・PR・issue コメント・資料のどれも残っていない作業
5. **レビュー**: 対象 PR が属する案件の下に置く（リポジトリ単位ではない）。対象名のみ・括弧書きなしは従来どおり。どの案件にも属さないものは「MCP・スキル」等のテーマ見出しにまとめる
6. **状態の扱い**: 実績の行に（対応中）等の状態は書かない。期間中に手を動かしたものは未完了でも実績に載せる
7. **本番反映などの事実は一次情報で確認する**: 「本番に出た／出ていない」を書く・答えるときは、PR 本文の「反映の順序」から推測せず、デプロイ workflow の実行記録・リリースタグで確かめる
8. 用語はコード内の呼び方ではなく先方・会議での呼び方にする（例: 「訴求リンク」→「リンクボタン」）

## モード差分

| | 月曜 | 水曜 | 金曜 |
|---|---|---|---|
| 対象範囲 | チャットアプリ関連（AI-search・サポートAI・各デモと、それを支える API・MCP・設定・key-service、エージェント調整用スキル）。研修は除く | AI＋その他 | AI＋その他 |
| セクション | 先週の作業実績／現在対応中の作業／今後の作業予定 | 実績のみ | 工数＋作業内容（従来どおり） |
| AI/その他の見出し | なし | なし（AI系を先、その他を後に並べる） | なし（従来どおり） |
| 行の抽象度 | 共通ルール3 | 共通ルール3 | テーマ単位で抽象的（従来どおり、PR番号・技術詳細なし）。階層・除外・レビュー配置のみ共通ルールを適用 |
| 工数の単位 | — | — | 案件単位（作業内容の見出しと揃える） |

## 月曜の「現在対応中」「今後の予定」

- 現在対応中: 自分の open PR（Draft 含む）と、自分にレビュー依頼が来ている open PR を `gh search prs` で拾う。
  レビューは「〇〇さんのレビュー」と書く。状態は分かるときだけ括弧で添える。
  PR・issue から読めない進行中の作業（例: 実装は完了し動作確認・依頼文作成中）はユーザーに聞く
- 今後の予定: 自分担当の open issue のうち自分の PR が無いものを参考として示し、issue 化前の予定をユーザーに聞く。担当 issue をそのまま予定にはしない（長期検討中・他者に依頼済みの issue が混ざるため）

- `gh` コマンドの具体形
