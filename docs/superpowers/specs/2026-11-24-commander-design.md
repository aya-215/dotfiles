# 司令塔スキル（/commander）設計

作成: 2026-11-24。手作業版 `~/memo/weekly-plan-2026-11-23.md` を 11/24 に実際に司令塔として使い、その中で決めたことをまとめた。

## 目的と理由

Claude のセッションを開きっぱなしで放っておかないための入口。

- ユーザーは、自分の作業が相手のボールになり、返ってきたら対応が要りそうなセッションを `/handoff` で引き継ぎメモにして閉じる。返ってきたら新しいセッションで `/pickup <キー>` して再開する
- `/handoff` は毎回使うものではない。自分のボールの作業は `~/memo/todo.md`（`/todo` が平日朝に一次データから更新する台帳）にある
- 司令塔は todo（全タスクの概要）と引き継ぎメモ（待ちの詳細）を丸ごと読み、優先順位まで考えて「今どれを、どこで、何を打って始めるか」を出す。Claude から開けるので todo を眺めるより楽、というのがユーザーの動機
- 司令塔の中身は時間が経つと古くなる前提で作る（ユーザー「基本的に司令塔は陳腐化していくイメージ」）。古くなったところは一次情報と照らして直す

## ゴール

1. 開くと、残りの作業を全部、優先度別に理由付きで出す。各項目に「今の状態（動ける／誰の何待ちか）」「起動する場所」「打つプロンプト」を付ける
2. ユーザーに「〇〇のセッションを起動して」と頼まれたら、作業ごとに新しい tmux セッションを立てて claude を起動し、プロンプトを打つ
3. 「〇〇終わった」「〇〇止まった」と言われたらファイルを更新し、一覧を出し直す
4. 「返ってきたもの有る？」と聞かれたら、待ちを全部 gh / GitBucket で確かめ、返ってきたものを出す
5. 待ちが済んでいるのに `status: blocked` のままの引き継ぎメモを見つけ、閉じるかユーザーに聞く

## やらないこと

- ボールが返ってきたことを通知する（プッシュ通知・cron での定期確認）。気づくのは基本ユーザー自身（ユーザー決定）
- 「返ってきたもの有る？」で Rocket Chat・メール・課題DB を見に行く（今は gh / GitBucket だけ。ユーザー決定。ただし取りに行く時間を実測してから足すか決める。下の「あとで決めること」）
- 金曜の来週まとめを別に作る。`/weekly-plan` 案はこのスキルに置き換える（ユーザー決定）
- todo.md を書き換える。「終わった」は司令塔のファイルにだけ書き、todo への反映は次の朝の `/todo` に任せる。`/todo-edit` は呼ばない（あれは「他のスキルからは使わない」と決めてある）
- 司令塔が自分で作業する。起動して最初のプロンプトを打つところまで
- 頼まれていない作業のセッションを勝手に起動する
- 外部アクション（PR コメント・マージ・Rocket Chat 送信）。それは起動先のセッションでユーザーが承認する

## 失敗とみなすこと（動いても駄目なもの）

- 一覧が一次情報とずれている（11/24 の手作業版で、引き継ぎメモが古くて PR #99 はマージ済み・#1308 はレビュー投稿済みなのに「まだ」になっていた）。一覧を出す前の照合を省かない
- 作り直しのときに、このファイルにしか無い情報（その日の判断、どの tmux セッションで作業中か、貼られたチェックリスト）が落ちる
- 動いているセッション（ユーザーが触ったもの）を kill する

## 制約

- 置き場所: スキルは `~/.dotfiles/.claude-global/skills/commander/`（`~/.claude/skills` にリンクされる）
- 決定的な処理（ファイル・メモの収集、PR 状態の取得、引き継ぐ欄の写し、作業場所の存在確認、祝日判定）はスクリプト。並べ方・理由・文章は Claude（`rules/learned-rules.md`「決定的な処理と非決定的な処理を分離する」）
- 引き継ぎメモの収集は `~/.claude/skills/pickup/scripts/find_handoff.py`（引数なしで待ち中の一覧を JSON で返す）を使う
- GitHub は `gh`（2アカウント。認証エラーなら `gh auth switch`）。GitBucket はスクリプトからは ebase-infra の `gitbucket-api/scripts/gitbucket_api.py`、セッション内からは `mcp__gitbucket__*`
- tmux 起動の手順と罠は agent-memory `user-preferences/commander-launch-tmux-sessions.md` にある（zsh の `"$s:tmp"` 問題、フォルダ信頼の確認はユーザーに任せる、動いているセッションは kill せず move-window）
- 応答は関西弁（ユーザー設定）。説明は論点を先に並べる（`rules/learned-rules.md`）

## 作り方の案（Approaches）

| 案 | 内容 | 取捨 |
|---|---|---|
| A. ファイルを持たず、毎回 todo・メモ・PR から作り直す | 古くならない・二重管理しない | このファイルにしか無い情報を残すには todo 等へ書き戻すしかなく、`/todo-edit` の「他スキルから使わない」に当たる |
| B. ファイルを毎回更新する | 軽い・その日の判断が残る・変化が見える | 並べ方や済んだ章が居座り、見落としが溜まる |
| C. 前の司令塔ファイルも材料にして作り直す | 並べ方が毎回新しい | 何を引き継ぐかを Claude が判断すると落とす恐れ |
| D. `/todo` に司令塔モードを足す | todo の収集処理を使える | `/todo` は 1回 17〜33 分（ログ実測）。気軽に開けないので外した |

**選んだもの: B と C の組み合わせ**（ユーザー「よさそう」）
- その日最初に開いたとき: 前の日の司令塔ファイルを材料に、今日の日付のファイルを作り直す（C）。済んだ章・古い並べ方はここで毎日一掃される
- 日中: 今日のファイルを更新する（B）
- C の弱点は、このファイルにしか無い情報を決まった欄に置き、その欄だけスクリプトが前のファイルから一字一句写すことで潰す
- 「2スキル（まとめる／使う）に分ける」案は、まとめると使うが同じセッションで並行し、毎日まとめてもよいという前提になったので取り下げた

## 決まった中身

### ファイル

- 置き場所: `~/memo/commander/<YYYY-MM-DD>.md`（Claude の判断。前の日のファイルは消さず残す）
- 構成（手作業版 `~/memo/weekly-plan-2026-11-23.md` を見本に）:
  1. 祝日と期限（11/23 が祝日でリリース 11/24 と重なった例があるので先頭）。今日から2週先まで出す（金曜に「来週分も出して」と頼まれても足りるように）
  2. 引き継ぐ欄: スクリプトが前のファイルから写す。中は次の小見出しに分ける
     - 期限: todo の next 欄（「（11/25）」等）・引き継ぎメモ本文・貼られたチェックリストから Claude が拾って足す。次の日以降はこの表を信じる（todo.md に期限の欄が無いため）
     - 済んだこと: 「〇〇終わった」と言われたもの。作り直しのとき一覧から外す。todo からその行が消えた（完了・削除）らスクリプトが外す。todo に残っているものは「todo 側も `/todo-edit` で閉じる？」と1行出す（一次情報に跡が残らない完了＝RDP 作業・口頭で済んだ件・決めごとが、翌朝の `/todo` で戻ってくるのを防ぐ。ユーザー決定）
     - 作業中の tmux セッション: スクリプトが `tmux ls` と照らし、もう無いものを自動で外す
     - メモ: その日の判断（「1は後回し」）、貼られたチェックリスト、決めることの経緯。一字一句写す。作り直しのとき古そうな行を「消してええ？」とまとめて聞き、ユーザーが OK したものだけ消す
  3. 優先度別の一覧: 最優先（期限当日に直接かかわる）／高（その前に済ませたい）／中（今週中・期限あり）／低（期限なし）／返事待ち。各項目に理由・今の状態・起動する場所・打つプロンプト
  4. 同じ場所を使う項目の注意（ブランチを切り替えない、worktree を切る等）
- 「このファイルの使い方」はファイルに書かない（スキルに持たせる。毎回コピーすると古い版とずれるため）

### 材料

- `~/memo/todo.md` 全部（`## 確認待ち`／`## やる`／`## 待ち`。`## 完了` は除く）
- 待ち中の引き継ぎメモ（`find_handoff.py` 引数なし）。メモの本文から PR・issue の URL と番号を拾い、todo の行の参照（`epc#1296`、`gb:<repo>#109`、`ebpm:No…`、`rc:…`）と突き合わせて同じ案件をまとめる。1件の案件に issue 番号（todo）と PR 番号（メモ）が別々に付いていることがある（例: todo `epc#1296`／メモ PR #1316）
- PR・issue の状態（open/merged/closed、レビュー判定、最新コメントの日時と書いた人、自分の最新コメント以降に相手のコメントがあるか、CI の失敗）。gh と GitBucket だけ。Rocket Chat・課題DB・メールで返事が来る待ちは「どこを見ればよいか」（例: Rocket Chat の河合さんの DM）だけ出す
- 前の日の司令塔ファイル（作り直しのとき）
- 起動する場所: todo の参照の頭から作業場所を引く対応表をスクリプトに持たせる（例: `epc#` → `~/src/github.com/ebase-dev/ebase-portal-chat`、`gb:<repo>#` → `~/src/192.168.208.80/gitbucket/<owner>/<repo>`、`ebpm:` は引き継ぎメモの作業場所）。引き継ぎメモがある項目はメモの「元のセッション」の作業場所を優先。打つプロンプトまで付けるのは、引き継ぎメモがある項目と場所が分かる項目だけ。`rc:` や参照の無い行は概要だけ（Claude の判断）

### 最初の1回

前の日のファイルが無いので、手作業版 `~/memo/weekly-plan-2026-11-23.md` から引き継ぐ欄に当たる中身（11/24 の判断、tmux セッション `pilot-p11`・`hankyu-102`、シフトオンのチェックリスト、期限の表）を Claude が一度だけ手で移す（Claude の判断）

### 動き

1. **開いたとき**: 今日のファイルが無ければ作り直し、あれば更新。どちらも一覧を出す前に PR・issue の状態を照合する
2. **「〇〇終わった／止まった」**: 今日のファイルを更新し、一覧を出し直す。引き継ぎメモの待ちが済んだなら `status: resolved` にしてよいか聞く
3. **「返ってきたもの有る？」**: 待ちを全部照合し、返ってきたもの（相手のコメント・レビュー・マージ・CI 結果）を、再開のプロンプト付きで出す
4. **「〇〇のセッションを起動して」**: tmux セッション（名前は「場所-課題番号」）を立て、`claude '<プロンプト>'` を打つ。プロンプトには再開キー・ユーザーの言葉・注意（ブランチを切り替えない等）を入れる。起動後に capture-pane で確かめ、フォルダ信頼の確認で止まっていればユーザーに伝える
5. **済んだのに開いたままのメモ**: 照合で待ちが済んでいる（PR がマージ済み等）のに `status: blocked` のメモを出し、閉じるか聞く

## 作る人に任せること

- スキル名（Claude の判断で `commander`）とスクリプトの分け方・言語（既存に合わせるなら Python、`python3 -I`）
- 照合の具体的な判定（「返ってきた」をどの条件で言うか）。最低限: 自分の最後の発言より後に相手のコメント・レビューがある、マージ・クローズされた、CI が変わった
- 優先度の付け方の細則（期限、ほかの作業を止めているか、同じ場所を使うかの順で効かせる）
- 祝日の判定方法
- テスト（スクリプト部分）
- todo.md の行の書式は `scripts/todo-ai/` の parser を流用できるなら流用する

## あとで決めること

- Rocket Chat・メールの返事も「返ってきたもの有る？」で見に行くか。取りに行くのにかかる時間を実測してから決める（ユーザー「とりに行く時間によってはあると便利なので実測して決めたい」）。Rocket Chat の MCP は 11/24 につながらなかった
