# プロンプトキャッシュの温め続け（B）と引き継ぎスキル（A）設計

作成: 2026-11-10

## 目的と背景

ユーザーは、PR の確認待ち・レビューへの返答待ち・営業さんの作業待ちのあいだ、Claude Code のセッションを開いたまま置き、返事が来たら同じセッションで続きを依頼する。追加で渡す文脈が最小限で済むので楽だが、プロンプトキャッシュ（サブスクで 1 時間 TTL）が切れると、次の 1 リクエストで会話全体を書き直す。

実測（2026-10-09〜11-10、メイン会話 17,046 リクエスト、全て Opus 5.5）:

- 1 時間以上空けてキャッシュが切れたのは 141 回（1 日 4.4 回）。API 換算で総額 $1,663 のうち約 $295（17.8%）が書き直しの上乗せ
- 「55 分ごとに ping して温め続けた場合」の試算: 1〜8 時間の待ち（78 回）は書き直し $169 → 温め $8。翌日再開（37 回）は $104 → $54。24 時間以上（21 回）は $41 → $88 で逆に高い
- ping 1 回の代金は会話全体のキャッシュ読み（$0.20/MTok）で、書き直し（$8/MTok）の約 1/40
- 1 時間以上放置された区切りのうち約半分は二度と再開されていない（作業が終わったまま開いているもの）。温め続けるとこれは純粋な無駄になる
- 平日の夜に置いて翌日再開した 34 回: 放置は中央値 16.3 時間、再開時刻は中央値 10:48、12 時までに 24 回

ユーザーの運用方針（ユーザーの判断）:

- 基本は全てのセッションを温め続ける（B）
- 誰かの判断待ちのセッションは引き継ぎを書いてセッションを消す（A）。引き継ぎを書いたセッションはユーザーが自分で消すので、B 側で特別扱いしない
- 自分で判断できるが手を付けていないセッションは、温めるか /compact かをユーザーがその都度判断する

## B: 温め続ける mod

### ゴール

- 対話セッションが待っているあいだ、キャッシュの期限が切れる前にフォークで ping してキャッシュを生かし、戻ったときの書き直しをなくす
- 本体の会話に何も足さない
- 使った結果を後で振り返れる記録を残す

### 非ゴール

- 祝日の判定（必要なら後で足す）
- キャッシュ切れを送信前に警告する機能（prompt-cache-control の表示で足りている）
- ping の効果の自動集計スクリプト（振り返りのときに作る）

### アンチゴール（動いても失敗とみなすもの）

- ping のやり取りが本体の会話に残る
- 外れた ping（キャッシュに当たらない ping）を送り続けて、書き直しより高くつく
- 金曜の夜〜週末に温め続ける

### 作り方（決定済み）

- [chrisvaillancourt/claude-cache-keeper](https://github.com/chrisvaillancourt/claude-cache-keeper)（commit `46570fd`、MIT）を `.claude-global/mods/cache-keeper/` にコピーして使う。既存の外部 mod（`prompt-cache-control`）と同じ運用:
  - `LICENSE` を残し、取得元と commit を `.claude-global/mods/README.md` の一覧に書く
  - `.claude-plugin/types/` を `.gitignore` に入れる（本体が型を書き出すため。リポジトリは PUBLIC）
  - `CLAUDE_CODE_PLUGIN_DIRS`（`.claude-global/settings.json` の `env`）にパスを足す
  - 手を入れた箇所を README に書き、取得元から差し替えるときに当て直せるようにする
- 選んだ理由: ping が `$.model.fork`（本体の会話に残らない）、戻った最初のリクエストがキャッシュに当たったかを自分で確かめて外れたら自動で止める、ping ごとの記録がある、Team アカウントで `classic.*` と `session.compact` が飛ばされる環境（このユーザーの環境）への代替処理がある。判断の部分が `hooks/policy.ts` の純粋関数に分かれていてテストがある
- 手を入れるのは判断の部分（`hooks/policy.ts` の `decide` と、その設定値）。テストを先に直してから実装を直す

### 止めるルール（決定済み）

元の「最後の作業から `maxIdleHours`（8 時間）で止める」を、次の時刻ルールに置き換える。基準時刻は元と同じく最後の作業（`lastTurnAt ?? lastRequestAt`）、時刻はマシンのローカル時刻（JST）。

| 最後の作業の曜日・時刻 | 温める期限 |
|---|---|
| 月〜木 | 翌日 12:00 |
| 金（17:00 より前） | その日の 17:00 |
| 金 17:00 以降 | 温めない |
| 土・日 | 温めない（わしの判断。週末に作業して置いたセッションは月曜まで持ち越さない） |

加えて、1 回の放置（最後の作業から次の作業まで）につき ping は最大 20 回。期限より先に 20 回に達したら止める。

- 20 回は時刻ルールの保険ではなく、費用の上限として効かせる（ユーザーの判断）。20 回目は最後の作業から約 18 時間 20 分後で、キャッシュは約 19 時間 20 分で切れる。つまり平日 16:40 より前に置いたセッションは、翌日 12:00 より前に冷える。ユーザーはこれを承知で、まず 20 回で使い、記録を見て損得を測りながら調整する
- `/keepwarm for|until` でユーザーが自分で延ばした期限の中では、回数上限を見ない（わしの判断。明示して延ばしたものが黙って切れないように）
- 手で打った `/keepwarm now` の ping は回数に数えない（わしの判断）。元の実装（`register.ts` の `ping` 内で当たったら `pings` を増やす）は手動でも数えるので、自動 ping だけを数えるように直す

元の仕組みのうち、そのまま残すもの:

- `/keepwarm for|until|on|off|auto|now|status` は残す。`for` / `until` は時刻ルールより優先して期限を延ばす（元の挙動と同じく、縮めはしない）
- `minContextTokens`（60k 未満は温めない）、キャッシュが外れたら止めて同じバージョンの間は自動 ping を休む仕組み、5 分 TTL のときに止める仕組み、`claude -p` を除外する仕組み

止めた理由は記録に残す（元の `StopReason` に、時刻ルールで止めたものと回数上限で止めたものを足す）。

### 記録

元の記録（`~/.claude/cache-keeper/<セッションID>.jsonl`。ping ごとの使用量・利用枠の増減・API 換算額、止めた理由、戻ったときの当たり確認）をそのまま使う。2 週間ほど使ったあと、この記録を集計して「浮いた額」と「ping にかかった額」を比べ、時刻ルールと回数上限を見直す。特に「20 回で止めたあとに戻ってきて書き直した」件数と額を数え、上限を上げるべきかを判断する（ユーザーの判断で、まず 20 回で始めて測る）。

### 確認方法

- `claude plugin test` / `claude plugin validate` / `nix shell nixpkgs#typescript -c tsc -p <mod>` が通る
- 時刻ルールと回数上限のテスト（曜日・時刻の境目: 木 23:59 → 金 12:00 期限、金 16:59 → 17:00 期限、金 17:00 → 温めない、土・日、20 回目で止まる、`/keepwarm until` が期限を延ばし、その中では 20 回を超えても止まらない、手動の `/keepwarm now` は回数に数えない）
- 実機: 使い捨ての tmux セッションで起動し（送り先は pane id で指定する。agent-memory の `tmux/send-keys-into-throwaway-session-pitfall.md` 参照）、`/keepwarm now` で ping がキャッシュに当たることと、記録ファイルに 1 行増えることを確かめる

## A: 引き継ぎスキル

### ゴール

- 誰かの判断待ちになったセッションの状態を、ユーザーが `/handoff` で残してからセッションを消せる
- 返事が来たら、新しいセッションで `/pickup <PR番号やURLや言葉>` を打つと引き継ぎが見つかり、すぐ続きを始められる

### 非ゴール

- PR・課題DB・Rocket Chat の新しい動き（マージ・レビュー・コメント）を取ってくること。ユーザーは何か動きがあってから「マージされたから残作業調べて」のように指示するので、動きは来る前提でよい（ユーザーの判断）
- 引き継ぎを書くタイミングの自動化（起動はユーザーが手でする。ユーザーの判断）
- `my-tasks` スキルとの連携（後で足す余地として残す）

### アンチゴール

- 引き継ぎが残っているのに `/pickup` で見つからない（当たりすぎて選ぶ手間が増えるほうがまし。ユーザーの判断）
- 引き継ぎに決まったキー欄を何個も埋めさせる（ユーザーの判断: 複数キーの管理はややこしいのでしない）
- 引き継ぎの置き場所を agent-memory と別に作る（二重管理になる）

### `/handoff`

- スキル置き場: `.claude-global/skills/handoff/`
- 決まった処理（スクリプト）が集めるもの: 作業ディレクトリ、リポジトリの remote とブランチ、そのブランチの PR（GitHub なら `gh pr view`。GitBucket は Claude が MCP で調べて本文に書く）、セッション ID、書いた日時
- Claude が書くもの: 題名、誰の何を待っているか、今の状態、決めたこととその理由、次にやること、関連（PR の URL、課題DB の課題No、Rocket Chat のスレッド等を本文にそのまま書く）
- 保存先: agent-memory の `memories/work-in-progress/`。frontmatter は agent-memory の規約（`summary` / `created` / `status` / `tags`）に従い、`tags` に `handoff`、`status` は待ち中を `blocked`、終わったら `resolved`。セッション ID は本文の「元のセッション」欄に `claude --resume <ID>` の形で書く
- 書いたあと、ユーザーがセッションを消す

### `/pickup`

- スキル置き場: `.claude-global/skills/pickup/`
- 探すのはスクリプト（Claude に推測させない）:
  - 引数の数字は表記揺れを吸収して当てる（先頭の 0、`#`、`PR`、`No` を無視。`7400` で `No00007400`、`1210` で `#1210` や `.../pull/1210` に当たる）。数字以外の言葉は、全部を含むもの（大小文字無視）に当てる
  - 探す順: `handoff` タグで `blocked` のもの → `handoff` タグの全て（`resolved` 含む）→ `work-in-progress/` 全体 → agent-memory 全体。最初に当たった段で止める
  - どこにも無ければ、`find-session` スキルで過去のセッションを探すことを提案する
  - 引数なしなら、`handoff` タグで `blocked` のものを新しい順に一覧
- 1 件なら読み込む。複数ならユーザーに選んでもらう（題名・日付・待ち相手を並べる）
- 読み込んだら: 引き継ぎの内容を短く示し、記録された作業ディレクトリが今と違えばそう伝え、文脈が足りなければ `claude --resume <ID>` で元の会話に戻れることを示す。そのうえでユーザーの指示（「マージされたから残作業調べて」等）に従って続ける
- 作業が終わったら `status: resolved` にする

## 制約

- dotfiles は Nix/Home Manager 管理。`~/.claude` は `.claude-global/` へのリンクなので、そこを直接編集してよい
- `settings.json` にはユーザーの未コミット変更が混ざりやすい。コミットは自分の変更だけを index に載せる（agent-memory の `wsl-git/partial-staging-unidiff-zero-hunk-merge.md` 参照。`-U0` の hunk 単位で外すと隣の変更を巻き込む）
- `claude plugin` コマンドは `settings.json` のキーの並びを変えることがある（`claude-code/plugin-cli-reorders-settings-json.md`）
- 外部コードは取り込む前に中身を読む（cache-keeper は読了: 通信は `$.model.fork` のみ、ファイル書き込みは `~/.claude/cache-keeper/` の記録だけ）
- コメントは `rules/code-comments.md`、シェルは `rules/shell-conventions.md` に従う

## 作る人に任せること

- 時刻ルールの値（12:00 / 17:00 / 20 回）を mod の設定（`userConfig`）として出すか、定数にするか
- 時刻ルールで止めた理由の名前
- `/handoff` でセッション ID を取る方法（スキル本文の変数置換・環境変数・作業ディレクトリに対応する `~/.claude/projects/` の最新 jsonl など、確実なものを調べて選ぶ）
- 検索スクリプトの言語（bash か python）と、引き継ぎのファイル名の付け方
- 引き継ぎ本文の見出しの細かい形

## わしの判断（ユーザー確認待ち）

- 土・日に置いたセッションは温めない
- cache-keeper の `minContextTokens`（60k 未満は温めない）をそのまま使う
- 待ち中の状態に agent-memory の既存の `blocked` を使う
- `/keepwarm for|until` の期限の中では回数上限を見ない
- 手動の `/keepwarm now` は回数上限に数えない
- A の `/pickup` は引き継ぎを見つけて読み込むだけにし、課題DB の番号は探すときに当たればよいとする

## 既知の気がかり

- フォークの ping が元の会話のキャッシュに当たらない不具合報告がある（anthropics/claude-code#100083、Message Threads と会話途中の system message が両方有効なとき。2.1.291、open）。cache-keeper は外れたら自動で止めるので、被害は外れた 1 回分で止まる
- prompt-cache-control の表示（入力欄の下の `cache 99% · 59:52`）は、メイン会話のリクエストだけを見て残り時間を数える。フォークの ping で期限が延びても、表示は延びずに「切れた」と出る可能性がある。作る人は実機で確かめ、ずれるなら記録したうえで、直すかどうかをユーザーに聞く
