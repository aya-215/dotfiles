# Rocket Chat 情報取得の複数ルーム対応 設計

## 背景・目的

日報（`daily-review` / cron）と `work-report` はどちらも Rocket Chat を情報源に使っているが、**取得対象が `mori.a-times` 1チャンネルに固定されている**。そのため自分宛の依頼や案件チャンネルでの作業が収集から漏れる。

2026-07-28 の調査で、実際に取り逃していた情報が確認された:

| 取り逃していた情報 | 発生場所 | 内容 |
|---|---|---|
| 週報提出依頼 | `websol-dev-ai-hub` | 7/27 松本さんから `@mori.a` 付きで SharePoint Loop への記入依頼（`AI開発` にも 7/21 に `@all` で同種の依頼あり） |
| ちらしJSON項目のフィードバック依頼 | `e食なび` | 7/23 増田さんが掲載商品パラメータ一覧を共有し「処理上の不都合があれば項目名の見直しを検討します」と打診。未応答 |
| AIちらし検索の打ち合わせ調整 | `e食なび` | 7/22〜7/27 の日程・場所調整スレッド（9返信） |
| 未完の約束 | DM（畑上さん） | 7/27「今週中に対応します」と回答。タスク候補だが日報・報告のどちらにも現れていなかった |

いずれも `mori.a-times` には存在せず、1チャンネル固定である限り構造的に拾えない。

## 現状の構造（調査結果）

同じ「`mori.a-times` だけ見る」ロジックが**2つの異なる実装で二重化**している。

| | 日報（cron 22:10） | work-report（対話） |
|---|---|---|
| 取得方法 | REST API 直叩き（`scripts/daily-review/fetch-rocketchat.sh`） | MCP ツール（`mcp__rocketchat__*`） |
| 対象指定 | `RC_CHANNEL` 環境変数**1個** = 構造的に1chのみ | SKILL.md に `mori.a-times` と記述 |
| 出力 | プレーンテキスト → クラウド POST | Claude のコンテキストへ直接 |
| 文字数制約 | `MAX_RC_CHARS=15000`・`MAX_PAYLOAD_CHARS=60000` | なし |
| Claude の有無 | 不在（cron・Agent SDK 不使用） | あり |

さらに `effort-estimate` / `quarterly-dev-report` / `rocketchat-search` も同種のロジックをコピーで保持している（本設計のスコープ外・後述）。

## API 能力の実測結果

REST API 直叩きと MCP ツールで能力差があることが判明した。**これが設計の核**。

| 能力 | MCP ツール | REST 直叩き |
|---|---|---|
| 購読ルームのみの列挙 | ❌ `list_channels` は未参加のパブリックchも返す（254件中パブリック166件、実購読は17件） | ✅ `rooms.get` で購読105件（`d`:47 / `p`:41 / `c`:17） |
| 最終メッセージ日時 | ❌ 返らない（`id/name/type/usersCount/messages/topic/description/readOnly` のみ） | ✅ `lm` フィールドで取得可 |
| 期間による事前絞り込み | ❌ 不可能（全件の履歴を引くしかない） | ✅ `lm` で 105件 → 38件（対象期間 7/21〜7/28）に**1コール**で絞れる |
| `from:` 検索 | ✅ 効く（存在しないユーザーで0件を確認） | ✅ 効く |
| `after:`/`before:` 検索 | — | ❌ **効かない**（リテラル扱いで0件になる） |
| 履歴の期間指定 | ✅ `oldest`/`latest` | ✅ `oldest`/`latest` |

補足:
- `_updatedAt` と `lm` は対象期間では両方38件で一致したが、`_updatedAt` はトピック変更・メンバー変更でも更新されるため、意味的に正確な **`lm` を採用**する。
- `search_messages` / `chat.search` には期間パラメータが存在しないため、期間フィルタは取得後に `ts` で判定する。

**結論:** REST 直叩きの方が能力が高い。`lm` による事前絞り込みがあるため、MCP 前提で検討していた「全チャンネル総当たり（約140コール）」は不要になる。

## 設計

### アーキテクチャ

決定的な処理（ルーム列挙・期間絞り込み・2軸判定）を共通シェル層に集約し、非決定的な処理（作業内容の分類・要約）だけを Claude に残す。`learned-rules.md` の「決定的な処理と非決定的な処理を分離する」に従う。

```
                  scripts/lib/rocketchat.sh   ← 新設（決定的な層）
                  ┌──────────────────────────────────┐
                  │ 1. rooms.get → 購読ルーム列挙      │
                  │ 2. lm で期間フィルタ               │
                  │ 3. 各ルームの履歴取得              │
                  │ 4. 2軸判定（発言 / メンション）     │
                  │ 5. スレッド展開                    │
                  │ 6. 整形して stdout                 │
                  └──────────────────────────────────┘
                       ↑                        ↑
        ┌──────────────┘                        └──────────────┐
   fire-daily-review.sh                          work-report SKILL.md
   （cron 22:10・Claude不在）                     （対話・Bash 経由で呼ぶ）
   （DM なし）                                    --include-dm
   --budget 15000                                予算指定なし
```

`work-report` は MCP ツールの利用をやめ、Bash 経由でこのスクリプトを呼ぶ。これにより取得ロジックが1箇所になり、両者の挙動が構造的に一致する。

### インターフェース

```bash
rocketchat.sh --from YYYY-MM-DD --to YYYY-MM-DD \
              [--include-dm] \
              [--budget N] \
              [--format text|json]
```

| オプション | 既定値 | 説明 |
|---|---|---|
| `--from` / `--to` | 必須 | 対象期間（JST。内部で UTC ISO8601 に変換） |
| `--include-dm` | 無効 | DM を候補プールに含める。cron は指定しない、work-report は指定する |
| `--budget` | 無制限 | 出力の文字数上限。超過時はルーム単位で落とす（後述） |
| `--format` | `text` | `text`: 「HH:MM user: msg」形式 / `json`: 構造化出力 |

**`--scope` は設けない。** 当初 `--scope mine|all` を検討したが、これは2つの独立した軸を1つのフラグに混ぜていた設計ミスだった。正しくは:

| 軸 | 制御するもの | 実装 |
|---|---|---|
| 候補プール | DM を含めるか | `--include-dm` |
| 絞り込み | どのルーム・メッセージを採用するか | **常に適用**（呼び出し側から無効化できない） |

絞り込みを呼び出し側の指定で無効化できる設計にすると、`grafana-alert`（45,553文字）や `reviewboard`（47,641文字）のような自動投稿チャンネルが work-report 側に流入する。絞り込みは常時適用とする。

### 採用の判定（2段階）

固定の除外リストは持たず、内容から機械的に判定する。**ルーム単位とメッセージ単位の2段階**で絞る。

#### 第1段階: ルームの採用（2条件のいずれか）

1. `username == "mori.a"` の発言が期間内に存在する
2. 本文に `@mori.a` が含まれるメッセージが期間内に存在する

`grafana-alert` や `reviewboard` のような自動投稿チャンネルは、どちらも満たさないため自然に落ちる。除外リストの保守は不要。

**`@all`/`@here` は条件に含めない。** 当初は「`AI開発` の `@all` 週報依頼を取り逃していた」ことを根拠に条件として入れたが、実データ（7/27）を検証すると:

| `@all` 由来で採用されたルーム | 内容 | 評価 |
|---|---|---|
| `AI開発` | 新人の玉木さん紹介 | ノイズ（自分にアクションなし） |
| `2026年度新人研修（大阪開発）` | 他人の質問と回答 | ノイズ（自分は無関係） |

さらに、根拠としていた週報依頼は **`websol-dev-ai-hub` で `@mori.a` 付きでも届いていた**ため、条件1・2だけで拾える。`@all` は「全員向けアナウンス」であり自分へのアクション要求とは相関しないため、条件から外す。

#### 第2段階: メッセージの絞り込み

ルームの性質によって2通りに分ける。

##### (a) 全メッセージを採用するルーム

- **自分の times（`mori.a-times`）**: 自分の作業ログそのもの。他人の発言も自分が出した話題への反応であり、すべて文脈として意味がある
- **DM**: 1対1のため、無関係な発言が構造的に存在しない

##### (b) 絞り込むルーム（他人の times・チャンネル・グループ）

自分が数件しか絡んでいないのに全履歴を持ってくると大半が無関係な雑談になるため、以下だけを残す:

- 自分の発言と `@mori.a` を含むメッセージ（**起点**）
- 起点が属するスレッドの親メッセージと、同一スレッド内の他の返信
- **起点の前後30分以内のメッセージ**

**時間窓が必須である理由:** 当初はスレッド展開だけで足りると考えたが、実データで破綻が確認された。`kawai.t-times` はスレッドを使わずフラットに会話しており（対象期間の非関連136件にスレッド属性が1つもない）、スレッド前提の絞り込みでは文脈が全て落ちる。

7/23 の MCP vs スキルの技術議論での実例:

| 時刻 | 発言 | 起点のみ | ±30分 |
|---|---|---|---|
| 07:21 | kawai.t「MCP化したがこれでよかったか分からん」（質問） | ❌ | ✅ |
| 07:24 | sato.m「スキルの方が持ち運びしやすい」 | ❌ | ✅ |
| 07:34 | sato.m「モデルが賢くなったのでCLIでいい」 | ❌ | ✅ |
| **07:37** | **mori.a「自分で作る分には全てskillでいい」** | ✅ | ✅ |
| 07:40 | kawai.t「確かに認証の有無が一番大きい違い」（反応） | ❌ | ✅ |

起点のみでは自分の発言だけが宙に浮き、何に答えたのか判別できない。日報の材料として使えない。

**削減率の高さは効率ではなく危険信号として扱う。** 起点のみ方式では他人の times で98%削減となったが、これは文脈の98%喪失を意味していた。

##### (a)(b) を分ける理由

時間窓は起点からの対称距離で切るため、**自分が話題を投げて相手が後から議論を続けた場合に尻尾が切れる**。自分の times はまさにその構造の場であり、この弱点が最も出る。

7/27 の OpenAI 残高切れインシデントでの実例:

| 時刻 | 発言 | ±30分のみ |
|---|---|---|
| 00:42 | mori.a「組織のAPI利用上限に達した」 | ✅ 起点 |
| 00:45 | mori.a「ログです」 | ✅ 起点 |
| 01:13 | tanaka.k「請求方法が前払いに変更されていた」 | ✅ 窓内 |
| **01:47** | matsumoto.h「向こうの対応が変わったってこと？」 | ❌ **落ちる** |
| **01:56** | tanaka.k「はい、自分も同じ認識です」 | ❌ **落ちる** |

自分の最終発言が00:45のため窓が01:15で閉じ、**インシデントの原因究明の結論部分**が欠落する。自分の times を全採用にすることで解決する。

### 庶務・日程調整の扱い

自分の発言がある以上、掃除当番の交代や会議の日程調整も条件1で必ず通る（実例: `奈良高専` の掃除当番、`開発_MDMチーム` の会議時間変更）。これらはシェル層では除外せず、**取得して Claude 側の分類に委ねる**。

機械的に判定できない「日報に載せるべき作業か」の判断を決定的なコードに持ち込まないため。文字数も小さく予算を圧迫しない。

### ペイロード予算の扱い（最重要の変更点）

現状の `fire-daily-review.sh` は文字数超過時にバイト位置で切り捨てている:

```bash
rocketchat_log="${rocketchat_log:0:$MAX_RC_CHARS}"   # ← 無言でカット
```

1チャンネル分なら実害は小さいが、複数ルームに拡張すると**連結の後ろに来たルームが丸ごと消え、しかも気づけない**。同ファイル内のセッション要約処理は「（※ 容量制限のため古い N セッションを省略）」と明示しているのに、Rocket Chat 側だけ無言で欠落する。

これを優先度つきのルーム単位ドロップに変更する:

1. 自分の発言があるルーム（最優先）
2. `@mori.a` の直接メンションがあるルーム
3. それ以外 → 予算超過時はここから落とす

落としたときは `（※ 容量制限のため N ルームを省略: room-a, room-b）` を出力に含める。**バイト位置での切り捨ては行わない。**

#### 予算判定はバイト数で行われる

`fire-daily-review.sh` の予算判定は bash の `${#var}` で行うが、これは**ロケール依存**で、cron 環境（`LANG` 未設定）では文字数ではなく**バイト数**を数える。実測:

```
LANG=ja_JP.UTF-8 → ${#v} = 14   （文字数）
LANG 未設定(cron) → ${#v} = 42   （バイト数）
wc -c            → 42           （どちらの環境でも同じ）
```

日本語は1文字約3バイトのため、文字数で見積もると実使用率を約3倍過小評価する。**`MAX_RC_CHARS` に対する評価は必ずバイト数で行う。**

この両義性を避けるため、`rocketchat.sh` 側の `--budget` 比較は `printf '%s' "$candidate" | wc -c` による明示的なバイト数計測を用いる（`${#var}` は使わない）。

#### 当初の評価の訂正

設計当初に記載した「日次最大 4,303文字＝予算の29%」は**二重に過小評価**だった:

1. **文字数で測っていた** — cron の実効判定はバイト数
2. **スレッド展開の実装前だった** — history が返さない返信が加わって増加した（週次で 13,633 → 19,284文字、+41%）

正しい評価は上表の通り**日次最大 9,608バイト＝64%**。したがって:

- `MAX_RC_CHARS` の変更は不要（15,000 のまま据え置く）
- ただし余裕は36%であり、予算処理（優先度ドロップ）は「異常時の安全弁」ではなく**通常運用で発動し得る機構**として扱う
- 会話量が増えた場合は再計測し、必要なら `MAX_RC_CHARS` の引き上げを検討する（バイト位置切り捨てではないため、超過しても欠落は省略マーカーで明示される）

### cron 送信範囲の制限

cron 経路は `redact.sh` を通した後、外部のクラウドエンドポイント（ルーチンの `/fire`）へ POST する。`redact.sh` は API キー・トークン専用のパターンマッチであり、**会話内容そのものはマスクしない**。

| 経路 | 送信先 | スコープ |
|---|---|---|
| work-report（対話） | ローカルの Claude コンテキスト | `--include-dm` あり（DM 47件を候補に含む） |
| 日報（cron） | 外部クラウドエンドポイント | `--include-dm` なし（DM を候補から除く） |

どちらの経路でも第1・第2段階の絞り込みは適用される。差は DM を候補プールに含めるかどうかだけ。

読むこと（ローカル調査）と外部へ夜間自動送信することは別の行為として扱い、cron 側は範囲を絞る。

### スレッド展開

history 系エンドポイント（`channels.history` / `groups.history` / `im.history`）はスレッド返信を全件返さない。**実測で、9返信のスレッドのうち history が返したのは3件のみだった**（`e食なび` のスレッド `C2TgNffumtDKqiGaf`）。

history から欠落していた6件には以下が含まれていた:

| 時刻 | 発言 | 内容 |
|---|---|---|
| 07-27 03:13 | m.shitagawa | effort低下対応の受領確認 |
| 07-27 03:16 | m.shitagawa | 依頼していた会議資料（Notionリンク）の共有 |
| 07-27 03:16 | mori.a | 「そちらです！非常に助かります」 |

つまり history のみでは「依頼したが未応答」と誤判定する。これは既存の各 SKILL.md にも展開の記述があるが**運用で守られず実際に誤判定が発生した**（2026-07-28 のセッションで、スレッド未展開のまま「返答未確認」と報告し、実際には7/27に解決済みだった）。

対策として、スレッドIDを `tmid`（返信側）と `tcount`（親側）から収集し、`chat.getThreadMessages` で全返信を取得して `_id` で重複排除しながらマージする。共通シェル層の必須処理として実装し、呼び出し側の努力に依存させない。

#### 既知の限界: history 0件のルームでスレッドが取り逃される

**未修正の構造的欠陥。** スレッドIDは対象期間の history に含まれるメッセージの `tmid`/`tcount` からのみ収集する。そのため **history が0件のルームでは `tids` が空になって早期 return し、そのスレッド内に期間内メッセージが存在しても取得されない。** ルーム自体が出力から丸ごと消える。

実測（2026-07-27 単日、`e食なび`）:

| 事象 | 値 |
|---|---|
| 当日の `channels.history` | **0件** |
| 同期間にスレッド内に存在したメッセージ | **3件**（`C2TgNffumtDKqiGaf`）＋3件（`r5ZcmTenpmCYEzbaj`） |
| 出力に現れた `e食なび` | **0回**（ルームごと消失） |

消えていた内容には「そちらです！非常に助かります」（実 ts `2026-07-27T03:16:51Z` ＝完全に期間内）が含まれる。**これは本設計のスレッド展開が防ごうとした「依頼したが未応答」という誤判定そのものの再発経路である。**

### 実装中に発見した計画外の不具合（修正済み）

**JST→UTC 変換の8時間ズレ。** 既存の `fetch-rocketchat.sh` と新規実装の両方に存在した。原因は2つの独立した誤用の複合:

1. `TZ=Asia/Tokyo date -d "..." -u` — `-u` が入力解釈のタイムゾーンも上書きする（POSIX 仕様）ため、JST のつもりが UTC として解釈される
2. `"00:00 +1 day"` — GNU date が `+1` を数値 UTC オフセットと解釈し `day` を無視する

結果、日報は「当日 09:00〜翌 08:00 JST」を取得していた（範囲が23時間）。コード自身のコメントが「JST 00:00〜翌 00:00」と宣言していたため、意図と実装の不一致としてバグと断定した。

実害は測定時点でゼロだった（対象月の自分の投稿72件がすべて 9〜18時台で、9時前の投稿が0件だったため）。ただし境界値検証で JST 00:00〜08:59 の発言がすべて欠落することを確認しており、深夜作業や早朝の投稿があれば取り逃していた。

正しい変換式は、タイムゾーンオフセットを入力文字列に内包する形:

```bash
oldest="$(date -u -d "${from}T00:00:00+09:00" +%Y-%m-%dT%H:%M:%S.000Z)"
latest="$(date -u -d "${to}T00:00:00+09:00 +1 day" +%Y-%m-%dT%H:%M:%S.000Z)"
```

### 予算保証の変更（記録）

旧 `fetch-rocketchat.sh` は `${rocketchat_log:0:$MAX_RC_CHARS}` により常に `MAX_RC_CHARS` 以内を強制していた。新方式の予算処理は「最初のブロックは無条件で採用する」（`out` が空のとき通過）ため、**単一ルームが `MAX_RC_CHARS` を超えた場合はその保証が働かない。**

実データでの評価では単一ルームの最大は 3,501 バイト（`MAX_RC_CHARS` の23%。OpenAI のスタックトレースを含む日の値）であり、即座のリスクは低い。`MAX_PAYLOAD_CHARS`（60,000バイト）の全体バックストップも維持されている。

バイト位置での切り捨てを廃止した結果として受け入れた変更であり、超過した場合も情報の欠落は省略マーカーで明示される。
