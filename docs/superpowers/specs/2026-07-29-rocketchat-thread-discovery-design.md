# Rocket Chat スレッド探索の syncThreadsList 化 設計書

日報 cron と work-report が、期間内に更新されたスレッドの返信を取り逃す問題を解消する。

- 調査記録: `docs/rocketchat-known-limits-investigation-2026-07-28.md`
- 前提実装: `docs/rocketchat-multiroom-2026-07-28.md`（2026-07-28 実装分）
- 対象ファイル: `scripts/lib/rocketchat.sh` / `scripts/lib/rocketchat-test.sh`

---

## 背景と問題

`expand_threads` はスレッドIDを**対象期間内の history に含まれる `tmid`/`tcount` からのみ**収集する。
そのため「親メッセージが期間外にあり、返信が期間内にある」スレッドを発見できない。

### 真の原因は `tshow`

`channels.history` にスレッド返信が現れるかは `tshow` フィールドが決める（実測）。

| `tshow` | 意味 | history に出るか |
|---|---|---|
| `True` | 「チャンネルにも表示」を付けた返信 | ✅ 出る |
| `None` | 通常のスレッド返信 | ❌ 出ない |

7/27 に取り逃していた7件はすべて `tshow=None` だった。
`e食なび` の全 history 500件中、`tmid` を持つ225件はすべて `tshow=True` である。

### 「history 0件」は条件ではない

調査前の想定（`docs/rocketchat-multiroom-2026-07-28.md` の「既知の限界」）は
「history が0件のルームで取り逃す」としていたが、これは誤り。
実測で **history 6件あった `2026年度新人研修（大阪開発）` でも取り逃していた**。

したがって旧ドキュメントが推奨していた案B（history 0件のルームのみ30日遡及）は
**発動条件そのものが誤っている**ため採用しない。

---

## 方針: `chat.syncThreadsList` でスレッドを直接列挙する

```
現状: 期間内 history の tmid/tcount から親IDを推定
変更: chat.syncThreadsList?rid=<room>&updatedSince=<oldest> で
      「期間内に更新されたスレッド」の親一覧を直接取得
```

`syncThreadsList` は各スレッドの `tlm`（thread last message）を返すため、
**親の `ts` が期間外でも `tlm` が期間内なら発見できる**。
history 依存・遡及期間の設定・`tshow` の挙動をすべて回避する。

### 実測による裏付け

`e食なび` 7/27 で `syncThreadsList` の結果と、全 history 500件を辿って見つけた
3スレッドが**完全に一致**した。

```
update=3
  r5ZcmTen ts=2026-06-24T07:19:14.333Z tlm=2026-07-28T05:43:03.125Z  ← 親は33日前
  AWLRMqv5 ts=2026-07-23T10:17:03.654Z tlm=2026-07-27T08:42:04.676Z
  C2TgNffu ts=2026-07-22T07:53:00.896Z tlm=2026-07-27T03:16:51.339Z
```

親が33日前の `r5ZcmTen` は、案Bの30日窓では拾えなかった。

## スコープ

### やること

`expand_threads` のスレッドID収集を `syncThreadsList` ベースに置き換える。
`rocketchat.sh` は日報 cron と work-report の共通層なので、**1箇所の変更で両経路に効く**。

DM（`t="d"`）でも `chat.syncThreadsList` が `success=true` を返すことを実測済み
（3ルームで検証）。`chat.*` 系はルーム種別に依存しないため `--include-dm` 経路も同時に有効化される。

### やらないこと（判断理由つき）

**1. `lm` ゲートの修正 — 実測で実利ゼロ**

`list_active_rooms` は `lm < oldest` でルームを捨てる。`lm` はスレッド返信では進まないため、
理論上は「スレッドのみ活動したルーム」が列挙段階で消える。実際に7月の非DMルーム44件中
12件が「`lm` より新しいスレッド返信」を保持していた。

しかし `lm` ゲートを撤廃した場合に回収できるものを実測すると:

| 日付 | `lm` で除外されたルーム | うち出力対象になる復活 |
|---|---|---|
| 2026-07-23 | 22件 | **0件** |
| 2026-07-27 | 27件 | **0件** |

`lm` は「スレッド返信では進まないが通常メッセージでは進む」ため、
**自分が関与しているアクティブなルームは通常メッセージで `lm` が更新されている**。
`lm` が古いまま取り残されるのは自分が関与していない休眠ルームだった。

候補ルームは 31〜36件 → 58件（全非DM）に増え APIコールはほぼ倍増する。
**コスト倍・実利ゼロ**のため見送る。理論的欠陥としては実在するので後追い候補に残す。

**2. `lm` ゲートに関する警告出力**

`fire-daily-review.sh` の呼び出しは `2>/dev/null` なので cron では見えない（既知事項）。
実害がゼロと判明した事象について、見えない警告を追加する価値はない。

**3. 案B（history 0件のルームのみ30日遡及）**

発動条件が誤っており（上記）、30日窓も実測データで既に不足している。

## 設計

### 変更対象は `expand_threads` のスレッドID収集部のみ

現状（`scripts/lib/rocketchat.sh:145-159`）:

```bash
tids="$(printf '%s' "$hist" | python3 -c '
# 期間内 history の tmid / tcount から収集
for m in ms:
    if m.get("tmid"): ids.add(m["tmid"])
    if m.get("tcount"): ids.add(m["_id"])
')"
```

変更後:

```bash
# chat.syncThreadsList で「期間内に更新されたスレッド」を直接列挙し、
# tlm >= oldest のものを対象にする。
# 併せて従来の tmid/tcount 由来も残す（和集合）。
```

### `tmid`/`tcount` 由来を残す理由

`syncThreadsList` の `updatedSince` の厳密な意味論（境界の開閉、サーバ側の更新判定）を
本調査では確定していない。従来経路を残して和集合を取れば、
**`syncThreadsList` が何らかの理由で取りこぼしても現状より悪化しない**。

重複は既存の `_id` ベースの重複排除で吸収される（変更不要）。

### 期間フィルタは現状のまま維持する

`chat.getThreadMessages` は `oldest`/`latest` を無視する（指定すると0件、省略すると全件）。
取得後の `ts` フィルタ（`rocketchat.sh:229`）は**必須のまま**。
あるスレッドは全31件のうち24件が期間外であり、これを省くと
生きているスレッドの全履歴が毎日の日報に混入する。

スレッド発見の窓が広がるほどこのフィルタの重要性は増すため、
テストで期間外が落ちることを明示的に検証する。

### 失敗時の挙動

既存の `room_history` / `chat.getThreadMessages` と同じ防御を踏襲する。

- `syncThreadsList` のレスポンスが JSON として不正 → stderr に警告し、そのルームは
  従来の `tmid`/`tcount` 由来のみで継続する（和集合の片方が欠けるだけで全体は落ちない）
- 1ルームの失敗が全体を落とさない原則を維持する

## データフロー

```
list_active_rooms  （変更なし。lm >= oldest で絞る）
        ↓ room_id, t, name
room_history       （変更なし。期間内 history を取得）
        ↓ hist JSON
expand_threads     ★ここだけ変更
        ├─ 従来: hist の tmid / tcount            ─┐
        ├─ 追加: syncThreadsList の tlm >= oldest ─┤→ 和集合
        ↓                                          ┘
        chat.getThreadMessages（各スレッド）
        ↓
        _id 重複排除 + ts 期間フィルタ  （変更なし）
        ↓
render_room        （変更なし。第1段階/第2段階の判定）
        ↓
collect_blocks → 予算処理  （変更なし）
```

## テスト方針

既存流儀に従う（`scripts/lib/rocketchat-test.sh`・現在67件）。

- 実 API は叩かない。`RC_CURL` で curl をスタブに差し替え fixture JSON を返させる
- `assert_*` 関数 / `ok:` `NG:` 出力 / 全通過で `ALL OK` + `exit 0`
- 認証情報（`RC_TOKEN` / `RC_USER_ID`）を fixture・ログ・コミットに含めない

### 追加するテストケース

1. **親が期間外・返信が期間内のスレッドを発見する** — `syncThreadsList` が `tlm` で返す
   スレッドの返信が出力に含まれること（本変更の主目的）
2. **`tshow=None` の返信が拾えること** — history に現れない返信の回収
3. **期間外の返信が落ちること** — `getThreadMessages` が全件返しても `ts` フィルタが効く
4. **`tmid`/`tcount` 由来との和集合** — 従来経路のみで見つかるスレッドが失われない
5. **`syncThreadsList` 失敗時の継続** — 不正 JSON で stderr 警告を出し、従来経路のみで継続
6. **DM（`t="d"`）でも `syncThreadsList` を呼ぶこと** — `--include-dm` 経路

### 変異テスト

既存実装で空証明を5件検出した経験（`docs/rocketchat-multiroom-2026-07-28.md`）を踏まえ、
**追加した各テストについて該当コードを壊してテストが落ちることを確認する**。

特に注意する点:

- fixture の親 `ts` を期間内にしてしまうと、`syncThreadsList` を無効化しても
  従来の `tmid`/`tcount` 経路で同じIDが導出され**テストが通ってしまう**
  （既存の空証明「`tmid`/`tcount` の独立性」と同型）。
  親 `ts` は必ず期間外に置く
- 期間フィルタのテストは、fixture の期間外メッセージが時間窓にも入らない位置に置く
  （既存の空証明「DM の窓外検証」と同型）

## 検証（実データ）

実装後、6日分（7/21・22・23・24・27・28）で以下を確認する。

- 7/27 に `e食なび` が出力に現れ、7件が含まれること
- 他の5日で出力が変化しないこと（増分ゼロの再現）
- `--budget 15000` 下で最大日（7/23）が 9,608バイトのまま変わらないこと
- `--include-dm` 経路（work-report・週次 35,042バイト）での増分を測定して記録すること
- `shellcheck` の指摘がゼロであること（`nix run nixpkgs#shellcheck`）
