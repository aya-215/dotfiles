# 日報の品質改善（切り出し要約導入後の第2弾）設計

## 背景と理由

2026-11-10 に日報の入力を「日次の切り出し要約」に切り替え（[前回の設計](2026-11-10-daily-report-day-slice-design.md)）、
10-13〜11-09 の17日を作り直した。2026-11-11 にその17日を、一次情報（全期間要約・git・jsonl）と Rocket Chat で照合した。

| 項目 | 新方式（17日） | 旧方式（12日・基準） |
|---|---|---|
| 切り出しの段階での落とし | 0件 | — |
| 生成での落とし | 31件（重大7件。影響で見ると5件） | 2件（重大2） |
| 根拠不明 | 24件（確信度・高3、区切り外5） | 18件（全件 RC で裏付けあり） |
| 誤分類 | 1件 | 2件 |
| 同じ成果が複数日に重複 | 7組（うち4組は区切り外の混入） | 2件 |
| 書式ドリフト | 1日 | 0日 |

旧方式の構造的な欠陥（日をまたいだ作業が消える）は直った。代わりに次の弱点が見えた。照合の詳細は
`docs/daily-report-day-slice-replay-2026-11.md` と、このセッションの照合報告による。

- **A. 区切り前の話が混ざる。** 区切り外5件と重複4組は、どれも多日セッションの切り出し要約が前の日の作業を当日分として書いたもの。
  切り出しには「前日までの経緯」として、会話の生ログを最大20,000字渡している（`summarize.sh` の `SLICE_CONTEXT_CHARS`）。
  「要約には含めないこと」という指示だけでは防げていない。11-09 には、区切り内のやりとりが週末明けに返ってきた tool_result だけのセッションが、
  11-06 の作業を当日分として書いた例がある。
- **B. git にしか出てこないマージを生成が落とす。** 重大の大半（#1160・#1202・eb-api-extended #128・#981）がこれ。
  ブラウザでマージした PR は、ペイロードの git 節に `Merge pull request #N` の1行があるだけになる。
- **C. Rocket Chat が削られる。** 8日中6日でルームが省かれ、案件の本丸の「シフトオン（AI_eBASE）」は6日とも落ちた。
  原因は、RC の予算が 15,000「バイト」（日本語で約5千字）のままなこと（`rocketchat.sh` の `--budget` はバイトで比べる）。
  セッション要約には日報に使わない節（実行した主なコマンド・ナレッジ候補・フィードバック/承認）が約4割ある
  （全切り出し242本の実測: 作業内容 33.0%・コマンド 17.3%・編集ファイル 14.7%・ナレッジ 13.2%・フィードバック 8.9%・結論 7.3%・意図 5.6%）。
- **D. git の収集範囲に穴がある。** 次が収集されていない。
  - `~/worktrees/*/`（例: hankyu の kensho90 系ブランチ、10-27・10-28 に計21コミット）
  - `~/src/192.168.208.80/gitbucket/<グループ>/<リポジトリ>/`（例: release-skills-repo）
  - `/mnt/d/git/*/`（例: pilot_webcatalog）
  また、別ディレクトリに clone したリポジトリ（`~/src/github.com/ebase-dev/eae-docs-idcf-getagentinfo` は eb-api-extended の独立した clone）が、
  ディレクトリ名のまま別リポジトリとして出る。今の `canonical_repo_name` は worktree の共通 `.git` しか見ないため。
- **E. 生成が状態を格上げ・取り違える。** 「発注予定」を「発注した」、「報告文を作成」を「報告した」と書く。
  ローマ字の ID `tamaki.s` に漢字「玉置」を当てた（正しくは玉木）。同じペイロードの中で後から訂正された古い記述を採った。
- **F. 自己チェック（`check-daily-report.sh`）の精度が足りない。** LLM の照合が、重大1件・重複2件を見逃した。

## ゴール

- 区切り外の作業が日報に入らない（区切り外の根拠不明と、それによる重複を0に近づける）。
- 区切り内に自分がマージした PR は、すべて日報に載る。載っていなければ自己チェックが決定的に気づく。
- Rocket Chat のルームが、予算不足で省かれない（普段の日）。
- 自分のコミットが、置き場所（worktree・GitBucket clone・D ドライブ）に関係なく git 節に入り、本体のリポジトリ名でまとまる。

## 非ゴール

- Web UI だけで行った操作（PR の Approve やコメント）を拾うこと。jsonl にも git にも痕跡が無く、API の収集が必要になるため今回は見送る。
- 生成がペイロードの外を読んだ可能性（「オッティ H91W」の1件）の調査。原因不明の1件だけなので様子を見る。
- 既存の `sessions/` の要約、それを使う他のスキル（後続案件としてメモ済み）。
- 5時間上限への対策（保留案件としてメモ済み）。

## アンチゴール

- 文脈を減らした結果、多日セッションの切り出し要約が「何の続きか」わからない要約になる。
- マージ一覧のせいで、他人の PR のマージ（レビュー作業としてマージボタンを押しただけのもの）を自分の実装として書く。
- 収集範囲を広げた結果、同じコミットが二重に数えられる、または他人のコミットが混ざる。
- どの変更も、22:10 の送信を止める経路を作ってはならない（前回の設計と同じ）。

## 制約

- 前回の設計の制約はすべて引き継ぐ（区切り 22:10、切り出し要約の置き場所、送信を止めない、redaction、テストは自前の bash テスト、など）。
- `/fire` の text 上限は 65,536字。全体の予算は 60,000字のまま。
- ルーティンのプロンプト変更は外部の設定変更なので、差分を見せて承認を得てから `RemoteTrigger update` する。
- サブスクの5時間上限があるので、検証で切り出しを大量に作り直すときは時間帯に気をつける。

## 決まっていること（こちらの判断。ユーザーは範囲 A〜F を承認済み）

### A. 区切り前の混入

1. 切り出しに渡す文脈を、生ログから「同じセッションの前日の切り出し要約の『意図』と『結論』」に替える。前日の切り出しが無ければ文脈なし。
   生の会話を渡さないので、書き写せる細部（コミットやテストの具体）が文脈に入らない。
2. 区切り内に、ユーザーの文字の発言（tool_result ではない user の text）が1件も無いセッションは切り出さない（決定的に判定）。
   承認待ちのツール結果が返っただけ、のような区切りを作業日と数えないため。
3. 切り出しのプロンプトに、「文脈に書かれた作業（コミット・PR・修正・配置）は、範囲内で改めて行われていない限り書かない」を明記する。

### B. git にしか出てこないマージ

4. fire が、区切り内の git ログから `Merge pull request #N from <owner>/<branch>` の行を決定的に抜き出し、ペイロードに
   【区切り内にマージされたPR】節として「リポジトリ・PR 番号・ブランチ・時刻」の一覧を載せる。
5. ルーティンには、「この節の PR は、自分の作業ならすべて項目に含める。他人の PR をレビューしてマージしたものはレビュー作業に置く」と指示する。
   自分の PR かどうかの最終判断は、今の生成ルール（他者の PR かどうか）に従う。
6. 自己チェックは、この一覧の PR 番号が日報の「📝 サマリー」節に出てくるかを、スクリプトで決定的に確かめる。
   出てこない PR があれば `missing` に重大として足し、通知の対象にする。

### C. Rocket Chat の予算

7. ペイロードに入れるセッション要約からは「実行した主なコマンド」「ナレッジ候補」「フィードバック/承認」の3節を外す。切り出し md 自体は全部残す。
8. RC の予算を字数で数え、既定を 15,000字にする（今は 15,000バイト）。全体の予算 60,000字は変えない。
   空きはセッション要約の削減分で賄う。全体が超えたときの削り方（古いセッションから落とす）は今のまま。

### D. git の収集範囲

9. 収集先に `~/worktrees/*/`、`~/src/192.168.208.80/gitbucket/*/*/`、`/mnt/d/git/*/` を足す。
10. リポジトリの正規名は、`origin` の URL の末尾（`.git` を除く）を最優先にする。取れなければ今の方法（共通 `.git` の親ディレクトリ名）。
    同じコミットの二重計上は、今の SHA による重複除去で防ぐ。
11. Work / Personal のラベルは、`origin` が `github.com/aya-215/` なら Personal、それ以外は Work とする。ラベルは今と同じく参考情報。

### E. 状態の格上げ・取り違え

12. ルーティンの生成ルールに3行足す。
    - 予定・依頼・準備の段階のものを、完了したように書かない（「発注予定」を「発注した」と書かない）。
    - 人をローマ字の ID でしか知らないときは、漢字を推測して当てない。ID のまま書くか、入力に出てくる漢字表記だけを使う。
    - 同じ入力の中で、後の記述が前の記述を訂正している場合は、後の記述に従う。

### F. 自己チェック

13. 6 の決定的な照合を `check-daily-report.sh` に足す。LLM の照合は今のまま叩き台として残す。

### ビルダー確認で決めた細部（こちらの判断）

14. 前日の切り出しの探し方: 同じ sid8（ファイル名の末尾）の切り出し md を、対象日より前の日付フォルダから新しい順に探し、最初に見つかったものを使う
    （直前の日に限らない。週末をまたいだ再開でも文脈が付く）。14日より前はさかのぼらない。
15. 2 で切り出さなかったセッションは「失敗」ではないので `.failed` に載せず、全期間の要約による補完もしない（補完すると区切り外が再び混ざるため）。
16. 自己チェックは、保存済みの payload.txt の【区切り内にマージされたPR】節を機械的に読む（git を再実行しない。区切りや収集先の判定を二重に持たないため）。
17. 照合のキーは PR 番号（`#N` の前後が数字でないこと）だけにする。リポジトリをまたいだ番号の衝突は、見逃しの方向にしか働かず、頻度も低いので受け入れる。
18. 他人の PR をレビューしてマージしたものも、レビュー作業の項目に PR 番号を書かせる（今の生成ルールも「PR番号は省略しない」）。
    これで「一覧の PR 番号は全部日報に出る」が成り立ち、誤通知が出ない。
19. マージの抽出は `Merge pull request #N from <owner>/<branch>` 行だけにする。既知の重大4件（#1160・#1202・eb-api-extended #128・#981）は、すべてこの形式だった（2026-11-11 に git で確認）。
    squash・rebase マージは対象外（今の運用では見当たらない）。
20. RC の予算は、`rocketchat.sh` に字数で比べる新しいオプション（例 `--budget-chars`）を足して fire だけがそれを使う。
    `--budget`（バイト）は work-report・my-tasks・verify-daily-report が使っているので、意味を変えない。
21. `origin` が無いリポジトリのラベルは Work に倒す（ローカルだけのリポジトリは業務の作業用が多いため）。ラベルは参考情報なので、誤っても影響は小さい。
22. 検証の dry-run は、切り出しの置き場所を本番と分ける（`SLICES_ROOT` を別ディレクトリに向ける）。今の17日分の切り出しと payload.txt を上書きしない。
23. ルーティンのプロンプトはリポジトリに置いていない（ルーティン本体が正本）。実装の終盤で `RemoteTrigger get` で取り、差分をユーザーに見せて承認を得てから更新する。

## 確かめ方

1. 前回と同じ17日について、jsonl と退避先が残っているうちに `--dry-run` でペイロードを作り直し、次を数字で確かめる。
   - 区切り外の既知の5件（10-21 試行1・10-29 #304・10-29 #1164 実装・11-09 ピン留め・11-09 `_archive`）が、その日の切り出し要約に出てこないこと。
   - 【区切り内にマージされたPR】節に、既知の重大（11-04 #1160・11-06 #1202・11-06 eb-api-extended #128・10-16 #981）が載ること。
   - RC の節に「容量制限のため … ルームを省略」が出ないこと（17日中、何日に出るか）。
   - git 節に hankyu の kensho90 系・pilot_webcatalog のコミットが入り、eae-docs-idcf-getagentinfo が eb-api-extended にまとまること。
2. 数日分を `--overwrite` で実際に作り直し、verify-daily-report（一次情報＋RC）で照合する。日はユーザーと決める。

## 作る人に任せること

- 前日の切り出し要約から「意図」「結論」を取り出す方法と、前日が無いときの扱いの細部。
- 「ユーザーの文字の発言」の判定方法（extract.py で user の text 行を数える、など）。
- マージ一覧の抽出元（`git log` を再度呼ぶか、git 節の生データから取るか）と書式。
- 3節を外す処理の場所（`build_sessions` の中が自然）。
- RC の予算を字数にする方法（`rocketchat.sh` 側を直すか、呼び出し側で換算するか）。
- 新しい収集先の glob の深さと、存在しないパスの扱い。
