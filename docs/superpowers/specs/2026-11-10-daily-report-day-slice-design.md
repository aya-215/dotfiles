# 日報の入力を「日次の切り出し要約」に変える設計

## 背景と理由

2026-11-10 に直近1ヶ月の日報を一次情報と照合した。日報の誤りの大部分は、生成側（クラウドルーティン）ではなく、
入力に使うセッション要約の**作られるタイミング**と**日付への振り分け方**から来ていた。

現行の仕組み:

- セッション要約は SessionEnd hook（exit・/clear 時）でしか作られない。
  21:00 の `backfill.sh` が拾うのは、要約が1本も無いセッションだけ。
- 要約は**セッションの最初から最後まで**を対象にし、**最後の発言の日**のフォルダ
  （`~/.nb/claude/sessions/YYYY-MM-DD/`）に入る。再要約されると、古いほうは消える。
- 22:10 の `fire-daily-review.sh` は、その日のフォルダだけを読む。

実測（10/12〜11/9）:

- 要約173本のうち **24本（14%）は締め（その日の 22:10）より後に書かれた**。すでに生成済みの日のフォルダに入るため、
  最終版は二度と日報に載らない。
  - 例1: 10-30 の #1080 昇格完了。最後の発言は 10-30 12:11、要約は 11-04 14:30。
    10-30 の日報は「昇格する想定」のままになり、昇格完了はどの日報にも載っていない。
  - 例2: 11-05 の PR #1202。最後の発言は 11-05 13:54、要約は 11-06 15:21。どの日報にも載っていない。
  - 例3: 11-05 の decrypt 確認。17:12 の古い版が締めに使われ、日報は「未取得」のまま。
- 8月以降の要約579本のうち **126本（22%）は日をまたいでいる**。全期間を要約するため、
  後の日に同じ成果がもう一度載る（例: REQ-2026-10-20-001 が 10/21・10/22・10/23 の3日に載った）。
- 根拠不明として出た項目は、サンプルを調べた範囲では全部 Rocket Chat で裏付けが取れた。
  日報の問題ではなく、検証スキル（verify-daily-report）が RC を見ていないのが原因。

## ゴール

- その日にやった作業が、**その日の日報に1回だけ**載る。
- 締めの時点で開きっぱなしのセッションも、締めの時点の状態で載る。
- 過去日を `--date` で再生成したとき、jsonl が残っている限り、同じ範囲の材料で作り直せる。
- 取りこぼしを1ヶ月後ではなく、翌朝に気づける。

## 非ゴール

- 既存のセッション要約（`~/.nb/claude/sessions/`）の作り方・置き場所・中身は変えない。
  振り返り（retrospective）・週報（work-report）・工数見積（effort-estimate）・find-session などが依存しているため。
- 日報生成本体をクラウドルーティンからローカルへ戻すことはしない。
- 日報の書式（【サマリー形式】【生成ルール】）は、分類例の追加を除いて変えない。

## アンチゴール（技術的に動いても失敗とみなすもの）

- 切り出し要約の生成が失敗・遅延したせいで、その日の日報が丸ごと送られない。
  失敗時は既存の `sessions/` の要約で送る（今と同じ品質に落ちるだけにする）。
- 同じ作業が複数日に載る状態が残る。
- DM・シークレットが切り出し要約やペイロードに入る（redaction は今と同じく通す）。

## 制約

- jsonl は約30日しか残らない（2026-11-10 時点で最古は 10-13）。それより古い日は新方式で再生成できない。
  その場合は既存の `sessions/` の要約にフォールバックする。
- jsonl の `user` / `assistant` の行には `timestamp`（UTC）が付いている。
- ローカルの `claude -p` はサブスク枠を使う。ユーザーいわく枠は毎回余っているので、回数やモデルは気にしなくてよい。
- cron の環境は LANG 未設定。`${#var}` は文字数ではなくバイト数を数える。
- `rocketchat.sh` は日付単位（`--from` / `--to`、JST の 0:00 区切り）でしか範囲を取れない。

## 決まっていること

### ユーザーが決めたこと

- 深夜（22:10 より後）の作業の扱いはユーザーが任せた。そのうえで、ユーザー自身は「翌日の日報が自然」という意見。
  → 区切りは下記のとおり「翌日に回す」にした（判断はこちら、理由は下記）。
- ローカルのサブスク枠は好きなだけ使ってよい。
- **過去の日報（10-13〜11-09）は新方式で実際に書き直して比べる。** 比べた結果をもとにさらに調整する。
  そのため、再生成のときは既存のサマリーを引き継がずに作り直す「上書きモード」が要る
  （今のルーティンは「既存サマリーの内容を失わない」ため、再発火しても古い誤りや重複が残る）。
  上書きモードは再生成（`--date`）のときだけ使う。毎晩の定時実行は今と同じく引き継ぐ。
  書き直す前の日報は、比べられるように退避しておく。
- **jsonl の保存期間は 180 日にする**（`cleanupPeriodDays: 180`、2026-11-10 に適用済み）。
  四半期報告の振り返りに余裕を持って足り、容量は約5GB の見込み。足りなければ後で延ばす。

### こちらで決めたこと（ユーザーは確認できる）

1. **区切りは「前日 22:10 〜 当日 22:10」（JST）に固定する。**
   実際に送信した時刻ではなく、予定の時刻で決める。こうすると深夜の作業は翌日の日報に1回だけ入り、
   `--date` で再生成しても範囲が変わらない。git 活動も同じ区切りにそろえる。
   RC はツールが日付単位なので暦日のままでもよい（作る人の判断）。
2. **日報専用の「日次の切り出し要約」を、既存の要約とは別の場所に作る。**
   その日の区切りの中に発言があるセッションを全部対象にする（開きっぱなしのものも含む）。
   jsonl から区切りの中のやりとりだけを取り出して要約する。
3. **文脈として、同じセッションの前日までの状況を短く添える。** 切り出しだけでは「何の続きか」がわからないため。
   ただし要約の本文は、当日の区切りの中でやったことだけにする。
4. **切り出し要約のモデルは Sonnet にする。** 枠に余裕があり、1本あたりの量も減るため。
   長尺は今の `summarize.sh` と同じく 1M コンテキストのモデルに回す。
5. **送信の直前に作る。** 22:10 の `fire-daily-review.sh` の中で、収集の前に生成する
   （別の cron に分けて時刻の前後関係に頼る形にはしない）。
6. **生成に失敗したセッションは、既存の `sessions/` の要約で代わりに埋める。** 全部失敗しても送信は止めない。
7. **毎晩の自己チェックを足す。** 日報が Issue に書き込まれたあと、ローカルで照合する。
   材料は切り出し要約・RC・git・生成された日報。取りこぼし・根拠不明・誤分類・書式を見る。
   結果はログに残し、問題があったときだけ Windows の通知を出す。
8. **`--date` での再生成も新方式で行う。** 区切りは 1 と同じ。jsonl が無い日はフォールバックする。
9. **小物も一緒に直す。**
   - verify-daily-report スキルの照合に RC を加える（`rocketchat.sh` で当日分を取る）。
   - ルーティンの生成ルールに、雑務寄りの作業の分類例を足す（社内リポジトリの worktree・ブランチ掃除、
     業務資料探しは Work）。
   - ルーティンのプロンプトに、【セッション要約】は「その日の区切りの中のやりとりだけ」だと明記する。
     ルーティンのプロンプト変更は外部の設定変更なので、差分を見せて承認を得てから `RemoteTrigger update` する。

10. **照合の基準も新方式に切り替える。** verify-daily-report と毎晩の自己チェックは、切り出し要約と 22:10 の区切りで照合する。
    切り出し要約が無い日（jsonl が消えた日・新方式の導入前）は、今の方式（`sessions/<暦日>/`、end の日で振り分け）で照合する。
    スキルはこの2つの方式の両方に対応させる。
11. **通知を出すのは「重大な取りこぼし」か「RC でも裏付けが取れない根拠不明」があったときだけにする。**
    軽微な取りこぼし・書式の揺れ・確信度が低いものはログに残すだけにする。毎晩通知が鳴ると無視されるようになるため。
12. **クラウド側で暦日のまま動く部分は今回そろえない。** ルーティンはコミット件数をペイロードの【git活動】から数えている（手順3）。
    そのため git をローカルで区切れば、件数も区切りにそろう。task Issue（手順4、close された日）とメール（暦日単位で保存）は暦日のままにする。
    どちらも1日に1回しか載らないので、重複や取りこぼしにはならない。
13. **検証に使う jsonl は退避済み。** 2026-10-12 以降に更新された jsonl 213本（665MB）を
    `~/.local/share/daily-slice-replay/jsonl-backup/`（元のパス構造のまま）にコピーした。
    保存期間を延ばす前に古いものが消える恐れがあったため。再生成の検証ではこちらも探索対象にする。

## 作る人に任せること

- 切り出し要約の置き場所・ファイル名・frontmatter（例: `~/.nb/claude/daily-slices/YYYY-MM-DD/<project>-<sid8>.md`）。
- 「区切りの中に発言がある jsonl」の見つけ方（mtime での絞り込み＋行ごとの timestamp 判定など）。
  サブエージェントの jsonl（`*/subagents/*`）と `claude -p` の非対話セッション（entrypoint が sdk-cli / sdk-py）は、
  今の backfill と同じく除外する。
- 要約プロンプトの細部。今の7項目の形式を流用するかは任せる。ただし【レビュー作業】【実装作業】の明記は残す
  （ルーティンの分類の一次情報になっているため）。
- 前日までの文脈の作り方（前日の切り出し要約の「結論」を使う、`sessions/` の要約を使う等）と長さ。
- 並列度とタイムアウト。作業した日は 5〜20 セッション程度ある。送信が遅れすぎないようにすること。
- 自己チェックの実行タイミング（ルーティンの完了を待つ方法）と、使うモデル。
- ペイロード予算の単位をそろえる方法（LANG を固定して文字数で数える等）。
- RC の区切りを 22:10 にそろえるかどうか。

## 確かめ方

jsonl が残っている 10-13〜11-09 を使い、`--date` に `--dry-run` を付けてペイロードを作り直す。
今の入力と比べて、次のことを数字で確かめる。

- 例1〜3（10-30 #1080、11-05 PR #1202、11-05 decrypt）が、**正しい日のペイロードに最終状態で入っている**こと。
- 日をまたぐセッションの成果が、**やりとりがあった日のペイロードにだけ入っている**こと
  （例: REQ-2026-10-20-001 が3日分に出ないこと）。
- 開きっぱなしのセッションが、締めの時点の状態で入っていること。

余裕があれば、数日分を実際に発火して、生成された日報を verify-daily-report（RC 照合あり）で照合する。
基準は 2026-11-10 の実測値（12日で取りこぼし2件・誤分類2件）。

## 後続（今回の範囲外）

既存の `sessions/` を使うスキル群（work-report・effort-estimate・retrospective など）も、同じ欠陥を抱えている可能性がある。
日報の改善が終わったら検討する（agent-memory: `work-in-progress/session-summary-consumers-improvement.md`）。
