## 新方式で悪くなった点・残った問題

1. **区切り前の文脈が当日の成果として書かれることがある。** 10-29 の切り出し（セッション 4cf5a885。jsonl は 10-26〜10-30 にまたがる）が、
   同じセッションの区切り前のやりとり（10-28 09時台 UTC = 18時台 JST。#304 の言及 16 件。区切りの開始は 10-28 22:10）で済んだ
   「MCP #304 の指摘修正・マージ」を 10-29 の作業として要約し、日報にも 10-29 のマージとして載った。
   切り出しは区切り前のやりとりも文脈として読ませているため、その中の完了した作業が当日分に漏れたとみられる。
   自己チェックはペイロードとしか照合しないので、この種の誤りは検出できない
2. **切り出しが全滅しても送信してしまう。** 11-05 の1回目は `written=0 failed=9` のまま、`sessions/` の全期間要約（旧方式の材料）で送った。
   今回はルーティン側も上限で止まったので Issue は無事だったが、ルーティンだけ動いていれば旧方式の内容で上書きされていた
3. **ペイロードが予算に近い日がある。** 10-13 は 58,662 字で、古い 1 セッションと RC 3 ルームが容量制限で省略された（11-04 も 54,271 字）。
   切り出しは旧の全期間要約より短いが、その日に触ったセッション数が多いと本数が増える（10-13 は 22 本）。省略されたセッションは自己チェックでも見えない
4. **軽微な取りこぼしが出ている。** 8 件（基準 12 日）。マージや PR 作成のような区切りの小さい作業が多い（例: 10-16 PR #981 のマージ、10-21 PR #121 の作成、11-06 PR #1202・#128 のマージ）。
   旧の実測でこの粒度を数えていたかは不明なので、悪化かどうかは確定できない
5. **書式ドリフトが 2 日。** 10-20（Personal 項目に件数を付けた・括弧の全角半角）と 11-06（見出しの件数と本文の不一致・件数表記の揺れ）。旧の基準 12 日は 0 日
6. **項目数が 17 日で 216 → 236 に増えた。** 区切り内の作業を細かく拾うようになった結果とみられるが、読む量は増える
7. **時間とコスト。** 1 日の発火に切り出しが 1〜5 分かかる（`claude -p` を候補セッション数ぶん呼ぶ）。dry-run も切り出しをやり直すため、確認と発火で 2 回分かかる

## 調整案

- 切り出しが全滅（`written=0` かつ `failed>0`）した日は、`--overwrite` のときは送らずに止める。毎晩の定時実行でも、全期間要約で送ったことをログと自己チェックに残す
- 切り出しで区切り前のやりとりを渡すときは、区切りの境目を明示した印を入れ、印より前は「前提」としてしか書かせない（完了した作業・マージを当日分に書かない）。
  区切り前の文脈の量を減らす（要約済みの短い前提に置き換える）ことも検討する。#304（セッション 4cf5a885 の 10-29）を回帰ケースにする
- 自己チェックに「git 活動のマージ日時と、サマリーに書かれたマージの日が合っているか」を足す。#304 の誤りは git ログの日時で機械的に判定できる
- ペイロードの容量: セッション数が多い日は、切り出し要約の「実行した主なコマンド」「編集/作成ファイル」節を落としてから古いセッションを省略する
