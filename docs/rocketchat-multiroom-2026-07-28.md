# Rocket Chat 情報取得の複数ルーム対応（2026-07-28 実装）

日報（cron）と `work-report` が Rocket Chat の1チャンネルしか見ていなかった問題を解消し、購読ルーム全体から自分に関係する情報を収集できるようにした記録。

- 設計書: `docs/superpowers/specs/2026-07-28-rocketchat-multiroom-design.md`
- 実装計画: `docs/superpowers/plans/2026-07-28-rocketchat-multiroom.md`
- コミット範囲: `7b385b0..54a7199`（21コミット）

---

## 何が問題だったか

日報と work-report はどちらも `mori.a-times`（自分の times）1チャンネルだけを見ていた。そのため**他のチャンネルに来た自分宛の依頼が構造的に拾えなかった**。

実際に取り逃していた例:

| 取り逃していた情報 | 場所 |
|---|---|
| 週報の提出依頼（`@mori.a` 付き） | `websol-dev-ai-hub` |
| ちらしJSON項目のフィードバック依頼「処理上の不都合があれば項目名の見直しを検討します」 | `e食なび` |
| 「今週中に対応します」という自分の約束 | DM |

さらに同じ「1チャンネルだけ見る」ロジックが**2つの異なる実装で二重化**していた。

| | 日報（cron） | work-report（対話） |
|---|---|---|
| 取得方法 | REST API 直叩き（`fetch-rocketchat.sh`） | MCP ツール |
| 対象指定 | `RC_CHANNEL` 環境変数1個 | SKILL.md に固定記述 |

---

## どう直したか

`scripts/lib/rocketchat.sh`（419行）を新設し、日報 cron と work-report の両方がこれを呼ぶ形にした。**`fetch-rocketchat.sh` は削除して二重実装を解消した。**

```
              scripts/lib/rocketchat.sh  ← 決定的な処理を集約
              ┌──────────────────────────────┐
              │ rc_api            API ラッパー │
              │ list_active_rooms ルーム列挙   │
              │ room_history      履歴取得     │
              │ expand_threads    スレッド展開 │
              │ render_room       絞り込み+整形│
              │ collect_blocks    予算処理     │
              └──────────────────────────────┘
                   ↑                    ↑
   fire-daily-review.sh          work-report/SKILL.md
   （cron 22:10・Claude不在）      （対話・Bash経由）
   --budget 15000                 --include-dm
```

ルーム列挙・絞り込み・スレッド展開という**機械的に決まる処理**をシェル層に置き、作業内容の分類という**非決定的な判断**だけを Claude 側に残した（`learned-rules.md` の「決定的な処理と非決定的な処理を分離する」に沿う）。

### 使い方

```bash
# work-report（対話・DM込み）
bash ~/.dotfiles/scripts/lib/rocketchat.sh --from 2026-07-21 --to 2026-07-28 --include-dm

# 日報 cron（DM除く・予算あり）
bash ~/.dotfiles/scripts/lib/rocketchat.sh --from "$d" --to "$d" --budget 15000

# デバッグ用
bash ~/.dotfiles/scripts/lib/rocketchat.sh --from ... --to ... --list-rooms    # 採用ルーム一覧
bash ~/.dotfiles/scripts/lib/rocketchat.sh --from ... --to ... --print-window  # 日付範囲の計算結果
```

出力形式:

```
===== e食なび [発言7,@me4] 19/22件 =====
  07:53 m.shitagawa: @mori.a 明日11:00〜12:00でAIちらし検索の打ち合わせお願いします
  10:18 h.masuda: 処理上の不都合があるようでしたら項目名の見直しを検討します
  ...
```

`[発言N,@meN]` が採用理由、`M/N件` が「絞り込み後 / 全件」を表す。

## 設計の要点

### 1. REST API 直叩きを選んだ理由

MCP ツールと REST API で能力差があった。**これが設計の起点**。

| 能力 | MCP ツール | REST 直叩き |
|---|---|---|
| 購読ルームのみ列挙 | ❌ 未参加のパブリックchも混ざる（`list_channels` が254件返すうちパブリック166件だが、実際の購読は17件だけ） | ✅ `rooms.get` が購読105件のみ返す（DM 47 / プライベート 41 / パブリック 17） |
| 最終メッセージ日時 | ❌ 返らない | ✅ `lm` フィールドで取得可 |
| 期間での事前絞り込み | ❌ 不可能 | ✅ `lm` で 105件→38件に**1コール**で絞れる |

MCP 前提だと「全チャンネル総当たり（約140コール）」が必要だったが、`lm` があるので不要になった。

### 2. ルーム採用の判定（第1段階）

以下のいずれかを満たすルームだけ採用する。

1. 自分の発言が期間内にある
2. `@mori.a` を含むメッセージが期間内にある

`grafana-alert`（45,553文字）や `reviewboard`（47,641文字）のような自動投稿チャンネルは、どちらも満たさないので**自然に落ちる**。除外リストの保守は不要。

**`@all`/`@here` は条件に含めない。** 当初は「`@all` の週報依頼を取り逃していた」ことを根拠に入れていたが、実データを検証すると `@all` で拾えるのは新人紹介や他人のQ&Aといったノイズだけで、根拠にしていた週報依頼は `@mori.a` 付きでも届いていた。

### 3. メッセージの絞り込み（第2段階）

ルームの性質で2通りに分ける。

| 対象 | 方式 | 理由 |
|---|---|---|
| 自分の times・DM | **全メッセージ採用** | 自分の作業ログそのもの。DM は1対1なので無関係な発言が構造的に存在しない |
| 他人の times・チャンネル | 起点＋スレッド＋**前後30分** | 自分が数件しか絡んでいないルームで全履歴を取ると大半が無関係な雑談になる |

この2段構えは**設計中に2回作り直した結果**で、どちらもユーザーの指摘が起点だった。

**① スレッド展開だけでは文脈が落ちる**

`kawai.t-times` はスレッドを使わずフラットに会話しており、起点だけ拾うと自分の発言が宙に浮く。

| 時刻 | 発言 | 起点のみ | ±30分 |
|---|---|---|---|
| 07:21 | kawai.t「MCP化でよかったのかいまいちわからん」（質問） | ❌ | ✅ |
| **07:37** | **mori.a「自分で作る分には全てskillでいい」** | ✅ | ✅ |
| 07:40 | kawai.t「確かに認証の有無が一番大きい違い」（反応） | ❌ | ✅ |

何に答えたのか判別できず日報の材料にならない。→ **時間窓±30分を追加**

**② 時間窓は「尻尾」を切る**

時間窓は起点からの対称距離で切るため、自分が話題を投げて相手が後から議論を続けた場合に末尾が落ちる。

7/27 の OpenAI 残高切れインシデント:

| 時刻 | 発言 | ±30分のみ |
|---|---|---|
| 00:45 | mori.a「ログです」 | ✅ 起点（最終発言） |
| **01:47** | matsumoto.h「向こうの対応が変わったってこと？」 | ❌ 落ちる |
| **01:56** | tanaka.k「はい、自分も同じ認識です」 | ❌ 落ちる |

**原因究明の結論部分**が欠落する。→ **自分の times・DM は全採用に変更**

補足として、`RC_CHANNEL`（自分の times 名）が未設定・不一致だとこの全採用が無言で発火せず時間窓に落ちるため、stderr 警告を出すようにした。実測で `7/7件` → `4/7件` の差が出る。

### 4. スレッド展開

**history 系エンドポイントはスレッド返信を全件返さない。** 実測で9返信のスレッドのうち3件しか返らなかった。

欠落していた内容には、以前「依頼したが未応答」と誤って報告した資料受領（「そちらです！非常に助かります」）が含まれていた。history だけを見ていたせいで見えていなかった。

`chat.getThreadMessages` で補完する。対象期間のスレッドIDは2箇所から集める必要がある。

- 返信側の `tmid`（親の `_id` を指す）
- 親側の `tcount`（返信数を持つ）

実測で `tmid` 由来3件 + `tcount` 由来1件 = 4スレッドだった。

**期間外フィルタが必須。** `chat.getThreadMessages` は `oldest`/`latest` を無視する（指定すると0件、省略すると全件返る）。API 側で絞れないので取得後に `ts` でフィルタする。あるスレッドは全31件のうち**24件が期間外**だったため、これを省くと生きているスレッドの全履歴が毎日の日報に混入する。

### 5. 予算処理

旧実装は文字数超過時にバイト位置で切り捨てていた。

```bash
rocketchat_log="${rocketchat_log:0:$MAX_RC_CHARS}"   # ← 無言でカット
```

1チャンネルなら実害は小さいが、複数ルームでは**連結の後ろに来たルームが丸ごと消え、しかも気づけない**。

優先度つきのルーム単位ドロップに変更した。

1. 自分の発言があるルーム
2. `@mori.a` のみのルーム
3. それ以外 → 予算超過時はここから落とす

落としたら `（※ 容量制限のため N ルームを省略: room-a, room-b）` を出力に含める。実測例:

```
予算なし        : 5,781バイト / 5ルーム
--budget 5000  : 4,720バイト / 3ルーム
省略マーカー    : （※ 容量制限のため 2 ルームを省略: 奈良高専,websol-dev-ai-hub）
```

残ったのは全て「発言あり」（優先度1）で、落ちたのは `@me` のみのルームだった。

## 実装中に見つけた本番バグ（修正済み）

### JST→UTC 変換の8時間ズレ

既存の `fetch-rocketchat.sh` と新規実装の両方にあった。**日報が毎晩「当日 09:00〜翌 08:00 JST」を取得していた**（範囲が23時間）。

原因は2つの独立した誤用の複合。

```bash
# 誤り
oldest=$(TZ=Asia/Tokyo date -d "$d 00:00" -u +%Y-%m-%dT%H:%M:%S.000Z)
latest=$(TZ=Asia/Tokyo date -d "$d 00:00 +1 day" -u +%Y-%m-%dT%H:%M:%S.000Z)
```

1. `TZ=Asia/Tokyo date -d "..." -u` — `-u` が**入力解釈のタイムゾーンも上書きする**（POSIX 仕様）ため、JST のつもりが UTC として解釈される
2. `"00:00 +1 day"` — GNU date が `+1` を**数値 UTC オフセット**と解釈し `day` を無視する

コード自身のコメントが「JST 00:00〜翌 00:00」と宣言していたため、意図と実装の不一致としてバグと断定した。

```bash
# 正しい書き方（オフセットを入力文字列に内包する）
oldest="$(date -u -d "${from}T00:00:00+09:00" +%Y-%m-%dT%H:%M:%S.000Z)"
latest="$(date -u -d "${to}T00:00:00+09:00 +1 day" +%Y-%m-%dT%H:%M:%S.000Z)"
```

**実害は測定時点でゼロだった。** 対象月の自分の投稿72件がすべて 9〜18時台で、9時前の投稿が0件だったため。ただし境界値検証で JST 00:00〜08:59 の発言がすべて欠落することを確認しており、深夜作業や早朝の投稿があれば取り逃していた。

なお `TZ=Asia/Tokyo date -d "... + 1 day"`（スペース入り）でも `latest` は壊れたままだったので、スペースを入れる回避策は使えない。

### `${#var}` はロケール依存でバイト数を数える

cron 環境（`LANG` 未設定）では `${#var}` が文字数ではなく**バイト数**を返す。

```
LANG=ja_JP.UTF-8 → ${#v} = 14   （文字数）
LANG 未設定(cron) → ${#v} = 42   （バイト数）
wc -c            → 42           （どちらでも同じ）
```

日本語は1文字約3バイトなので、文字数で見積もると実使用率を**約3倍過小評価**する。設計時に「日次最大4,303文字＝予算の29%」と書いていたが、実効値は **9,608バイト＝64%** だった。

このため `rocketchat.sh` の予算比較は `printf '%s' "$candidate" | wc -c` で明示的にバイト数を測る（`${#var}` は使わない）。

## テスト

`scripts/lib/rocketchat-test.sh` に67件。実 API は叩かず、`RC_CURL` 環境変数で curl をスタブに差し替えて fixture JSON を返させる。

**「テストが通る」と「テストが機能する」は別**という前提で、各機能に変異テスト（該当コードを壊してテストが落ちるか確認）を実施した。これで空証明を5件見つけた。

| 見つけた空証明 | 内容 |
|---|---|
| DM名の検証 | `_id` 列にマッチしていただけで name 列を検証しておらず、自分を除外するロジックを壊しても全テストが通った |
| 不正レスポンスの経路 | `render_room` にも独立した try/except があるため、`room_history` の防御を消しても stdout では同じ結果になり検出できなかった（stderr 捕捉で解決） |
| DM の窓外検証 | fixture の2メッセージが1分差だったため、全採用でなくても時間窓に自然に収まっていた |
| `tmid`/`tcount` の独立性 | 親が `tcount` を持ち返信が `tmid` で同じ親を指すため、片方を無効にしてももう片方が同じIDを導出した |
| 優先度ソート | fixture が末尾にあると入力順のまま末尾に残るだけでソート除去を検出できなかった |

`shellcheck`（`nix run nixpkgs#shellcheck` で実行可能）の指摘はゼロ。

**history が0件のルームでスレッドが取り逃される。**

スレッドIDは対象期間の history 内の `tmid`/`tcount` からしか集めないため、history が0件のルームでは早期 return し、**スレッド内に期間内メッセージがあっても取得されない**。ルーム自体が出力から丸ごと消える。

実測（2026-07-27・`e食なび`）:

| 事象 | 値 |
|---|---|
| 当日の `channels.history` | 0件 |
| 同期間にスレッド内に存在したメッセージ | 6件（2スレッド） |
| 出力に現れた `e食なび` | 0回（消失） |

消えていた内容に「そちらです！非常に助かります」（期間内）が含まれる。**スレッド展開が防ごうとした「依頼したが未応答」の誤判定が再発する経路。**

6日調査（7/21・22・23・24・27・28）では 7/27 のみ該当、計6件だった。

対策案とコスト（7/27単日・候補32ルームで実測）:

| 案 | 内容 | API コール |
|---|---|---|
| A（現状） | history からのみ収集 | 32 |
| B | history 0件のルームに限り過去30日へ範囲を広げる | **37（+16%）** |
| C | 全ルームで過去30日を見る | 倍近く |

案 B が費用対効果に優れる。対応する場合は案 B を起点に、遡及期間を設定可能にすることを推奨。

### その他の記録

- **予算保証の変更**: 予算処理は「最初のブロックは無条件で採用する」ため、単一ルームが `MAX_RC_CHARS` を超えた場合はその保証が働かない。旧実装は文字列切り詰めで常に強制していた。実データでの単一ルーム最大は3,501バイト（予算の23%、OpenAI のスタックトレースを含む日の値）で即座のリスクは低く、`MAX_PAYLOAD_CHARS` の全体バックストップも維持されている
- **cron では警告が無音**: `fire-daily-review.sh` の呼び出しが `2>/dev/null` なので、`RC_CHANNEL` 未設定警告やルーム取得失敗の警告は cron 実行時には見えない
- **`|| true` の変異はテスト不能**: コマンド置換内の失敗は `set -e` が伝播しないため、`|| true` を削除してもテストで検出できない。`room_history` 側も同様で、Task 2 時点から存在する構造的性質
