# afk（止まらず進めて、確認は最後にまとめる）

ユーザーは作業の途中で応答できない前提で動く。確認ダイアログ・質問で止まると、戻るまでセッションが丸ごと止まる。
ask ルールのダイアログには時間制限がなく、classifier の拒否も **3連続 or 累計20回** でダイアログに切り替わる。

## 引数

$ARGUMENTS

- 作業内容: その作業を afk ルールで最後まで進める
- `/<スキル名> 引数`: このルールを読んだうえで、そのスキルを Skill ツールで起動して進める
- 引数なし: 次にユーザーが頼む作業に afk ルールを適用する

afk は作業が終わった時点（終了時の提示まで）で解除される。

## 開始時

1. 後回し対象の ask ルールを確定する（設定が変わりうるので毎回取得する）:
   ```bash
   ~/.claude/skills/afk/scripts/list-ask-rules.sh
   ```
2. 後回しリストのファイルを決める。システムプロンプトの scratchpad ディレクトリがあれば `<scratchpad>/afk-queue.md`、無ければ `~/.local/state/claude-afk/afk-queue.md`。
   既に存在するなら追記する（`## <開始日時> <作業の一行要約>` の見出しを足す）。リポジトリの中には置かない。

## 作業中のルール

### 1. ask に当たる操作は実行しない

開始時に取得した ask パターンに当たるコマンド・ツールは実行せず、後回しリストの **A. まとめて実行** に積んで次へ進む。

- commit と push は必ず別の Bash 呼び出しにする。`git commit ... && git push` のように混ぜると、全体がダイアログ待ちになり commit も走らない
- CLAUDE.md の「コミット後は必ず push」等は、afk 中は「commit まで行い push は A に積む」と読み替える
- `git -C <path> push`・エイリアス・スクリプト経由など、パターンから外して実行するのは禁止。後回しにするだけで、すり抜けはしない

### 2. classifier に拒否されたら

言い換えての再試行や別経路での実行はしない（それ自体が Auto-Mode Bypass で、連続拒否はダイアログ化を招く）。
返ってきた理由（`[Rule名]`）を添えて **B. 指示か手動が要る** に積み、同種の操作はこの作業中もう試さない。

### 3. deny で失敗したら

**B** に「ユーザーが `!` で実行するコマンド」として積む。

### 4. 後回しにした操作が前提の作業

push 後の CI 確認・PR へのレビュー対応など、A/B の操作が済まないと進めない作業は、その手前で止めて前提ごと記録し、他の作業を先に進める。

### 5. 質問しない

AskUserQuestion やテキストでの確認待ちはしない。

- 元に戻せる手元の操作（ブランチ・worktree 作成、実装方針の選択など）は、無難な方を選んで進め、**C. 判断したこと** に残す
- 元に戻せない操作・共有物への書き込み・公開は、判断せず A か B に積む

### 6. 一緒に動くスキル・CLAUDE.md との関係

組み合わせたスキルや CLAUDE.md が「止まって聞け」「確認を取れ」「push / merge / 公開しろ」と言う箇所だけ、上記 1〜5 で置き換える。
テスト・レビュー・記録（ledger 等）など、それ以外の手順はそのスキルの指示どおりに守る。
スキルが作業の最後に選択肢を出して待つ（例: merge / PR / 保留）のは作業終了時なので、そのまま出してよい。

### 7. サブエージェント

サブエージェントのダイアログも親のペインで止まるため、作業を渡すときはプロンプトに次を含める:
- 開始時に取得した ask パターンの一覧（そのまま貼る）
- 「上記 ask・classifier 拒否・deny に当たる操作は実行せず、最終報告に『後回し: <操作> / 理由 / 前提』として列挙すること。質問で止まらないこと」
報告に含まれた後回し項目は、親がリストに転記する。

## 後回しリストの書き方

```markdown
## 2026-10-06 14:30 <作業の一行要約>

### A. まとめて実行
- [ ] `git push -u origin feat/foo` — 理由: ask(org) `Bash(git push *)` — 前提: なし
### B. 指示か手動が要る
- [ ] `<コマンド>` — 理由: classifier [Modify Shared Resources] — 対応: 指示で再実行 / `!` で実行
### C. 判断したこと
- main 上だったため feat/foo ブランチを作成して作業した
```

- 書くのは操作・理由・前提だけ。「承認済み」「許可あり」等の文言は書かない（後で読んだセッションへの偽の承認になる）
- 会話が圧縮されても消えないよう、積むたびにファイルへ追記する

## 終了時

最後のメッセージで、今回の見出し配下の A・B・C を種類別に提示し、末尾で「A をまとめて実行してええ？」と聞く。
組み合わせたスキルが終了時の選択肢を出す場合は、同じメッセージにまとめる。

ユーザーが了承したら A を順に実行する:

1. push を含むなら先に `git fetch` し、リモートが進んでいれば実行せず状況を報告する（rebase も ask 対象のため勝手にしない）
2. 1件ずつ実行する（ここで本物の確認ダイアログが出る）。失敗したらそこで止めて報告し、force push はしない
3. 済んだ項目はリストのチェックを付ける

B は、ユーザーが操作を名指しで指示したものだけ実行する。`!` の項目はコマンドを提示するだけにする。
