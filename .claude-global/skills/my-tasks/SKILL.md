# タスク棚卸し（my-tasks）

一次データ（日報・Rocket Chat・GitHub/GitBucket・gitワークツリー・Claudeセッション要約）を横断して、**今抱えているタスクを取りこぼしなく列挙する**。

**このスキルのゴールは可視化であって、判定ではない。** ユーザーは完了/未完了を自分で分かっている。速くて正確なのはユーザー側の判定であり、こちらの役目は「候補を漏れなく机の上に並べる」こと。

`work-report`（過去に何をやったかの報告）とは問いが直交する。あちらは「やったこと」、こちらは「残っていること」。

## やらないこと

- ファイル保存・git commit・Issue登録（チャット出力のみ）
- 外部アクション（PRコメント投稿・催促メッセージ送信）。**提案までで止まる**
- KPT・工数集計・生産性指標（それぞれ `weekly-report` / `effort-estimate` の役割）
- 個人リポジトリ（`~/.dotfiles`、`aya-215/life` 自体）の作業を業務タスクとして出すこと

## 対象期間

**直近2週間固定。** `start=$(date -d '14 days ago' +%Y-%m-%d)`、`end=today`。

ただし**期間フィルタは「一次データを読む範囲」にのみ適用する。** open な Issue/PR の状態確認は期間外でも行う（後述の「塩漬け」参照）。

## 実行コスト

Step 0〜3 をすべて実行して**8分前後・120k tokens 程度**かかる。短縮モードは設けない。

工程を省いた簡易版を実測したところ、時間は33%減ったが、省いた工程ぶん以上に精度が落ちた（相手待ちタスクの「自分で動ける分」が見えなくなる、薄い項目で件数を埋める、注記付きの項目を「完了っぽい」に置いたまま放置する）。**取りこぼしゼロが目的である以上、この交換は成立しない。**

待ち時間が問題になる場合は、モードを削るのではなくバックグラウンドで実行すること。

## 手順

### Step 0: 前提を整える（必須・スキップ禁止）

この2つを飛ばすと、**エラーが出ないまま間違った結論が出る**。

**0-1. 日報リポジトリを最新化する**

```bash
git -C ~/src/github.com/aya-215/life pull --ff-only
```

ローカルが古いと、blog md が存在しない日について「Issue を見に行く」経路に落ちる。その Issue が既に CLOSED（＝blog md へ移行済み）だと**空のサマリーを読んで「その日は作業なし」と誤読する**。pull すれば blog md が現れて解決する。

**0-2. gh の認証アカウントを使い分ける**

| 対象 | アカウント | 指定方法 |
|---|---|---|
| `aya-215/life`（日報） | aya-215 | `GH_TOKEN=$(gh auth token --user aya-215)` |
| `ebase-dev/*`（業務） | eBASE-Mori | `GH_TOKEN=$(gh auth token --user eBASE-Mori)` |

**取り違えると 0件が静かに返る。** `--author=@me` / `--review-requested=@me` は「今アクティブなアカウント」で解決されるため、業務リポジトリを aya-215 で叩くと常に空になる。0件を見たら**まずアカウントを疑う**こと。

`gh auth status` で現在のアクティブアカウントを確認できる。

### Step 1: 一次データを集める

以下を**並列に**実行する（相互に依存しない）。

**日報サマリー（直近2週間）**

```bash
LIFE=~/src/github.com/aya-215/life
GH_LIFE=$(gh auth token --user aya-215)
d=$(date -d '14 days ago' +%Y-%m-%d)
while [ "$(date -d "$d" +%s)" -le "$(date +%s)" ]; do
  f="$LIFE/blog/$(echo "$d" | tr -d '-').md"
  if [ -f "$f" ]; then
    echo "=== $d ==="; sed -n '/^## 📝 サマリー/,/^## /p' "$f" | sed '$d'
  else
    n=$(GH_TOKEN="$GH_LIFE" gh issue list --repo aya-215/life \
      --search "in:title ${d} の記録" --state all --label memo --json number,title \
      --jq "[.[] | select(.title | startswith(\"${d} \"))][0].number" 2>/dev/null)
    [ -n "$n" ] && { echo "=== $d (issue #$n) ==="; GH_TOKEN="$GH_LIFE" gh issue view "$n" \
      --repo aya-215/life --json body --jq '.body' | sed -n '/^## 📝 サマリー/,/^## /p' | sed '$d'; }
  fi
  d=$(date -d "$d +1 day" +%Y-%m-%d)
done
```

> **日報の「未完了タスク: 他N件」欄は読まない。** 生成元の `nb tasks:todos open` に業務タスクが1件も入っておらず、名指しされる項目も blog に直接埋め込まれた古い固定文字列である。この欄からは業務タスクは拾えない。**タスクは本文サマリーから拾うこと。**

**Rocket Chat（自分の発言と自分宛メンションだけに絞る）**

```bash
bash ~/.dotfiles/scripts/lib/rocketchat.sh --from "$start" --to "$end" --include-dm > /tmp/rc.txt
grep -nE "=====|mori\.a:|@mori\.a" /tmp/rc.txt | grep -vE "mori\.a-times \["
```

生出力は数十KBあり雑談が大半を占める。**絞らずに読むとタスクが埋もれる。** 依頼の受領・約束・催促はほぼこの3種類（自分の発言／自分宛メンション／DM）に出る。

**open な Issue/PR（期間フィルタなしで状態を引く）**

```bash
GH_WORK=$(gh auth token --user eBASE-Mori)
for r in ebase-dev/ebase-portal-chat ebase-dev/ebase-middleware-mcp ebase-dev/eb-api-extended; do
  GH_TOKEN="$GH_WORK" gh issue list --repo "$r" --state open --assignee @me \
    --json number,title,updatedAt --jq '.[] | "\(.number)\t\(.updatedAt[:10])\t\(.title)"'
  GH_TOKEN="$GH_WORK" gh pr list --repo "$r" --state open --author @me \
    --json number,title,updatedAt,reviewDecision \
    --jq '.[] | "PR#\(.number)\t\(.updatedAt[:10])\t\(.reviewDecision // "-")\t\(.title)"'
done
```

GitBucket（社内）は `mcp__gitbucket__gitbucket_list_prs` / `gitbucket_list_issues` を使う。`gh` は通らない。

このリポジトリ群は Issue に assignee をほぼ付けない運用のため `--assignee @me` は0件になりやすい。**0件でも異常ではない**が、その場合は起票者・チャット文脈・git実データから再構成すること。なお `--author @me` も0件なら、そちらはアカウント取り違えを疑う（Step 0-2）。

**チェックリストの展開は open な PR/Issue のみ**を対象にする。マージ済み・クローズ済みは対象外（理由は Step 2 を参照）。

**gitワークツリーの取り残し（コード実体のみ）**

```bash
for r in ~/src/github.com/ebase-dev/*/ /mnt/d/tomcat/webapps/hankyu /mnt/d/tomcat/webapps/eb-api-extended; do
  [ -d "$r/.git" ] || [ -f "$r/.git" ] || continue
  s=$(git -C "$r" status --short 2>/dev/null \
    | grep -vE '(^\?\? |/)docs/|\.md$|^\?\? .*\.(zip|sql|txt)$' | head -20)
  [ -n "$s" ] && { echo "=== $(basename "$r") ==="; echo "$s"; \
    echo "  branch: $(git -C "$r" branch --show-current)"; }
done
```

**`docs/` 配下・`.md`・調査用の一時ファイルは除外する。** このユーザーは docs をコミットしない運用のため、除外しないと計画書が数十件ノイズとして出てタスクが埋もれる。

残るのは**コード実体の未コミット差分**のみ。これは「作業したが着地していない」の強いシグナルで、特に**マージ済みブランチの上に乗った差分**は紛失・混線リスクがあるため必ず出す。

**Claudeセッション要約（gitに残らない調査・調整作業の補完）**

```bash
for dir in ~/.nb/claude/sessions/*/; do
  d=$(basename "$dir")
  [ "$d" \< "$start" ] && continue
  for sf in "$dir"*.md; do
    awk 'seen && /^---$/ { b=1; next } /^project:/ { seen=1 } b { print }' "$sf" | head -25
  done 2>/dev/null
done
```

### Step 2: タスク候補を抽出する

以下のシグナルを拾う。**迷ったら出す**（取捨選択はユーザーが行う）。

| シグナル | 例 | 出す先 |
|---|---|---|
| 自分が口頭で約束した | 「確認します」「見ておきます」「対応します」の後に完了記録がない | 自分ボール |
| 依頼を受領した | `@mori.a` 宛の依頼・レビュー依頼 | 自分ボール |
| 締切・日時が明示された | 「8/26 FIX」「本日16:00」「今週中に」 | 自分ボール（最上位） |
| 日報に着手記録があり完了記録がない | 「要件把握のみ」「未着手」「調整途中」 | 自分ボール |
| open な Issue/PR で自分がアサイン | assignee:@me / author:@me | 自分ボール |
| **open な** PR本文のチェックリストが未消化 | `- [ ]` が残っている | 自分ボール（**相手待ちと独立に動ける分がある**） |
| 未コミット差分・停止中worktree | `git status` に出る（docs/`.md` 除外後） | 自分ボール |
| 完了と報告したが助言・指摘の反映が残る | 「レビューで意見をもらった」「反映します」 | 自分ボール |
| 「〜さん待ち」「〜さんが調整中」 | **本人が明示的に待ちと述べている** | 他人ボール |
| PR が CHANGES_REQUESTED / レビュー提出済み | 自分がレビューを出し終えた | 他人ボール |
| 完了記録がある/完了を示唆する | 「マージしました」「完了しました」 | 完了っぽい |

**マージ済み・クローズ済みの PR/Issue のチェックリストは見ない。** チェックボックスはマージ判断のための作業メモであり、マージされた時点でその判断は済んでいる。未チェックのまま残っていても宿題ではない。**チェックリストを掘るのは open な PR/Issue に限る。**

**assignee が他人であることは、他人ボールの根拠にならない。** アサイン運用はリポジトリごとに異なり、実際には完了済みでも assignee が残ることがある。他人ボールに入れてよいのは**本人（または相手）が明示的に「待ち」と述べた記録がある場合のみ**。根拠が assignee だけなら「完了っぽい」に置いて確認を促す。

**「記録がないこと」は未完了の証拠にならない。** 電話・口頭・対面でのやり取りはどのデータソースにも残らない。約束の記録があって完了の記録がない場合、**未完了と断定せず「完了っぽい（要確認）」に置く**。断定すると、既に終わったことを何度も蒸し返すことになる。

**「完了っぽい」に注記を付けたくなったらブロックが違う。** 「ただし〜が残っている可能性あり」と書きたくなる項目は、その残りぶんが実際のタスク。**自分ボールに上げて、残りぶんを具体的なアクションとして書く。**

**時系列の最新を優先する。** 古い自己申告（「未着手」）と新しい実データ（PRマージ済み）が食い違ったら、**新しい方を採る**。日報は書かれた時点のスナップショットであり、その後の変化を含まない。

**`Closes #N` / `Fixes #N` を持つ open PR は展開して確認する。** マージ時に別Issueが自動クローズされる。そのIssueの中身が実際には解決していない場合、**未解決のまま静かに閉じる**。これは通常の経路では絶対に検出できないので明示的に見ること。

```bash
GH_TOKEN="$GH_WORK" gh pr view <N> --repo <repo> --json body --jq '.body' | grep -iE "closes|fixes|resolves"
```

### Step 3: 出力する

**必ず以下の3ブロック構成にする。** 順序・見出しを変えない。

各ブロックが「ユーザーが取る行動」で分かれているため、情報量が増えても認知コストが上がらない。**1本のリストにタグを付けて混ぜてはいけない** — 全行を同じ速度で読む必要が生じ、それが「ごちゃつく」状態になる。

```
## 🔴 自分ボール

1. **<タスク名>** — <次に取る具体的アクション>（締切があれば末尾に添える）

## ⏳ 他人ボール（待ち）

- **<待ち相手の名前>**
  - <何待ちか>
  - <同じ相手の別件>

## ✅ 完了っぽい（要確認）

<タスク名>マージ済 / <タスク名>相手確認済 / ...（カンマ区切りで1段落）
```

**ルール:**

- **自分ボールは1タスク1行。** タスク名＋次のアクションだけを書き、説明を積まない。複数行ブロックにすると、**最も重要なブロックが最も読みにくくなる** — 他人ボール・完了っぽいが1〜2行で視認しやすいのに、自分ボールだけ壁になるという逆転が起きる
- **根拠は書かない。** 出典・日付・PR番号を本文にも末尾にも載せない。これは自分の仕事の棚卸しであり、ユーザーは各項目を既に把握している。目的は「思い出す」ことであって「証明する」ことではない。**聞かれたときだけ答える**（そのため収集時の出典は手元に保持しておく）
- **優先度は提案であって決定ではない。** 締切明示 > 消失リスク（未push・未コミット差分）> 相手を待たせている > ブロッカー指定 > その他、の順に並べる。並べた上で「判断はユーザー」と添える
- **他人ボールは待ち相手を行頭に置き、人単位でグルーピングする。** 読む目的は「誰を催促するか」なので、まず人で引けて中身に降りられる形にする。**1件しかない相手も名前を見出しにしてぶら下げる** — 件数で書式を変えると出力構造が回ごとに揺れる
- **「完了っぽい」を勝手に消さない。** 判定を誤るのはこちら側であり、消すと消えたことにユーザーが気づけない。列挙して残す
- 期間外の古い open Issue/PR（塩漬け）は本文に混ぜず、末尾に `> 塩漬け: 30日以上更新のない open Issue/PR が N件（#12, #34...）` と件数だけ添える

## Common Mistakes

| やりがちな失敗 | 何が起きるか | 対処 |
|---|---|---|
| life を pull せずに読む | CLOSED Issue の空ボディを読み「作業なし」と誤読 | Step 0-1 を必ず実行 |
| gh のアカウントを混同 | 業務リポジトリが常に0件で返り、静かに全部見落とす | Step 0-2。0件を見たらアカウントを疑う |
| 日報の「未完了タスク: 他N件」を信じる | 実体のない数字を追う。業務タスクは1件も入っていない | 本文サマリーから拾う |
| 古い自己申告をそのまま採用 | マージ済みの作業を「未着手」と誤報告 | 時系列で最新の実データを優先 |
| Rocket Chat を絞らず読む | 雑談に埋もれてタスクを取りこぼす | 自分の発言・自分宛メンション・DMに絞る |
| 完了と判定して未完了リストから消す | 消えたことにユーザーが気づけない | 「完了っぽい」ブロックに列挙して残す |
| open な PR を「相手待ち」で片付ける | 本文チェックリストの自分で進められる分を見落とす | open PR に限りチェックリストの `- [ ]` を確認 |
| **マージ済みPRのチェックリストを掘る** | マージ判断済みの作業メモを宿題として誤報告する | open な PR/Issue だけを対象にする |
| **assignee が他人 → 他人ボールと判定** | 完了済みタスクを「待ち」として蒸し返す | 明示的な待ちの記録がなければ「完了っぽい」へ |
| **完了記録がない → 未完了と断定** | 電話・口頭で終わった件を何度も掘り返す | 断定せず「完了っぽい（要確認）」に置く |
| **`docs/`・`.md` の未コミットを出す** | 計画書が数十件ノイズになりタスクが埋もれる | コード実体の差分だけに絞る |
| **「完了っぽい」に but 注記を付ける** | 残りぶんが行動に結びつかない | 注記が付くなら自分ボールへ上げる |
| `Closes #N` を見ない | マージ時に未解決Issueが silent-close される | Step 2 で明示的に展開 |
| **件数を揃えようとして薄い項目で埋める** | 「open issue 3件」等の粗い塊が混ざり、粒度が壊れる | 項目数は結果。無理に増やさない |
| **同じタスクを自分ボールと他人ボールに重複計上** | どちらが実態か読み手が判断できない | 待ち相手が明示されているなら他人ボール1本に置く |
| **自分ボールを複数行ブロックで書く** | 最優先ブロックが一番の壁になり、他人ボール・完了っぽいの方が読みやすいという逆転が起きる | 1タスク1行に固定 |
| **根拠・出典を添える** | 行が伸びて一覧性が落ちる。ユーザーは自分の仕事を把握済みで、証明は求めていない | 書かない。聞かれたら答える |
| **他人ボールを案件単位で並べる** | 同じ相手が離れた行に散り、催促の判断ができない | 待ち相手を行頭にして人単位でまとめる |
| 出力構造を毎回変える | 前回との差分が取れず、可視化の意味が薄れる | 3ブロック構成を固定 |

## Red Flags

以下を思ったら手を止めること。

- 「これは終わってるやろから出さんでええか」→ **判定はユーザーの仕事。出す**
- 「0件やったから対象なしやな」→ **まず gh のアカウントを確認**
- 「日報が空やから作業なしやな」→ **pull したか確認。土日以外で空は疑う**
- 「相手待ちやから自分は何もできんな」→ **open PR のチェックリストを見たか**
- 「件数が多いから絞ろか」→ **取りこぼしゼロが目的。絞らずブロックで分ける**
- 「マージ済みやけどチェックが残ってるな」→ **それは宿題やない。出さへん**
- 「完了の記録が見当たらんから未完了やな」→ **断定せず「完了っぽい」へ。口頭で終わってるかもしれん**
- 「assignee が他人やから待ちやな」→ **明示的な待ちの記録があるか確認したか**
- 「完了っぽいけど一応注記付けとこ」→ **注記が要るなら自分ボールや**
