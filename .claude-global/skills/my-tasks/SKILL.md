# タスク棚卸し（my-tasks）

一次データ（日報・Rocket Chat・GitHub/GitBucket・gitワークツリー・Claudeセッション要約）を横断して、**今抱えているタスクを取りこぼしなく列挙する**。

**このスキルのゴールは可視化であって、判定ではない。** ユーザーは完了/未完了を自分で分かっている。速くて正確なのはユーザー側の判定であり、こちらの役目は「候補を漏れなく机の上に並べる」こと。

`work-report`（過去に何をやったかの報告）とは問いが直交する。あちらは「やったこと」、こちらは「残っていること」。

## やらないこと

- ファイル保存・git commit・Issue登録（チャット出力のみ）
- 外部アクション（PRコメント投稿・催促メッセージ送信）。**提案までで止まる**
- KPT・工数集計・生産性指標（それぞれ `weekly-report` / `effort-estimate` の役割）
- 個人リポジトリ（`~/.dotfiles`、`aya-215/life` 自体）の作業を業務タスクとして出すこと

## 対象期間

**直近2週間固定。** `start=$(date -d '14 days ago' +%Y-%m-%d)`、`end=today`。

ただし**期間フィルタは「一次データを読む範囲」にのみ適用する。** open な Issue/PR の状態確認は期間外でも行う（後述の「塩漬け」参照）。

## 実行コスト

Step 0〜3 をすべて実行して**8分前後**かかる。短縮モードは設けない。

トークン量の目安（別実行での実測値。日によって増減する）:

| ソース | 実測 |
|---|---|
| Rocket Chat | 435行 / 88KB → **50k tokens 超** |
| セッション要約 | 66ファイル・1,648行 / 129KB → **約26k tokens** |

**バイト数からトークン数を割り算で概算しないこと。** 日本語でも URL・マークアップ・
英数字が混じるため比率が一定にならない。実測では `bytes ÷ 3` が Rocket Chat で
**4割ほど過小**に出た（88KB → 概算29k に対し実測50k超）。見積もりが要るなら実測すること。

なお修正前は期間フィルタが効かず、セッション要約だけで**約272k tokens**を読んでいた。

工程を省いた簡易版を実測したところ、時間は33%減ったが、省いた工程ぶん以上に精度が落ちた（相手待ちタスクの「自分で動ける分」が見えなくなる、薄い項目で件数を埋める、注記付きの項目を「完了っぽい」に置いたまま放置する）。**取りこぼしゼロが目的である以上、この交換は成立しない。**

待ち時間が問題になる場合は、モードを削るのではなくバックグラウンドで実行すること。

## 手順

### Step 0: 前提を整える（必須・スキップ禁止）

この2つを飛ばすと、**エラーが出ないまま間違った結論が出る**。

**0-1. 日報リポジトリを最新化する**

```bash
git -C ~/src/github.com/aya-215/life pull --ff-only
```

ローカルが古いと、blog md が存在しない日について「Issue を見に行く」経路に落ちる。その Issue が既に CLOSED（＝blog md へ移行済み）だと**空のサマリーを読んで「その日は作業なし」と誤読する**。pull すれば blog md が現れて解決する。

**0-2. gh の認証アカウントを使い分ける**

| 対象 | アカウント | 指定方法 |
|---|---|---|
| `aya-215/life`（日報） | aya-215 | `GH_TOKEN=$(gh auth token --user aya-215)` |
| `ebase-dev/*`（業務） | eBASE-Mori | `GH_TOKEN=$(gh auth token --user eBASE-Mori)` |

**取り違えると 0件が静かに返る。** `--author=@me` / `--review-requested=@me` は「今アクティブなアカウント」で解決されるため、業務リポジトリを aya-215 で叩くと常に空になる。0件を見たら**まずアカウントを疑う**こと。

`gh auth status` で現在のアクティブアカウントを確認できる。

### Step 1: 一次データを集める

以下を**並列に**実行する（相互に依存しない）。

**日報サマリー（直近2週間）**

```bash
LIFE=~/src/github.com/aya-215/life
GH_LIFE=$(gh auth token --user aya-215)
d=$(date -d '14 days ago' +%Y-%m-%d)
while [ "$(date -d "$d" +%s)" -le "$(date +%s)" ]; do
  f="$LIFE/blog/$(echo "$d" | tr -d '-').md"
  if [ -f "$f" ]; then
    echo "=== $d ==="; sed -n '/^## 📝 サマリー/,/^## /p' "$f" | sed '$d'
  else
    n=$(GH_TOKEN="$GH_LIFE" gh issue list --repo aya-215/life \
      --search "in:title ${d} の記録" --state all --label memo --json number,title \
      --jq "[.[] | select(.title | startswith(\"${d} \"))][0].number" 2>/dev/null)
    [ -n "$n" ] && { echo "=== $d (issue #$n) ==="; GH_TOKEN="$GH_LIFE" gh issue view "$n" \
      --repo aya-215/life --json body --jq '.body' | sed -n '/^## 📝 サマリー/,/^## /p' | sed '$d'; }
  fi
  d=$(date -d "$d +1 day" +%Y-%m-%d)
done
```

> **日報・セッション要約に含まれる過去の `/my-tasks` 出力は一次データではない。**
> このスキルの実行結果は日報とセッション要約に記録されるため、次回それを読むと
> **前回の推測が「実測された事実」として戻ってくる。** 実測で、ある締切を全ソースに grep したところ
> ヒットは日報とセッション要約の2箇所だけで、どちらも過去の my-tasks 出力の引用であり、
> 一次発言はどこにも存在しなかった。「タスク棚卸し」「/my-tasks で整理」といった記述を見たら
> **そこから先は自分の過去出力なので、根拠として使わない。** 締切・タスク名は必ず
> Rocket Chat・Issue/PR 等の一次発言まで遡って裏を取ること。

> **日報の「未完了タスク: 他N件」欄は読まない。** 生成元の `nb tasks:todos open` に業務タスクが1件も入っておらず、名指しされる項目も blog に直接埋め込まれた古い固定文字列である。この欄からは業務タスクは拾えない。**タスクは本文サマリーから拾うこと。**

**Rocket Chat（全文をそのまま読む。grep で絞らない）**

```bash
start=$(date -d '14 days ago' +%Y-%m-%d); end=$(date +%Y-%m-%d)
bash ~/.dotfiles/scripts/lib/rocketchat.sh --from "$start" --to "$end" --include-dm
```

> **`start` / `end` は各コマンドの先頭で定義すること。** Bash 呼び出し間でシェル変数は persist しない。
> 未定義のまま渡すと `rocketchat.sh` が「--from と --to は必須」で `exit 2` する（静かには壊れないが1ステップ無駄になる）。

**`grep -nE "=====|mori\.a:|@mori\.a"` で絞ってはいけない。** かつてこの絞り込みを使っていたが、実測で
判定を壊すことが判明したため撤去した。理由は3つある。

1. **他人の返信行が構造的に全て消える。** 残るのは自分の発言と自分宛メンションだけなので、
   「自分が質問し、答えが無い」という形だけが量産される。**他人ボールが必ず水増しされる方向に偏る。**
   実測では、返信で決着済みの5件（相談3件・障害報告1件・他メンバーへの引き継ぎ1件）が全て
   「相手待ち」として誤って出力された。
2. **前後文脈を足しても解決しない。** `-B2 -A6` を付けると 445行中401行（90%）が残り、
   全文との差はわずか **約1,700 tokens**。フィルタとして機能していない。
3. **フィルタ出力を保存ファイルにする事故が起きる。** 出力が大きいと退避ファイルへ書かれ、
   以降そちらを読み続けてしまう。`grep -n` を二重に通すと行番号も二重採番になり、
   前後を見に行こうとしても座標が合わない。

**全文は Read の上限を超えるので、必ず分割して最後まで読み切ること。** 実測で 88KB は
1回では読めず、274行目付近で切られて2回に分かれた。**1ページ目だけで判定に入ってはいけない。**
決着の一言も、自分が宣言した作業も、後半にしか無いことがある（実測では下川さん案件・
障害報告の決着・他メンバーの引き取りが全て2ページ目にあった）。
`offset` をずらして末尾まで読んでから Step 2 に進むこと。

全文は実測で **435行・50k tokens 超**（14日ぶん）。雑談は確かに多いが、
**その雑談の中に決着の一言（「ダメでした」「いそぎません」「〜が原因でした」）が混ざる。**
読み飛ばすコストより、決着を見落として幽霊タスクを出すコストの方が高い。

**open な Issue/PR（期間フィルタなしで状態を引く）**

```bash
GH_WORK=$(gh auth token --user eBASE-Mori)
for r in ebase-dev/ebase-portal-chat ebase-dev/ebase-middleware-mcp \
         ebase-dev/eb-api-extended ebase-dev/ebase-agent-specs; do
  echo "=== $(basename "$r") ==="
  i=$(GH_TOKEN="$GH_WORK" gh issue list --repo "$r" --state open --assignee @me \
    --json number,title,updatedAt --jq '.[] | "\(.number)\t\(.updatedAt[:10])\t\(.title)"')
  p=$(GH_TOKEN="$GH_WORK" gh pr list --repo "$r" --state open --author @me \
    --json number,title,updatedAt,reviewDecision \
    --jq '.[] | "PR#\(.number)\t\(.updatedAt[:10])\t\(.reviewDecision // "-")\t\(.title)"')
  # レビュー依頼は assignee/author のどちらにも掛からないため独立に引く（下の注記を参照）
  q=$(GH_TOKEN="$GH_WORK" gh pr list --repo "$r" --state open --search "review-requested:@me" \
    --json number,title,updatedAt \
    --jq '.[] | "PR#\(.number)\t\(.updatedAt[:10])\treview-requested\t\(.title)"')
  [ -n "$i" ] && echo "$i"
  [ -n "$p" ] && echo "$p"
  [ -n "$q" ] && echo "$q"
  # 3つとも0件なら絞り込みを外して全openを見る（自分が起票していない宿題を拾うため）
  if [ -z "$i" ] && [ -z "$p" ] && [ -z "$q" ]; then
    echo "  -- assignee/author ともに0件。全openを表示 --"
    GH_TOKEN="$GH_WORK" gh issue list --repo "$r" --state open \
      --json number,title,updatedAt --jq '.[] | "\(.number)\t\(.updatedAt[:10])\t\(.title)"'
  fi
done
```

**`--search "review-requested:@me"` を省かないこと。** レビュー依頼は `--assignee @me`（Issue）にも
`--author @me`（自分が書いた PR）にも掛からない。**他人の PR に自分が指名されている状態**なので、
この2軸では原理的に拾えない。実測した取りこぼし:

```
                       assignee@me  author@me  フォールバック  review-requested@me
ebase-portal-chat        #665         なし        発動せず       PR#684, PR#683  ← 落ちる
ebase-middleware-mcp     なし         #229        発動せず       PR#230          ← 落ちる
eb-api-extended          #59          なし        発動せず       なし
ebase-agent-specs        なし         なし        ★発動          なし
```

**フォールバックは「両方0件」が条件なので、片方にヒットがあると発動しない。**
その結果、生きているレビュー依頼3本が一覧に一度も現れなかった。
Step 2 には「レビュー関連の open PR は1件ずつ実状態を引く」と書いてあるが、
**Step 1 がその PR を集めていなければ判定のしようがない。** ここは Step 2 と対になっている。

**この4リポジトリはリモート基準の固定リストであり、ローカル列挙で置き換えてはいけない。**
`ls -d ~/src/github.com/ebase-dev/*/` で置き換えると2方向に壊れる（実測済み）:

- `eb-api-extended` は**ローカルに clone が無く** `/mnt/d/tomcat/webapps/` にしかない → **脱落する**
- `emm-*` / `epc-*` は親リポジトリの **worktree** で、同じ Issue/PR を指す → **重複して引く**

つまり **Issue/PR sweep の対象集合と、後述の git status sweep の対象集合は別物**。
前者はリモート基準の固定リスト、後者はローカル glob（worktree を拾う必要がある）。統一しないこと。
リポジトリが増えたときは `gh repo list ebase-dev --limit 50 --json name --jq '.[].name'` で確認して
このリストに手で足す。

**`--assignee @me` / `--author @me` がともに0件のリポジトリは、絞り込みを外して全 open を見る。**
このリポジトリ群は assignee をほぼ付けない運用のため `--assignee @me` は0件になりやすく、
さらに**自分が起票していない Issue が自分の宿題になっている**ケースがある。実測値:

```
                       assignee@me  author@me  全open
ebase-portal-chat            1          4        30
ebase-middleware-mcp         0          5        16
eb-api-extended              1          4         6
ebase-agent-specs            0          0         6   ← 両方0。全openを見ないと6件すべて落ちる
```

**この分岐は上のスニペットに実装済み**（両方0件なら自動で全 open を出す）。出てきた項目は
チャット文脈・git実データと突き合わせて自分に関係するものを拾う。
なお**全リポジトリで `--author @me` が0**なら、それはアカウント取り違えを疑う（Step 0-2）。

**GitBucket（社内）** は `mcp__gitbucket__gitbucket_list_prs` / `gitbucket_list_issues` を使う。`gh` は通らない。
対象は **`owner=hankyu_kitchenyell` / `repo=ebase-web`**（`/mnt/d/tomcat/webapps/hankyu` の remote から特定・疎通確認済み）。
他にも増えている可能性があるため、次のコマンドで remote を洗い出してから叩くこと:

```bash
for d in ~/src/github.com/*/*/ /mnt/d/tomcat/webapps/*/; do
  u=$(git -C "$d" remote get-url origin 2>/dev/null)
  case "$u" in *gitbucket*) echo "$(basename "$d") -> $u";; esac
done 2>/dev/null
```

GitBucket には `--author @me` 相当の絞り込みが無い。**自分の表記は `eBASE-Mori` と `森彪人` の2種類が混在している**
（コミット履歴で実測）ため、単純一致で絞ると取りこぼす。件数が少ないので**全 open を取得して目視で判別する**こと。

**チェックリストの展開は open な PR/Issue のみ**を対象にする。マージ済み・クローズ済みは対象外（理由は Step 2 を参照）。

**gitワークツリーの取り残し（コード実体のみ）**

```bash
for r in ~/src/github.com/ebase-dev/*/ /mnt/d/tomcat/webapps/hankyu /mnt/d/tomcat/webapps/eb-api-extended; do
  [ -d "$r/.git" ] || [ -f "$r/.git" ] || continue
  s=$(git -C "$r" status --short 2>/dev/null \
    | grep -vE '(^\?\? |/)docs/|\.md$|^\?\? .*\.(zip|sql|txt|log|csv)$|^\?\? .*/?_[^/]*$' | head -20)
  [ -n "$s" ] && { echo "=== $(basename "$r") ==="; echo "$s"; \
    echo "  branch: $(git -C "$r" branch --show-current)"; }
done
```

**こちらはローカル glob で正しい。** Issue/PR sweep と違い、`emm-*` / `epc-*` の **worktree にこそ未コミット差分が残る**
（実測で `package-lock.json` の差分を検出）。`*/` を固定リストに置き換えないこと。

**`docs/` 配下・`.md`・調査用の一時ファイルは除外する。** このユーザーは docs をコミットしない運用のため、除外しないと計画書が数十件ノイズとして出てタスクが埋もれる。
`^\?\? .*/?_[^/]*$` は `_oom_probe.mjs` のような**アンダースコア始まりの使い捨て調査スクリプト**を落とす（実測で5件除去、コード実体の差分は保持）。

残るのは**コード実体の未コミット差分**のみ。これは「作業したが着地していない」の強いシグナルで、特に**マージ済みブランチの上に乗った差分**は紛失・混線リスクがあるため必ず出す。

**Claudeセッション要約（gitに残らない調査・調整作業の補完）**

```bash
start=$(date -d '14 days ago' +%Y-%m-%d)
for dir in ~/.nb/claude/sessions/*/; do
  d=$(basename "$dir")
  [[ "$d" < "$start" ]] && continue
  for sf in "$dir"*.md; do
    [ -f "$sf" ] || continue
    awk 'seen && /^---$/ { b=1; next } /^project:/ { seen=1 } b { print }' "$sf" | head -25
  done 2>/dev/null
done
```

> **`[ -f "$sf" ] || continue` を省かないこと。** `.md` が1つも無い日があり、zsh は該当なしの glob に対して
> `no matches found` エラーを出して**ループごと中断する**（bash のように未展開のまま渡らない）。
> 途中の日で止まると以降が読まれないが、エラーが紛れて気づきにくい。

> **`[ "$d" \< "$start" ]` と書かないこと。** ユーザーのシェルは zsh で、`[` は `\<` を解釈せず
> `condition expected: <` を stderr に吐いて **`continue` を実行しない**。エラーで止まらないため
> 気づけないまま**全期間を読む**。実測では対象10ディレクトリに対し55ディレクトリ・464ファイルを読み、
> 2ヶ月前に完了した作業が「今のタスク」として並んだ。必ず `[[ ]]` を使う。
> 同じ罠は `quarterly-dev-report` でも踏まれており、姉妹スキル（`retrospective`・`verify-daily-report`）は
> すでに `[[ ]]` へ移行済み。

### Step 2: タスク候補を抽出する

以下のシグナルを拾う。**迷ったら出す**（取捨選択はユーザーが行う）。

| シグナル | 例 | 出す先 |
|---|---|---|
| 自分が口頭で約束した | 「確認します」「見ておきます」「対応します」の後に完了記録がない | 自分ボール |
| **自分が成果物を作ると宣言した** | 「修正PR出します」「issue作成します」「〜を作成します」「〜に連携します」「また連絡します」 | 自分ボール |
| 依頼を受領した | `@mori.a` 宛の依頼・レビュー依頼（**3名以上への一斉メンションを除く**） | 自分ボール |
| 締切・日時が明示された | 「8/26 FIX」「本日16:00」「今週中に」 | 自分ボール（最上位） |
| 日報に着手記録があり完了記録がない | 「要件把握のみ」「未着手」「調整途中」 | 自分ボール |
| open な Issue/PR で自分がアサイン | assignee:@me / author:@me | 自分ボール |
| **open な** PR本文のチェックリストが未消化 | `- [ ]` が残っている | 自分ボール（**相手待ちと独立に動ける分がある**） |
| 未コミット差分・停止中worktree | `git status` に出る（docs/`.md` 除外後） | 自分ボール |
| 完了と報告したが助言・指摘の反映が残る | 「レビューで意見をもらった」「反映します」 | 自分ボール |
| 「〜さん待ち」「〜さんが調整中」 | **本人が明示的に待ちと述べている** | 他人ボール |
| PR が CHANGES_REQUESTED / レビュー提出済み | 自分がレビューを出し終えた | 他人ボール |
| 完了記録がある/完了を示唆する | 「マージしました」「完了しました」 | 完了っぽい |

**マージ済み・クローズ済みの PR/Issue のチェックリストは見ない。** チェックボックスはマージ判断のための作業メモであり、マージされた時点でその判断は済んでいる。未チェックのまま残っていても宿題ではない。**チェックリストを掘るのは open な PR/Issue に限る。**

**他人ボールに置く前に、その発言以降の返信を必ず読む。** これは推測ではなく確認できる事実なので、
省略してはいけない。自分が投げた質問・依頼・報告に相手が答えていれば、その時点で他人ボールではない。
返信の内容によって行き先が変わる:

| 返信の内容 | 行き先 |
|---|---|
| 「〜が原因でした」「対応しました」（決着） | 完了っぽい |
| 「いそぎません、が進めておいてください」（自分に戻った） | **自分ボール** |
| 他メンバーが「こちらで進めます」と引き取った | 対象外（**ただし下の分解ルールを先に適用する**） |
| 返信が無い | 他人ボール |

**引き取りを判定する前に、自分の発言に作業がいくつ含まれるか数える。** ひとつの発言が
複数の作業に言及していることは多く、**そのうち一部だけが引き取られる。** 発言全体が
引き取られたと解釈すると、引き取られていない作業が消える。

実測した誤り:

```
自分:   「Xがまだ実装できていないので、取り急ぎYのみ変更したものを作成します」
          → 作業A: 取り急ぎYを作成（自分が宣言）／作業B: Xの実装（未着手）

他メンバー:「こちらでFEタスクとして進める予定でした。9月前半までには実装できます」
          → 引き取ったのは作業B（「実装」「9月前半」が指しているのはXの方）

誤った判定: 発言全体が引き取られた → 作業Aごと対象外に消えた
正しい判定: 作業Bのみ対象外。作業Aは自分ボールに残る
```

**引き取りの範囲は、引き取った側の言葉で判断する。** 上の例では「実装」「9月前半」という
語が作業Bだけを指している。**自分の発言の全体量ではなく、相手が名指しした対象に限って外す。**
判断がつかないときは外さない（迷ったら出す、が原則）。

**「自分の質問だけが並んでいる」状態は、返信を読んでいない兆候である。** 会話は普通、答えが返る。
自分の発言だけが連なって見えるなら、データの取り方を疑うこと（Step 1 の Rocket Chat を参照）。

**質問形だけでなく宣言形も拾う。** 「〜でしょうか？」（質問）は相手に渡るが、
「〜します」「〜を作成します」（宣言）は**自分に残る**。質問形だけを拾って宣言形を拾わないと、
他人ボールばかりが増えて自分の宿題が消える。実測で、自分が「取り急ぎ〜を作成します」と
宣言した作業が丸ごと出力から欠落した。

**3名以上への一斉メンションは依頼ではない。** 週報リンクの共有・議事録の共有・
マイルストーン更新の告知などは、宛先に自分が含まれていても定型連絡である。
**名指しの依頼（「@mori.a これ見てもらえますか」）が伴う場合のみタスクにする。**

**締切は、根拠となる発言を特定できるときだけ書く。** 締切は最優先のソート条件なので、
貼り間違えると並び順ごと壊れる。実測で、ある案件で合意した日付を、
話題が近い別タスク（依存関係の後段にある未着手のリファクタリング）に貼ってしまい、
着手すらできないタスクが最上位に並んだ。**「どの発言で誰と合意したか」を言えない締切は書かない。**

**assignee が他人であることは、他人ボールの根拠にならない。** アサイン運用はリポジトリごとに異なり、実際には完了済みでも assignee が残ることがある。他人ボールに入れてよいのは**本人（または相手）が明示的に「待ち」と述べた記録がある場合のみ**。根拠が assignee だけなら「完了っぽい」に置いて確認を促す。

**「記録がないこと」は未完了の証拠にならない。** 電話・口頭・対面でのやり取りはどのデータソースにも残らない。約束の記録があって完了の記録がない場合、**未完了と断定せず「完了っぽい（要確認）」に置く**。断定すると、既に終わったことを何度も蒸し返すことになる。

**「完了っぽい」に注記を付けたくなったらブロックが違う。** 「ただし〜が残っている可能性あり」と書きたくなる項目は、その残りぶんが実際のタスク。**自分ボールに上げて、残りぶんを具体的なアクションとして書く。**

**時系列の最新を優先する。** 古い自己申告（「未着手」）と新しい実データ（PRマージ済み）が食い違ったら、**新しい方を採る**。日報は書かれた時点のスナップショットであり、その後の変化を含まない。

**レビュー関連の open PR は、一覧の結果で判定せず1件ずつ実状態を引く。**
一覧に出ている＝自分の宿題、ではない。次の3状態は `reviewRequests` と自分の `reviews` で決定的に判別できる:

```bash
GH_WORK=$(gh auth token --user eBASE-Mori)
GH_TOKEN="$GH_WORK" gh pr view <N> --repo <repo> --json title,author,reviewRequests,reviews \
  --jq '"title: \(.title)",
        "author: \(.author.login)",
        "reviewRequests: \([.reviewRequests[].login]|join(","))",
        "myReview: \([.reviews[]|select(.author.login=="eBASE-Mori")|.state]|join(","))"'
```

**この表は他人の PR に対する判定用である。`author` が自分の PR は表に掛けず、無条件で自分ボールに置く。**
自分の PR は自分にレビュー依頼が付かないため `reviewRequests` は空、自分でレビューも出さないので
`reviews` も空になる。**表の最終行に当たって「対象外」として消える。** 実測で、
`reviewDecision: CHANGES_REQUESTED` が付いた対応待ちの自分の PR がこれで消えかけた。
`--json` に `author` を必ず含め、**先に author を見て自分なら表を使わないこと。**

| reviewRequests | 自分の review | 判定 |
|---|---|---|
| 自分が含まれる | 無し | **自分ボール**（レビュー未提出） |
| 自分が含まれる | 提出済み | 自分ボール（再レビュー依頼が来ている） |
| 空 | APPROVED / CHANGES_REQUESTED | 完了っぽい |
| 空 | 無し | **対象外**（自分に用は無い。出さない） |

**レビュー依頼は実行中に増える。** 実測で、ある PR の `reviewRequests` が空だった数時間後に
3名が追加されていた。**収集時点のスナップショットであり、古い判定を次回に持ち越さないこと。**

実測で3件を検証し、3件とも上表どおりに正解した。表を使わずに一覧だけで判定したときは、
**既に Approve 済みの PR と、レビュー依頼が解除済みの PR を自分ボールへ誤って出した。**

**一覧取得時のタイトルを判定にも出力にも使わない。** PR は改題される。
実測で、一覧取得時とその後で内容の異なるタイトルになっていた PR があり、
古いタイトルのまま「別の不具合の修正」として報告してしまった。**タイトルは必ず個別取得の値を使う。**

**`Closes #N` / `Fixes #N` を持つ open PR は展開して確認する。** マージ時に別Issueが自動クローズされる。そのIssueの中身が実際には解決していない場合、**未解決のまま静かに閉じる**。これは通常の経路では絶対に検出できないので明示的に見ること。

```bash
GH_WORK=$(gh auth token --user eBASE-Mori)
GH_TOKEN="$GH_WORK" gh pr view <N> --repo <repo> --json body --jq '.body' | grep -iE "closes|fixes|resolves"
```

> **`GH_WORK` の定義を省略しないこと。** Bash 呼び出し間で変数は persist しないため、
> 未定義だと `GH_TOKEN=""` になる。このとき `gh` は**エラーにならず現在のアクティブアカウントへ
> 静かにフォールバックする**（実測確認済み）。eBASE-Mori がアクティブなら偶然動くが、
> aya-215 に切り替わっていると 0件が静かに返る — Step 0-2 の失敗モードそのもの。

### Step 3: 出力する

**必ず以下の3ブロック構成にする。** 順序・見出しを変えない。

各ブロックが「ユーザーが取る行動」で分かれているため、情報量が増えても認知コストが上がらない。**1本のリストにタグを付けて混ぜてはいけない** — 全行を同じ速度で読む必要が生じ、それが「ごちゃつく」状態になる。

```
## 🔴 自分ボール

1. **<タスク名>** — <次に取る具体的アクション>（締切があれば末尾に添える）

## ⏳ 他人ボール（待ち）

- **<待ち相手の名前>**
  - <何待ちか>
  - <同じ相手の別件>

## ✅ 完了っぽい（要確認）

<タスク名>マージ済 / <タスク名>相手確認済 / ...（カンマ区切りで1段落）
```

**ルール:**

- **自分ボールは1タスク1行。** タスク名＋次のアクションだけを書き、説明を積まない。複数行ブロックにすると、**最も重要なブロックが最も読みにくくなる** — 他人ボール・完了っぽいが1〜2行で視認しやすいのに、自分ボールだけ壁になるという逆転が起きる
- **根拠は書かない。** 出典・日付・PR番号を本文にも末尾にも載せない。これは自分の仕事の棚卸しであり、ユーザーは各項目を既に把握している。目的は「思い出す」ことであって「証明する」ことではない。**聞かれたときだけ答える**（そのため収集時の出典は手元に保持しておく）
- **優先度は提案であって決定ではない。** 締切明示 > 消失リスク（未push・未コミット差分）> 相手を待たせている > ブロッカー指定 > その他、の順に並べる。並べた上で「判断はユーザー」と添える
- **他人ボールは待ち相手を行頭に置き、人単位でグルーピングする。** 読む目的は「誰を催促するか」なので、まず人で引けて中身に降りられる形にする。**1件しかない相手も名前を見出しにしてぶら下げる** — 件数で書式を変えると出力構造が回ごとに揺れる
- **「完了っぽい」を勝手に消さない。** 判定を誤るのはこちら側であり、消すと消えたことにユーザーが気づけない。列挙して残す
- 期間外の古い open Issue/PR（塩漬け）は本文に混ぜず、末尾に `> 塩漬け: 30日以上更新のない open Issue/PR が N件（#12, #34...）` と件数だけ添える

## Common Mistakes

| やりがちな失敗 | 何が起きるか | 対処 |
|---|---|---|
| life を pull せずに読む | CLOSED Issue の空ボディを読み「作業なし」と誤読 | Step 0-1 を必ず実行 |
| gh のアカウントを混同 | 業務リポジトリが常に0件で返り、静かに全部見落とす | Step 0-2。0件を見たらアカウントを疑う |
| 日報の「未完了タスク: 他N件」を信じる | 実体のない数字を追う。業務タスクは1件も入っていない | 本文サマリーから拾う |
| 古い自己申告をそのまま採用 | マージ済みの作業を「未着手」と誤報告 | 時系列で最新の実データを優先 |
| **Rocket Chat を grep で絞る** | 他人の返信行が全て消え、決着済みの件が「相手待ち」として量産される | 全文を読む。前後文脈を足しても90%残るので絞る意味がない |
| **返信を読まずに他人ボールへ置く** | 既に答えが返っている件を「催促候補」として蒸し返す | 発言以降の返信を必ず読み、内容で行き先を決める |
| **質問形だけ拾って宣言形を拾わない** | 他人ボールが水増しされ、自分が宣言した成果物が丸ごと消える | 「〜します」「〜を作成します」は自分ボール |
| **一覧の結果でレビューPRを判定** | Approve 済み・依頼解除済みの PR を自分ボールへ誤出力する | `reviewRequests` と自分の `reviews` を1件ずつ引く |
| **一覧取得時のタイトルを使い回す** | 改題された PR を別件として報告する | タイトルは個別取得の値を使う |
| **締切を話題の近いタスクに貼る** | 着手できないタスクが最上位に並び、並び順ごと壊れる | 根拠の発言を特定できない締切は書かない |
| **3名以上への一斉メンションを依頼と解釈** | 週報リンク等の定型連絡がタスクとして並ぶ | 名指しの依頼が伴う場合のみタスクにする |
| **一部の引き取りを発言全体の引き取りと解釈** | 引き取られていない作業まで対象外に消える | 発言に含まれる作業を数え、相手が名指しした分だけ外す |
| **`review-requested:@me` を引かない** | 他人のPRのレビュー依頼が原理的に拾えず、生きた依頼が丸ごと落ちる | assignee/author と独立に引く |
| **自分が author の PR に判定表を当てる** | 対応待ちの自分のPRが「対象外」として消える | author が自分なら表を使わず無条件で自分ボール |
| **Rocket Chat の1ページ目だけで判定に入る** | 決着・引き取り・自分の宣言が後半にあると全て落ちる | offset をずらして末尾まで読み切る |
| **過去の my-tasks 出力を一次データとして読む** | 前回の推測が「事実」として固定化し、循環する | 日報・セッション要約中の棚卸し記述は根拠にしない |
| **bytes ÷ 3 でトークン数を概算する** | 実測と4割ズレる。見積もりを外す | 割り算で出さない。必要なら実測する |
| 完了と判定して未完了リストから消す | 消えたことにユーザーが気づけない | 「完了っぽい」ブロックに列挙して残す |
| open な PR を「相手待ち」で片付ける | 本文チェックリストの自分で進められる分を見落とす | open PR に限りチェックリストの `- [ ]` を確認 |
| **マージ済みPRのチェックリストを掘る** | マージ判断済みの作業メモを宿題として誤報告する | open な PR/Issue だけを対象にする |
| **assignee が他人 → 他人ボールと判定** | 完了済みタスクを「待ち」として蒸し返す | 明示的な待ちの記録がなければ「完了っぽい」へ |
| **完了記録がない → 未完了と断定** | 電話・口頭で終わった件を何度も掘り返す | 断定せず「完了っぽい（要確認）」に置く |
| **`docs/`・`.md` の未コミットを出す** | 計画書が数十件ノイズになりタスクが埋もれる | コード実体の差分だけに絞る |
| **「完了っぽい」に but 注記を付ける** | 残りぶんが行動に結びつかない | 注記が付くなら自分ボールへ上げる |
| `Closes #N` を見ない | マージ時に未解決Issueが silent-close される | Step 2 で明示的に展開 |
| **件数を揃えようとして薄い項目で埋める** | 「open issue 3件」等の粗い塊が混ざり、粒度が壊れる | 項目数は結果。無理に増やさない |
| **同じタスクを自分ボールと他人ボールに重複計上** | どちらが実態か読み手が判断できない | 待ち相手が明示されているなら他人ボール1本に置く |
| **自分ボールを複数行ブロックで書く** | 最優先ブロックが一番の壁になり、他人ボール・完了っぽいの方が読みやすいという逆転が起きる | 1タスク1行に固定 |
| **根拠・出典を添える** | 行が伸びて一覧性が落ちる。ユーザーは自分の仕事を把握済みで、証明は求めていない | 書かない。聞かれたら答える |
| **他人ボールを案件単位で並べる** | 同じ相手が離れた行に散り、催促の判断ができない | 待ち相手を行頭にして人単位でまとめる |
| 出力構造を毎回変える | 前回との差分が取れず、可視化の意味が薄れる | 3ブロック構成を固定 |

## Red Flags

以下を思ったら手を止めること。

- 「これは終わってるやろから出さんでええか」→ **判定はユーザーの仕事。出す**
- 「0件やったから対象なしやな」→ **まず gh のアカウントを確認**
- 「日報が空やから作業なしやな」→ **pull したか確認。土日以外で空は疑う**
- 「相手待ちやから自分は何もできんな」→ **open PR のチェックリストを見たか**
- 「件数が多いから絞ろか」→ **取りこぼしゼロが目的。絞らずブロックで分ける**
- 「Rocket Chat 長いから grep で絞ろか」→ **返信が全部消える。全文を読む**
- 「自分の質問ばっかり並んどるな」→ **返信を読んでいない兆候。データの取り方を疑う**
- 「一覧にレビュー依頼が出とるから自分ボールやな」→ **`reviewRequests` を個別に引いたか**
- 「この締切、たぶんこのタスクのやつやろ」→ **根拠の発言を言えないなら書かない**
- 「週報のメンション来とるからタスクやな」→ **3名以上の一斉連絡は依頼やない**
- 「他の人が引き取ってくれたから対象外やな」→ **引き取られたんはどの作業か。発言に何個入っとる**
- 「レビュー依頼は author か assignee で拾えるやろ」→ **どっちにも掛からん。専用クエリを引け**
- 「自分のPRやから reviewRequests 空やな、対象外や」→ **author が自分なら無条件で自分ボール**
- 「日報に前回の棚卸し結果が書いてあるわ」→ **それは自分の過去出力。一次発言まで遡れ**
- 「マージ済みやけどチェックが残ってるな」→ **それは宿題やない。出さへん**
- 「完了の記録が見当たらんから未完了やな」→ **断定せず「完了っぽい」へ。口頭で終わってるかもしれん**
- 「assignee が他人やから待ちやな」→ **明示的な待ちの記録があるか確認したか**
- 「完了っぽいけど一応注記付けとこ」→ **注記が要るなら自分ボールや**
