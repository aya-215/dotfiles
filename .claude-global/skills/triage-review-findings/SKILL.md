# レビュー指摘のトリアージ

レビュー指摘を受け取った直後に、**何を実際に直すか**を決める。

## このスキルが必要な理由

レビュアーは「何か見つける」方向に働く。見つからないと仕事をしていないように見えるため、
到達不能なコードや理論上の問題まで拾う。それ自体は悪くないが、**受け取る側が選別しないと
際限がない**。

判定は両方向に転ぶ。どちらの失敗も実測例がある。

### 失敗A: 応えすぎる

実測例（1つのPRでレビュー3周・計8件）:

| 種類                     | 件数 |
| ------------------------ | ---- |
| 実際に壊れていた         | 3    |
| 到達不能                 | 1    |
| 安全側の過剰動作         | 1    |
| 設計判断（バグではない） | 1    |
| 理論上のみ（再現不能）   | 1    |
| **前の修正が生んだ**     | 1    |

壊れていたのは3件。しかも1件は過剰修正の副産物だった。
LOW の指摘を直すために構造を変え、それが MEDIUM の指摘を生んだ。

同じ動機はコメントと issue にも出る。**却下したぶんをコメントや issue に変換すれば、
結果は応えすぎと同じ**になる。だから抑えるべき対象は3つある: 実装 / コメント / issue化。

### 失敗B: 却下しすぎる

| 事例                            | 判断                                                                | 結果                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| トランスポート配線の切替        | 「設計変更で規模が大きい」と見積もり、スコープ外として別issueを提案 | **誤り**。問い直されて試作したら**実質15行**で、PRの主張（仕様準拠）がこれ無しには成立しなかった               |
| ドメインルールのUseCase集約     | 「設計変更で本PRの2倍の差分」と見積もり、issue化を提案              | **誤り**。実測したら **+24/−13行**（型チェック・arch-check パス）。見積もりのまま issue化 へ分岐していた       |

どちらも**実測せずに見積もりで却下した**のが原因。「設計変更だから大きい」は
判定の根拠にならない。だから第2段では**行き先を決める前に全件で実測する**（手順6）。

### 両方を同時に踏むこともある

上の失敗Bと同じセッションで、逆向きの失敗も踏んだ:

| 事例                            | 判断                               | 結果                                                                                                           |
| ------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| スキルdrefの旧API記述の一括変換 | 関連するので自分でスコープを広げた | **誤り**。2エージェント・6ラウンド消費。計画の完了条件は既に満たされており、検証済みの成果物の出荷を止めていた |

「範囲外か」だけで振り分けると両方を間違える。**必要かどうか**と
**どこで対応するか**は別の問いであり、順に判定する（手順3 → 手順6）。

## 鉄則

**既定は「何もしない」。** 応えるほうが例外である。実装・コメント・issue化 の3つすべてに適用する。

指摘が妥当かどうかと、対応が必要かは**別の問い**。妥当な指摘でも据え置いてよい。

## 手順

### 1. 指摘を一覧にする

各指摘について以下を書き出す。ファイル・シンボルが不明な指摘は、この時点で本文から特定する。

- ファイルパス
- 中心となるシンボル（関数・メソッド名）
- 主張されている失敗シナリオ
- レビュアーが付けた severity と verdict（CONFIRMED / PLAUSIBLE）

### 2. 機械判定を回す（LLM の心証に頼らない部分）

各指摘に対して実行する:

```bash
scripts/check-finding.sh <file> [symbol] [base-ref]
```

出力される事実:

- **PR差分内か** → 差分外なら既存の問題。このPRで直す義務はない（未追跡・ステージ済みも差分内に含む）
- **本番の呼び出し元があるか**（テスト除外）→ 0件なら到達不能
- **対応するテストがあるか** → 無ければ修正しても回帰を検出できない

このスクリプトは「直すべきか」を答えない。判断材料を確定させるだけ。

#### 「判定不可」が出たときは自分で確かめる

**判定不可 は結果ではない。** スクリプトが答えを出せなかったという申告である。
この場合は該当項目を LLM が自分でコードを読んで判断すること。**0件・なし として扱ってはいけない。**

判定不可 が出る条件:

- 対象ファイルが呼び出し元検索の対応言語（`.ts` / `.tsx` / `.js`）ではない
- 既知の命名規約に一致するテストファイルが無い（別の配置規約を使っている可能性）
- 指定パスが存在しない / base-ref が見つからない

なお呼び出し元の件数は **上限値**（同名の別シンボルを含みうる）。0件でないことの証拠にはなるが、
正確な件数としては扱わない。

### 3. 第1段: 対応がいるかを判定する

**この段では「どこで対応するか」を考えない。** 必要性だけを見る。
PR差分内・差分外で経路を分けない。**全件がこの段を通る。**

次の2つは並列で、**どちらかに当たれば「対応がいる」**:

- **A. 今壊れているか**
  - 到達不能（呼び出し元0件）→ 壊れていない
  - 安全側の過剰動作（正しさは保たれる）→ 壊れていない
  - 実行すると誤った結果・例外になる → **壊れている**
- **B. 直さないとこのPRの主張が嘘になるか**
  - PR本文やコミットメッセージに書く内容が事実に反する → **当たる**
  - 「あれば良い」だけ → 当たらない。この2つを混同しない

どちらも当たらないなら、**第1段で終了**。第2段には進まない。
行き先は 何もしない（報告のみ）、または手順5の関門を通った場合のみコメント。

判定を締める補助の問い:

- **直さないと何が起きるかを具体的に言えるか。** 言えないなら対応不要。
  「気持ち悪い」「意図に反する」は理由にならない。影響を述べるとき、その前提条件が
  実在するかを確認する（例:「別テナントに影響」ならそのテナント構成が実際にあるか）。
  確認できないなら据え置く。
- **その修正で新しい問題が出ないか。** 構造を変える修正は、それ自体が新しい指摘を生む。
  **LOW / 再現不能な指摘に構造変更で応えてはいけない。** ただし B に当たる指摘は、
  構造変更を伴っても対象外にしない。

### 4. 分類結果を出す

第1段の結果で行き先が決まる。**第2段（手順6）に進むのは「対応がいる」ものだけ。**

第1段が「対応はいらない」:

| 分類                     | 条件                                                                  | 対応                                                           |
| ------------------------ | --------------------------------------------------------------------- | -------------------------------------------------------------- |
| **何もしない**           | 既定。A も B も当たらない                                             | 報告のみ                                                       |
| **コメントで判断を残す** | 壊れていない（到達不能・安全側・設計判断） **かつ** 手順5の関門を通る | 該当箇所に「なぜこうなっているか」を書く。**既定は書かない**側 |

第1段が「対応がいる」→ 第2段（手順6）でどこで対応するかを決める。
**どちらに振り分けるにも、先に実測が必要**（手順6の入口）:

| 分類               | 条件                                                                                      | 対応                                   |
| ------------------ | ----------------------------------------------------------------------------------------- | -------------------------------------- |
| **このPRで対応**   | **既定。** 実測したうえで2基準に当たらない。差分内・差分外を問わない                      | 修正する。再現テストを先に書く         |
| **issue化**        | **例外。** 実測したうえで2基準のいずれかに当たる **かつ** 差分の性質が違う                | 起票（外部アクションなので承認を得る） |

**issue化 は「対応がいる」と決まったものの中の狭い出口である。** 必要性を否定する
経路ではない。必要ないものは第1段で落ちており、issue化 には来ない。

### 5. 「コメントで判断を残す」の前に既存コメントを数える

**コメントは最終手段であり、無料ではない。** 「壊れていないからコメントで残す」を
機械的に適用すると、指摘の数だけコメントが増える。レビュアーは1周で5件も10件も
挙げてくるため、全部に書くと該当箇所がコメントで埋まり、**本当に非自明な1件が埋没する**。

コメントを書けるのは**第1段で「対応はいらない」と判定されたもの**だけで、
そのうえで下の4問を通ったときに限る。第2段（issue化 の見送り）からは流入させない。

書く前に該当箇所の現状を測る:

```bash
sed -n '<開始>,<終了>p' <file> | grep -c '^\s*//'   # コメント行数
sed -n '<開始>,<終了>p' <file> | wc -l              # 総行数
```

そのうえで各指摘に問う:

1. **既存コメントが既に説明していないか** → していれば書かない（重複はノイズ）
2. **「起こらないこと」の説明になっていないか** → 到達不能な経路の解説は、
   読む人に「何か起こるのか」と考えさせるだけ。書かない
3. **コードから導けないか** → 導けるなら書かない
4. **誤読の実害が既に出ているか** → 出ているなら書く（最優先）

**新規追加より既存の訂正を優先する。** レビュアーが誤読した記述があるなら、
それは実害が確認された記述である。追記ではなく**同じ行数で書き換える**。

実測例（2026-08-21、1つのPR）: コメント4件を追加する判断だったが、該当箇所は
46行中13行が既にコメント（28%）で、「400を返す理由」が2箇所で重複していた。
精査の結果 **4件 → 1件（既存コメントの訂正）** に絞った。却下した3件の理由は
「既存が説明済み」「到達不能」「コードから導ける」。

コメント密度が周辺より明らかに高くなるなら、**既存の重複を削る**ことも選択肢に入れる。

### 6. 第2段: どこで対応するかを決める

入るのは第1段で「対応がいる」と決まったものだけ。**既定は「このPRで対応」。**
issue化 は影響範囲が大きいものだけに使う例外の出口である。

**「PR差分外だから」は issue化 の理由にならない。** 差分内・差分外は判定に使わない。

#### 入口: まず実測する（全件必須・飛ばせない）

**この段に入ったものは、行き先を決める前に必ず測る。** 試作して測る:

```bash
scripts/measure-cost.sh [base-ref]
```

試作が無ければ exit 1 で突き返される。**その状態で行き先を判定してはいけない。**
SDKや外部ライブラリの機能なら、型定義を読み、最小の疎通コードを書いて動かす。

実測を「大きいと主張するとき」だけの義務にしてはいけない。**それでは
「大きくない」と見積もりで判断する側が素通りし、実際には大規模な変更を
このPRに引き込む。** 規模の判断は、どちらの方向でも実測値に基づく。

**影響範囲の2基準**（どちらかに当たれば issue化 の候補）:

| 基準                                     | 判定の根拠                                                          |
| ---------------------------------------- | ------------------------------------------------------------------- |
| **① 設計変更が要る（実測して大きい）**   | 入口で測った実測値（`+N/−M行`）。見積もりでは判定しない             |
| **② データ破損・セキュリティ・本番障害** | 影響の性質。規模とは独立に当たりうる（小さい修正でも該当する）      |

実測して小さいと分かれば ① は当たらない。②は規模と無関係なので、
小さくても当たれば issue化 の候補として残る。

**問い: 差分の性質が同じか**

2基準のいずれかに当たっても、これを併せて見る。
同じ性質（同じ移行・同じリファクタの続き）なら、足しても切り分けは汚れない。
性質が違うもの（機能追加の中に設計変更、移行の中にテスト容易性改善）を混ぜると、
レビュアーが2種類の差分を分離できなくなる。**違うなら分ける。**

同じ性質なら、①に当たってもこのPRで対応してよい。

---

**判定**: 順番に通す。**実測は分岐より前にあり、飛ばせない。**

1. **入口で実測する**（この時点では判定しない。数字を出すだけ）
2. 実測値を見てから2基準に当たるか判定する
3. **どちらにも当たらない** → **このPRで対応**（既定）
4. **①または②に当たる** → 差分の性質が違えば issue化。同じなら このPRで対応

実測を経ずに行き先へ分岐する経路は無い。**「大きいから issue化」も
「小さいからこのPRで対応」も、どちらも実測値を根拠にする。**
片方向だけを義務にすると、もう片方が見積もりの抜け道になる。

鉄則（既定は何もしない）は第1段の話であり、この段では変わらない。
第2段は既に「必要」と決まったものの行き先を決めるだけで、必要性を再判定しない。

### 7. issue を作る前に必ず問う

> **これは誰が、いつ着手するか**

答えられないなら、issue にしても放置され「未対応の不具合がある」というノイズを残す。
その場合は**このPRでやってしまうほうが誠実**。第2段に来ているものは既に
「対応がいる」と判定済みであり、issue にしないことは対応しないことを意味しない。

逆に、レビュアーが受け入れ条件まで示してくれた等で拾える形になっているなら issue でよい。

**却下した issue をコメントに振り替えない。** issue化 を見送った既定は
「このPRで対応」であり、コメントではない。コメントを書くのは手順5の関門を通ったときだけ。

### 8. 周回を記録する

スクラッチパッドに判定履歴を残す（`review-triage-round<N>.md`）。

同じ指摘・同じ修正案が別の周回で再登場することがある。前回どう判断したかを
参照できないと、一度却下した案を再検討して一貫性を失う。

記録する内容: 指摘の要約 / 分類 / 判断根拠 / 却下した修正案とその理由 /
第2段に入ったものは全件、入口で測った実測値（`+N/−M行`）。

### 9. 報告して承認を待つ

分類表を提示し、**実行前に承認を得る**。分類したまま修正まで一気に進めない。

報告に含めるもの:

- 分類表（指摘 → 第1段の判定 → 行き先 → 根拠）
- 「このPRで対応」に分類したものの修正方針
- 据え置いたものについて、なぜ対応しないか
- 第2段に入ったものは実測値。issue化 を提案するものは当たった基準も
- 前周回で却下した案が再登場していればその旨

## いつレビューを止めるか

**指摘がゼロになるまで続けない。** 基準は:

> PRの目的が達成され、「壊れている」に分類される指摘がゼロになったら止める

残っているのが「到達不能」「安全側」「設計判断」だけになったら、それは完了状態である。

**逆に、「壊れている」がゼロでも PRの目的が未達なら止めてはいけない。**
指摘を全部処理したことと、PRが主張どおりのものになっていることは別。
第1段のB（PRの主張が嘘になる）に該当する指摘が残っているなら止めない。

## 自分の過剰修正を検出する

新しい指摘が前回の自分の修正に由来する場合、それを明示する。
「LOW の指摘4を直すため構造を変え、その結果 MEDIUM の指摘2が生まれた」という連鎖は、
放置すると無限に続く。連鎖を見つけたら、**元の修正を取り下げる選択肢**も検討する。

コメントに迷ったら: **そのコメントは、指摘が来なくても書いたか。**
書かなかったなら、それは指摘に応えるためのコメントであって、読者のためではない。

## 判定が緩みやすい場面

以下は「壊れている」側に寄せてしまいやすい。機械判定の結果を優先すること。
**ただし 判定不可 は「結果」ではないため、この優先の対象外。**
判定不可 を根拠に「壊れていない」と結論づけてはいけない。

- 指摘の文章が具体的で説得的（説得力は正しさではない）
- 実測やモックでの再現が示されている（再現できても到達経路がなければ壊れていない）
- severity が HIGH と付いている（レビュアーの見立てであり確定ではない）
