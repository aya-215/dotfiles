# レビュー指摘のトリアージ

レビュー指摘を受け取った直後に、**何を実際に直すか**を決める。

## このスキルが必要な理由

レビュアーは「何か見つける」方向に働く。見つからないと仕事をしていないように見えるため、
到達不能なコードや理論上の問題まで拾う。それ自体は悪くないが、**受け取る側が選別しないと
際限がない**。

実測例（1つのPRでレビュー3周・計8件）:

| 種類                     | 件数 |
| ------------------------ | ---- |
| 実際に壊れていた         | 3    |
| 到達不能                 | 1    |
| 安全側の過剰動作         | 1    |
| 設計判断（バグではない） | 1    |
| 理論上のみ（再現不能）   | 1    |
| **前の修正が生んだ**     | 1    |

壊れていたのは3件。しかも1件は過剰修正の副産物だった。
LOW の指摘を直すために構造を変え、それが MEDIUM の指摘を生んだ。

### 逆方向の失敗もある

絞る方向だけが正解ではない。同じセッションで両方を踏んだ実測例（2026-08-21）:

| 事例                            | 判断                                                                | 結果                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| トランスポート配線の切替        | 「設計変更で規模が大きい」と見積もり、スコープ外として別issueを提案 | **誤り**。問い直されて試作したら**実質15行**で、PRの主張（仕様準拠）がこれ無しには成立しなかった               |
| スキルdrefの旧API記述の一括変換 | 関連するので自分でスコープを広げた                                  | **誤り**。2エージェント・6ラウンド消費。計画の完了条件は既に満たされており、検証済みの成果物の出荷を止めていた |

前者は**実測せずに見積もりで却下した**のが原因。後者は**PRの主張に不要なものを足した**のが原因。
「範囲外か」だけで振り分けると両方を間違える。

## 鉄則

**既定は「何もしない」。** 直すほうが例外である。

指摘が妥当かどうかと、このPRで直すべきかは**別の問い**。妥当な指摘でも据え置いてよい。

## 手順

### 1. 指摘を一覧にする

各指摘について以下を書き出す。ファイル・シンボルが不明な指摘は、この時点で本文から特定する。

- ファイルパス
- 中心となるシンボル（関数・メソッド名）
- 主張されている失敗シナリオ
- レビュアーが付けた severity と verdict（CONFIRMED / PLAUSIBLE）

### 2. 機械判定を回す（LLM の心証に頼らない部分）

各指摘に対して実行する:

```bash
scripts/check-finding.sh <file> [symbol] [base-ref]
```

出力される事実:

- **PR差分内か** → 差分外なら既存の問題。このPRで直す義務はない（未追跡・ステージ済みも差分内に含む）
- **本番の呼び出し元があるか**（テスト除外）→ 0件なら到達不能
- **対応するテストがあるか** → 無ければ修正しても回帰を検出できない

このスクリプトは「直すべきか」を答えない。判断材料を確定させるだけ。

#### 「判定不可」が出たときは自分で確かめる

**判定不可 は結果ではない。** スクリプトが答えを出せなかったという申告である。
この場合は該当項目を LLM が自分でコードを読んで判断すること。**0件・なし として扱ってはいけない。**

判定不可 が出る条件:

- 対象ファイルが呼び出し元検索の対応言語（`.ts` / `.tsx` / `.js`）ではない
- 既知の命名規約に一致するテストファイルが無い（別の配置規約を使っている可能性）
- 指定パスが存在しない / base-ref が見つからない

なお呼び出し元の件数は **上限値**（同名の別シンボルを含みうる）。0件でないことの証拠にはなるが、
正確な件数としては扱わない。

### 3. 3つの問いで分類する

機械判定の結果を踏まえ、各指摘に順に問う。

**問い1: 今壊れているか**

- 到達不能（呼び出し元0件）→ 壊れていない
- 安全側の過剰動作（正しさは保たれる）→ 壊れていない
- 実行すると誤った結果・例外になる → 壊れている

**問い2: 直さないと何が起きるかを具体的に言えるか**

言えないなら直す必要はない。「気持ち悪い」「意図に反する」は理由にならない。
影響を述べるとき、その前提条件が実在するかを確認する（例:「別テナントに影響」なら
そのテナント構成が実際にあるか）。確認できないなら据え置く。

**問い3: この修正で新しい問題が出ないか**

構造を変える修正は、それ自体が新しい指摘を生む。
**LOW / 再現不能な指摘に構造変更で応えてはいけない。**

ただしこれは「構造変更は避けよ」ではない。**PRの主張そのものに関わる指摘は、
構造変更を伴っても対象外にしない**（手順6で判定する）。拡大解釈して、
やるべき変更まで却下しないこと。

### 4. 分類結果を出す

| 分類                     | 条件                                                                                        | 対応                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **直す**                 | 壊れている **かつ**（PR差分内 **または** 手順6の関門を通る）                                | 修正する。再現テストを先に書く                                 |
| **コメントで判断を残す** | 壊れていない（到達不能・安全側・設計判断） **かつ** 手順5の関門を通る                       | 該当箇所に「なぜこうなっているか」を書く。**既定は書かない**側 |
| **issue化**              | 壊れている **かつ** PRスコープ外 **かつ** 手順6で据え置きと判定 **かつ** 着手者が想定できる | 起票（外部アクションなので承認を得る）                         |
| **何もしない**           | 上記いずれにも当たらない                                                                    | 報告のみ                                                       |

### 5. 「コメントで判断を残す」の前に既存コメントを数える

**コメントは無料ではない。** 「壊れていないからコメントで残す」を機械的に適用すると、
指摘の数だけコメントが増える。レビュアーは1周で5件も10件も挙げてくるため、
全部に書くと該当箇所がコメントで埋まり、**本当に非自明な1件が埋没する**。

書く前に該当箇所の現状を測る:

```bash
sed -n '<開始>,<終了>p' <file> | grep -c '^\s*//'   # コメント行数
sed -n '<開始>,<終了>p' <file> | wc -l              # 総行数
```

そのうえで各指摘に問う:

1. **既存コメントが既に説明していないか** → していれば書かない（重複はノイズ）
2. **「起こらないこと」の説明になっていないか** → 到達不能な経路の解説は、
   読む人に「何か起こるのか」と考えさせるだけ。書かない
3. **コードから導けないか** → 導けるなら書かない
4. **誤読の実害が既に出ているか** → 出ているなら書く（最優先）

**新規追加より既存の訂正を優先する。** レビュアーが誤読した記述があるなら、
それは実害が確認された記述である。追記ではなく**同じ行数で書き換える**。

実測例（2026-08-21、1つのPR）: コメント4件を追加する判断だったが、該当箇所は
46行中13行が既にコメント（28%）で、「400を返す理由」が2箇所で重複していた。
精査の結果 **4件 → 1件（既存コメントの訂正）** に絞った。却下した3件の理由は
「既存が説明済み」「到達不能」「コードから導ける」。

コメント密度が周辺より明らかに高くなるなら、**既存の重複を削る**ことも選択肢に入れる。

### 6. 「スコープ外」と判定する前の4つの問い

**「PR差分外だから」は却下の理由にならない。** 入口で振り分けず、以下を通してから決める。

**問い1: コストを実測したか（却下する前の義務）**

見積もりで「規模が大きい」と判断してはいけない。**試作して測る。**
SDKや外部ライブラリの機能なら、型定義を読み、最小の疎通コードを書いて動かす。
実測せずに「設計変更だから」と却下したものが、実際には十数行だったことがある。

これは「やる理由」ではなく制約である。**測らずに却下してはいけない**、という意味。

**問い2: やらないとこのPRの主張が嘘になるか**

なるなら**やる**。PR本文やコミットメッセージに書く内容が事実に反するなら、
それはスコープの問題ではなく、PRが未完成だということ。

「あれば良い」だけならやらない。この2つを混同しない。

**問い3: 差分の性質が同じか**

同じ性質（同じ移行・同じリファクタの続き）なら、足しても切り分けは汚れない。
性質が違うもの（機能追加の中に設計変更、移行の中にテスト容易性改善）を混ぜると、
レビュアーが2種類の差分を分離できなくなる。**違うなら分ける。**

**問い4: 誰がいつ着手するか答えられるか**

答えられないなら、issue にしても放置される。その場合は**やってしまうほうが誠実**。
逆に、レビュアーが受け入れ条件まで示してくれた等で拾える形になっているなら issue でよい。

---

**判定**: 問い2が Yes なら、問い1で測ったコストが妥当な範囲であれば**やる**。
問い2が No なら、問い3・4 で issue化 か 何もしない を決める。

鉄則（既定は何もしない）は変わらない。この4問は**例外を通すための関門**であって、
既定を反転させるものではない。

### 7. issue を作る前に必ず問う

> **これは誰が、いつ着手するか**

答えられないなら作らない。到達不能な不具合や、実運用データがないと決められない設計判断は
issue にしても着手されず、「未対応の不具合がある」というノイズを残すだけ。

**代わりにコードコメントで判断を残す。** issue は探さないと読まれないが、
コメントは次にそのコードを読む人がその場で読む。

### 8. 周回を記録する

スクラッチパッドに判定履歴を残す（`review-triage-round<N>.md`）。

同じ指摘・同じ修正案が別の周回で再登場することがある。前回どう判断したかを
参照できないと、一度却下した案を再検討して一貫性を失う。

記録する内容: 指摘の要約 / 分類 / 判断根拠 / 却下した修正案とその理由。

### 9. 報告して承認を待つ

分類表を提示し、**実行前に承認を得る**。分類したまま修正まで一気に進めない。

報告に含めるもの:

- 分類表（指摘 → 分類 → 根拠）
- 「直す」に分類したものの修正方針
- 据え置いたものについて、なぜ直さないか
- 前周回で却下した案が再登場していればその旨

## いつレビューを止めるか

**指摘がゼロになるまで続けない。** 基準は:

> PRの目的が達成され、「壊れている」に分類される指摘がゼロになったら止める

残っているのが「到達不能」「安全側」「設計判断」だけになったら、それは完了状態である。

**逆に、「壊れている」がゼロでも PRの目的が未達なら止めてはいけない。**
指摘を全部処理したことと、PRが主張どおりのものになっていることは別。
手順6の問い2に該当する指摘が残っているなら、範囲外でも対応する。

## 自分の過剰修正を検出する

新しい指摘が前回の自分の修正に由来する場合、それを明示する。
「LOW の指摘4を直すため構造を変え、その結果 MEDIUM の指摘2が生まれた」という連鎖は、
放置すると無限に続く。連鎖を見つけたら、**元の修正を取り下げる選択肢**も検討する。

## コメントの過剰も過剰修正の一種

「直す」を絞れても、**却下した指摘のぶんだけコメントを足せば結果は同じ**になる。
どちらも「レビュアーに応えた形を作る」動機から来る。手順5の関門は「直す」側の
鉄則（既定は何もしない）をコメントにも適用するためにある。

判定に迷ったら: **そのコメントは、指摘が来なくても書いたか。**
書かなかったなら、それは指摘に応えるためのコメントであって、読者のためではない。

## 判定が緩みやすい場面

以下は「壊れている」側に寄せてしまいやすい。機械判定の結果を優先すること。
**ただし 判定不可 は「結果」ではないため、この優先の対象外。**
判定不可 を根拠に「壊れていない」と結論づけてはいけない。

- 指摘の文章が具体的で説得的（説得力は正しさではない）
- 実測やモックでの再現が示されている（再現できても到達経路がなければ壊れていない）
- severity が HIGH と付いている（レビュアーの見立てであり確定ではない）
