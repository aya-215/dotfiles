# PR対話レビュー

PRをClaudeと一緒に読み、コードの理解を深めるためのスキル。
Claudeが能動的に進行役となり、各フェーズで必ず理解確認を行う。

## 引数

$ARGUMENTS

- 引数なし: **現在ブランチに紐づくPRを対象にする**（デフォルト）
- PR番号のみ: `123`
- PR番号＋リポジトリ: `123 owner/repo`
- GitBucket の PR の URL（`http://192.168.208.80:8080/gitbucket/<owner>/<repo>/pull/<番号>`）

レビュー済みの PR について「レビュー返ってきた」「修正来た」と言われたら、Step 0〜6 ではなく末尾の「再レビュー」節に従う。

## Iron Law

```
理解確認なしに次のフェーズへ進まない。
ユーザーが y を返すまで、絶対に先へ進むな。
```

## 確認ルール

AskUserQuestion は使わない。直前の本文が描画されず消える不具合（claude-code#74260 系）が Opus でも再発したため。

- 毎フェーズの最後は、**本文末尾の質問文で終えて止まる**
- 質問文には次に進む先と合図を必ず書く（例: 「気になる点があれば書いてください。問題なければ y で 3-B へ進みます」）
- 口調は本文・質問文ともに です・ます調 で統一する。下記テンプレの文言は例であり、口調ごと従う
- 進む合図は `y`。「次」「OK」「進む」等も合図として受け付ける。合図があるまで次のフェーズへ進まない
- ユーザーが質問・深掘りをした場合 → 答えた後、**再び質問文で締めて止まる**（自動で次へ進まない）
- **1メッセージ = 1質問のみ**
- **例外**: ユーザーが自分の論点・疑問を持ち込んだときは、確認を挟まずまず追従する。議論・検証・意見表明の途中に確認を差し込まない（詳細は「検証と対話のバランス」節）。一段落してから質問文で締める

## The Process

### Step 0: PR特定

優先順位: **明示指定 > 現在ブランチ > 聞く**

1. 引数でPR番号が指定されていればそれを使う
2. 引数なしの場合、`gh pr view`（番号なし）で**現在ブランチに紐づくPRをそのまま対象にする**。確認の質問は出さない
3. 現在ブランチにPRが無く `gh pr view` が失敗したときだけ、本文の質問文でPR番号を聞いて止まる：

```
「現在のブランチに PR が見つかりませんでした。レビューする PR 番号を教えてください（リポジトリが違う場合は owner/repo も）」
```

### Step 1: PR情報取得

先に `git remote -v` でリモートを見る。GitBucket なら `gh` は使えないので、末尾の「GitBucket の場合」の対応表に読み替える。

```bash
# 引数なし（現在ブランチのPR）
gh pr view
gh pr diff

# PR番号指定の場合
gh pr view <PR番号>
gh pr diff <PR番号>

# リポジトリを指定する場合
gh pr view <PR番号> --repo <owner>/<repo>
gh pr diff <PR番号> --repo <owner>/<repo>
```

続けて、PR の土台が古くないかを確かめる。別の PR の上に積んだ PR や、ベースが先に進んだ PR では、マージ済みの修正を巻き戻すことがある。

```bash
git -C <repo> fetch origin <base> <head>
git -C <repo> merge-tree --write-tree --name-only origin/<base> origin/<head>   # 2行目以降にファイル名が出たら衝突
git -C <repo> diff origin/<base> origin/<head> --stat                            # PR 固有の変更だけになっているか
```

衝突や、ベース側の最近の修正を消す差分があれば、Step 2 の「PRが自分で認めている未検証の点」の後に事実として書く（所見としての評価は Step 5 で行う）。

### Step 2: PR全体の解説（質問→納得までのループ）

最初に、PRを読んでいない人が1画面で全体を掴める解説を出す。ファイル単位ではなく「何を・どう動くか・なぜそう作ったか」の単位で書く。
ここではレビュー所見・設計論点の候補は**出さない**（Step 3 で出す）。

以下の見出しで、平易な言葉で簡潔に書く：

1. **何をするPRか**: 1〜2文。値の出どころ等を対比したいときは小さな表を使ってよい
2. **処理の流れ**: 番号付きで3〜6ステップ。分岐条件（「〜のときだけ」「〜なら書かない」）も流れの中に書く
3. **設計の要点**: 3〜4個。各1〜2行で「何をしたか＋その理由」
4. **PRが自分で認めている未検証の点**: PR本文の「未検証」「範囲外」等から拾う。無ければ省略

例：

```
## PR #817 のまとめ

**何をするPRか**
shifton で会話を1ターン保存したあと、そのターンに「誰が・どの車について聞いたか」を追記します。
| 項目 | 値の取り方 |
|---|---|
| ユーザーグループ名 | ログイン情報（GetUserInfo）から取る |
| メーカー／車名／型式／年式 | 出典リンクの itemID で 00002 を引き直す |

**処理の流れ**
1. /api/chat/save がターンを保存し、すぐに応答を返す
2. 応答後（after()）、shifton のときだけ記録処理を動かす
3. 回答文の URL から volumeName=00002 の itemID を拾う
4. 車両が1台なら 00002 から4項目を取る。0台や複数台なら車両は書かない
5. 値のある項目だけを書き込む

**設計の要点**
- 値はサーバー側で取り直す: クライアント由来の文字列は書かない
- 応答を待たせない: MCP 2往復を応答後に回す
- 失敗しても会話の保存は壊さない: warn 1行だけ

**PRが自分で認めている未検証の点**
- 実際のエージェント回答・after() 経由の実行では未確認
```

解説の後は、本文末尾で次のように促して止まる：

```
質問があれば何でもどうぞ。納得できたら y で設計論点の一覧に進みます。
```

- ユーザーの質問には検証ガードに従って裏取りしてから答える。答えた後も同じ一文で促して止まる
- ユーザーが y 等で満足を示すまで Step 3 に進まない
- 手順書・skill・プロンプトなど文書の PR では、以降の解説も「追加された文の引用 → 平たく言うと → 由来（PR が挙げる実例）」の順で書く。分析から入らない

### Step 3: 設計判断・実装意図の解説

**重心は「コードが何をしているか」ではなく「なぜこう作ったか」に置く。** ユーザーが最も知りたいのは実装の意図・設計判断であることが多い。

#### Step 3-0: 設計判断の一覧提示（必須・最初に行う）

個別の解説に入る前に、**このPRで説明すべき設計判断を全て箇条書きで提示する**。

- 各トピックは**1行（見出しのみ）**。中身はここでは書かない
- 番号を振る（3-A, 3-B, 3-C, ...）
- **この一覧が Step 3 の終了条件になる。** 全トピックを消化するまで Step 4 へ進まない
- 一覧提示後は確認を挟まず、そのまま 3-A に入る

一覧の例：

```
このPRの設計判断は5つあります。順に見ていきます。

- 3-A: なぜ生パラメータでなく「モード」なのか
- 3-B: 既定値を card にした理由
- 3-C: detail が sortInfo を丸ごと含む理由
- 3-D: ツール分割の判断
- 3-E: 縮退検出の設計
```

#### Step 3-A 以降: 1トピックずつ解説

各トピックで説明する内容：
1. **なぜこの設計・実装を選んだか**（意図・背景）
2. **他にどんな選択肢があり、なぜそれを採らなかったか**（トレードオフ）
3. その判断が妥当か、過剰／不足はないか

**分量規定（厳守）:**

- **1メッセージ = 1トピックのみ。5〜10行に収める。**
- 複数の設計判断を1メッセージに詰め込まない
- トピックを消化するたびに、末尾に**残りを1行で示す**（例: `残り: 3-C / 3-D / 3-E`）
- 長くなる場合はトピックを分割する。1メッセージを長くしない

**設計判断はファイル境界に縛られず横断的に扱う。** 1つの設計判断が複数ファイルにまたがることは多い（例: ツール層＋サービス層＋登録集約点）。ファイル単位で区切らず、意図の単位でまとめる。

コードの逐次的な仕組み解説は、**意図を理解するのに必要な範囲に絞る**。「このファイルを1行ずつ丁寧に」は必須ではない。ユーザーが「このファイル詳しく」と求めたときだけ深掘りする（オプション）。

→ **[質問で締める]** 「この設計判断の意図は伝わりましたか？気になる点や深掘りしたい所があれば書いてください。問題なければ y で 3-B へ進みます」（進む先は次のトピック。最後のトピックなら Step 4）

一覧の全トピックを消化するまで繰り返す。次のトピックに進む前に必ず確認する。

### Step 4: 影響範囲の説明

- 他のコードへの波及
- 外部サービスやAPIへの影響
- 破壊的変更の有無

→ **[質問で締める]** 「影響範囲について気になる点があれば書いてください。問題なければ y で Step 5 へ進みます」

### Step 4.5: 影響コード追跡

変更されたコードの呼び出し元・依存先を追跡する：
- 変更された関数/コンポーネントを使用している箇所をgrepで検索
- 型変更がある場合、影響を受ける型の利用箇所を確認
- APIの変更がある場合、クライアント側への影響を確認

影響が見つかった場合はユーザーに報告し、Step 5のレビュー観点に含める。
影響がない場合はその旨を伝えて次へ進む。

### 検証ガード（所見を出す前に必須）

ユーザーの疑問への回答・レビュー所見・設計上の指摘を述べる前に、必ず一次情報で裏取りする：

1. 前提（設計書・引き継ぎ・**ユーザーの推測・自分の直感・相手への同調**）を鵜呑みにしない
2. 本体コード・実データ・実挙動で確認してから結論を出す
3. 各所見を **CONFIRMED / PLAUSIBLE / REFUTED** に分類して提示する
   - CONFIRMED: 一次情報で確認済み
   - PLAUSIBLE: もっともらしいが未確認（「まだ未確認だが」と明示）
   - REFUTED: 確認したら誤りだった

裏取り前の推測を先に述べない。特に、ユーザーの疑問に反射的に同調して未検証の所見を出さない（「ご指摘の通り」の前に確認する）。

### 検証と対話のバランス

検証ガードで確認を増やしすぎないための運用ルール：

- **裏取り（コード確認・実データ検証・advisor相談）は許可を求めず、その場で実行してよい。** 検証のたびに確認を挟まない
- ユーザーが自分の論点・疑問を持ち込んだら、フェーズ確認を挟まず**まずそれに追従する**
- **議論・検証・意見表明の途中では、確認を差し込まない。** 追従の一連（裏取り→分類付き所見の提示）が完了してから、確認フェーズに戻す
- 論点が一段落したら、元のフェーズ進行に戻す（追従したうえで戻す）

### Step 5: レビュー観点の整理

以下のチェックリストに基づき、変更内容を評価する：

**チェック観点:**
- セキュリティ: 入力検証、認証・認可、シークレット漏洩
- パフォーマンス: N+1、不要な再計算、メモリリーク
- エッジケース: null/undefined、空配列、境界値、並行処理
- テスト: 変更に対するテストの有無、異常系カバレッジ
- 互換性: 破壊的変更、既存APIへの影響
- 手順書・skill の PR: 追加したルールが、PR の挙げる失敗の原因に効いているか（症状だけを塞いでいないか）。参照している skill・ファイル・用語が配布先に実在するか（grep で確かめる）

**重要度分類:**
- Critical: マージすべきでない問題
- Important: マージ前に対応が望ましい問題
- Nit: 改善提案（マージには影響しない）

**必須: ユーザーが持ち込んだ論点を再掲する**

対話中にユーザーが出した疑問・違和感は、**結論が出たものも含めて Step 5 の所見として必ず再掲する**。
ユーザーが自分で気づいた点こそレビューの成果物であり、対話の流れで消費して終わらせない。

- 検証の結果 CONFIRMED になったもの → 重要度を付けて所見に含める
- REFUTED になったもの → 「検証したが誤りだった」と結論を明記して含める
- 判断が割れて決着しなかったもの → **「設計論点」として重要度なしで記録する**（Critical/Important/Nit を付けない）

問題が見つかった場合は重要度を付けて提示する。
問題がない場合は「確認した結果、特に問題は見つからなかった」と明示する。
良い点（意図的な設計判断、コード品質の向上等）も挙げる。

→ **[質問で締める]** 「レビュー観点で気になるものはありましたか？ほかに確認したいことがあれば書いてください。問題なければ y でサマリーへ進みます」

### Step 6: レビューサマリー

対話を通じて得られた内容を以下の形式で整理する：

1. **良かった点**: 対話中にユーザーが評価した点 + Step 5の良い点
2. **確認した点**: Step 3-4で理解確認できた内容
3. **気になった点・質問**: Step 5の問題点（重要度付き）
4. **レビュー判定の推奨**: Approve / Request Changes + 理由

→ **[質問で締める]** 「サマリーを整理しました。修正する点はありますか？このままレビューコメントを書く場合は /write-review-comment を使ってください」

## 再レビュー（レビューへの返信・修正コミットの確認）

「レビュー返ってきたので確認して」「修正来た」で入る。分析と報告だけを行い、返信の投稿はしない。
ebase-portal-chat・ebase-middleware-mcp・eb-api-extended の PR は review-aiebase-pr の再レビューを使う。

1. **返信と新しいコミットを取る。** PR のコメント一覧から、自分のレビュー以降の返信を読む。前回の付録に書いた対象 commit（「対象はブランチ `…`（<sha>）」）から先のコミットを出し、差分を読む
   ```bash
   git -C <repo> fetch origin <base> <head>
   git -C <repo> log --oneline <前回のsha>..origin/<head>
   git -C <repo> show <新しいsha> -- <関係するパス>
   ```
2. **前回の指摘ごとに対応表を作る。** 1行1指摘で「✅ 反映 / △ 一部 / ❌ 未対応 / 見送り（理由付き）」と、確かめた根拠（ファイル:行・テスト名）を書く。作者の返信の要約ではなく、差分で確かめた結果を書く
3. **片付けの漏れを grep する。** 削除・改名した名前（ファイル名・欄の名前・手順番号・skill 名）が残っていないかを、PR ブランチ全体で検索する
4. **土台を確かめ直す。** Step 1 の `merge-tree` を、最新のベースに対してもう一度流す
5. **前回の自分のコメントが崩れていないかを見る。** 投稿したコメントを取得し、制御文字（`\x1b` など）・つながった箇条・誤字がないかを見る。崩れていたら報告する（直すかはユーザーが決める）
6. **見送りの判断を評価する。** 作者が見送った指摘は、その理由が成り立つかを一次情報で確かめ、妥当なら妥当と書く
7. 最後に、承認してよいかの所見と、確認できなかったこと（テスト未実行など）を書き、「返信の文面が必要なら案を作ります」で締める。文面は write-review-comment の型D に従う

## GitBucket の場合

`git remote -v` が社内 GitBucket（`192.168.208.80:8080/gitbucket`）を指すとき、`gh` の代わりに次を使う。

| やること | GitHub | GitBucket |
|---|---|---|
| PR の概要 | `gh pr view <番号>` | `mcp__gitbucket__gitbucket_get_pr`（owner・repo・number） |
| コメント・返信 | `gh pr view <番号> --comments` | `mcp__gitbucket__gitbucket_list_comments` |
| 差分 | `gh pr diff <番号>` | `git -C <repo> fetch origin <base> <head>` → `git -C <repo> diff origin/<base>...origin/<head>` |
| 変更ファイル | `gh pr diff --name-only` | 上の `git diff` に `--stat` |

MCP のツールは最初は deferred なので、ToolSearch（`select:mcp__gitbucket__gitbucket_get_pr,mcp__gitbucket__gitbucket_list_comments`）で読み込んでから呼ぶ。GitBucket の PR にはレビュー状態（Approve / Request Changes）が無く、コメントだけになる。

## gh CLI Reference

```bash
# PR概要（番号省略＝現在ブランチのPR）
gh pr view
gh pr view <PR番号>

# diff（全体）
gh pr diff
gh pr diff <PR番号>

# 変更ファイル名のみ
gh pr diff --name-only
```

認証エラーが出た場合は `gh auth switch` でアカウントを切り替える。
