# 内容チェックの観点

形式（F01〜F17）はスクリプトが判定する。ここは**LLMが一次情報を読んで判定する項目**だけを置く。
要件・ルーブリック・雛形の本文は転記しない（正本が更新されたときに追従できなくなるため）。毎回、下の「正本」から読む。

## 正本（毎回読む）

| 何を | どこ |
|---|---|
| 提出物ごとの要件 | `closes #N` の Issue 本文（MCP `gitbucket_get_issue`） |
| フェーズの提出物定義 | `submissions/<track>/phase<N>-*/README.md`（head 側） |
| 既知のカリキュラム不備（繰り返し報告しない） | `references/known-curriculum-issues.md` |
| 到達目標・カリキュラム上の説明 | カリキュラム本体。agent: `http://192.168.208.80:8080/gitbucket/AI_dev/ai-team-docs/raw/main/docs/training/agent-onboarding/README.md` ／ infra: 同 `infra-onboarding/README.md`（curl で認証なし取得可） |
| ルーブリック | agent: `progress/agent/checklist.md` の `## 評価軸` 節 ／ infra: `README.md` の「評価軸」 |
| レビューの流れ・運用ルール | `README.md`「使い方（メンター）」「日々の流れ」、`docs/pr-checklist.md` の「補足」 |

## 一次情報の取り方

- 公式docs（例: `https://code.claude.com/docs/en/permission-modes`）は WebFetch の結果が大きくファイルに退避される。退避先を grep して該当節を抜く
- 公開 GitHub リポジトリの履歴は `gh api repos/<owner>/<repo>/commits?path=<path>` で追う（削除・改名はコミットメッセージで確かめる）

## 内容の観点

| ID | 観点 | 判定のしかた |
|---|---|---|
| C1 | Issue 要件の網羅 | Issue 本文から**内容の要求**を1つずつ抜き出し、提出物のどの節が応えているかを対応づける。提出先・ブランチ・PR本文・ラベルなど手続きの要求は F 側で見るので含めない |
| C2 | Issue の太字（`**…**`）の強調点 | 太字は出題者が「ここを外すな」と示した点。C1 とは別に個別に判定する（表示では、C1 の行と中身が同じならその行にまとめる）。ただし課題の理由・背景を述べた太字（例: 「これがエージェントの入出力の型そのもの」）は説明の要求ではないので、未達の根拠にしない |
| C3 | カリキュラムの到達目標 | 該当フェーズの到達目標・本文の説明と突き合わせる。カリキュラムの言い回しの丸写し（自分の言葉でない）もここで見る |
| C4 | 技術的記述の正確さ | C1・C2・C5 に関わる記述を優先し、一次情報（公式docs・実リポジトリ・実コード・実機）で裏取りする。それ以外は怪しいものだけ見る。カリキュラムの記述と食い違ったら、カリキュラム側が古い可能性も確かめる。どの一次情報にも出てこない固有名詞は「未裏取り・PLAUSIBLE」とし、受講者への問いにする |
| C5 | [x] にした項目の水準 | チェックリストで [x] にした項目が、提出物の内容で本当に「説明できる」水準か。C1〜C4 の結果から判定する |
| C6 | 自己評価の妥当性 | ★は「★★★を基本とし、Issue の要件を満たせなかった分だけ下げる」で見る。メンターが受講者に口頭で伝えた基準で、`checklist.md` の評価軸・`pr-checklist.md` の「★★☆止まり」より優先する（文書側は未反映）。★はPRを出した時点の提出物で付け、レビュー後の修正で付け直さない。理由は要件の網羅ではなく、Issue を見て提出物をどう書くと判断したか（何を書き、何を確かめたか）が具体的に書かれているかを判定する。下げたなら、どの要件が足りないかも見る。★は口頭で伝える運用なので、返すなら口頭用の一言にする |
| C7 | 「詰まった点・聞きたいこと」への回答 | 質問ごとに一次情報で答えを用意する。原因がカリキュラムや配布物の不備なら「メンター側の作業」として分けて書く |
| C8 | Nit | 用語の不正確さ・説明のない固有名詞・表記の揺れ。マージ判断には影響させない |

## 指摘の重さ

最初の判定で厳しく付け、メンターがあとから削る、という流れを繰り返した（#117〜#121）。最初から次の基準で分ける。

| 重さ | 何を入れるか |
|---|---|
| 依頼（マージ前に直してもらう） | Issue に書かれた内容要件が欠けている、または一次情報で CONFIRMED の誤りがある。2件を超えそうなら重いものから絞る（#117 は主1件＋その他2件、#119 は2件だった） |
| 任意（マージを止めない） | 説明が浅い・理由が書かれていない・より良い書き方がある。最大2件 |
| 返さない | 次のフェーズで扱う内容／「誤解しているかもしれない」という推測だけの指摘／Nit（C8）／再レビューで初めて気づいた点 |

## コメントの型（PR #117〜#121 で実際に投稿したもの）

- 1行目は `@tamaki.s`。次に良かった点を1〜2文（「〜具体的に書かれていてわかりやすいと思いました！」）
- 依頼は数を先に言い（「2点ほど、もう少し説明を詳しく書いていただきたい場所があります」）、1点ごとに**理由**（「issueで〜を書くように指示があるので」）と**何を書けばよいか**を具体的に書く。問いの形にはしない
- 補足の説明は**答えまで書く**。理解を確かめる抽象的な問いは伝わりにくい（#121）
- 承認は「確認しました！」＋良かった点1文＋「LGTMです！」。指摘が無ければ「okです！必要な項目を適切に書けていると思います！」程度で足りる
- 承認時に補足を添えるなら、なぜそうなっているか（答え）と、今後意識してほしいことを短く
- 形式の漏れは**該当行を引用して**具体的に返す（例: チェックリストの行をそのまま貼って「チェックが入っていなかったので確認お願いします」）
- 自己評価の★は口頭で伝える。#117 では PR 上で★の付け方を書いたが、#118 以降は「直接話させてください」として口頭に移した
- `docs/pr-checklist.md`: 確認事項に全部チェックが無いPRはレビューしない（秘匿情報の混入は取り返しがつかないため）
