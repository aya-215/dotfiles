# 研修提出物PRのレビュー

tamaki-ai-training の提出PRについて、**形式はスクリプトで、内容は一次情報で**判定し、「Issue と PR の内容 → 気になる点 → 返す内容」の3つだけを短く出す。
投稿はしない。

## 手順

1. **PRを特定する**: 引数の番号を使う。無ければ `mcp__gitbucket__gitbucket_list_prs`（open）で、1本ならそれ、複数なら本文末尾の質問で番号を聞いて止まる
2. **メタ情報を取る**（MCP）
   - `gitbucket_get_issue` を**PR番号で**呼ぶ → `labels` と最新の `body`。`get_pr` の body は古いことがあるので使わない
   - `gitbucket_get_pr` → `head` / `base`
   - 本文の `closes #N` の Issue を**すべて** `gitbucket_get_issue` → `labels` / `body`
   - `gitbucket_list_comments` をPR番号で呼ぶ → メンターのコメントに**依頼**があり、そのコメントより後に head へコミットが積まれていれば**再レビュー**（下の「再レビュー」）。「明日返します」「確認しました」のような依頼の無いコメントは数えない
3. **meta.json を Write ツールで scratchpad に書く**（形式は `scripts/check_submission.py` の docstring。Issue が複数なら `issue` を配列にする）。body は MCP の値を改変せずに入れる
4. **形式チェックを実行する**
   ```bash
   python3 ~/.claude/skills/review-training-submission/scripts/check_submission.py \
     --repo-dir <tamaki-ai-training の clone> --meta <meta.json>
   ```
   - clone に `refs/review/head` / `refs/review/base` を fetch する（作業ツリーは触らない）
   - 出力はユーザーに貼らない。FAIL / WARN / UNKNOWN の行だけを「気になる点」に理由付きで書く
   - マージ済みPRを見直すときは `--merge-commit <sha>` を足す
5. **内容チェック**: `references/criteria.md` の正本を読み、C1〜C8 を判定する。提出物は `git show refs/review/head:<path>` で読む。指摘の重さは criteria.md の「指摘の重さ」で決める
6. **取り直し**: 結論の直前に `get_issue`（本文）と `git ls-remote origin <head>`（head SHA が `refs/review/head` と同じか）を確認する。変わっていたら 2 からやり直す
7. **1段目を出して止まる**（下の出力形式）

## 再レビュー（修正が push された後）

- 見るのは、**直近の依頼コメントで依頼した点が満たされたか**だけ。「Issue と PR の内容」の表を `| 依頼した点 | 修正後の対応 |` に替える
- 新しい指摘は足さない（前回言わなかった点を後から言わない）。例外は形式チェックの FAIL と秘匿情報
- 依頼がすべて満たされていれば、推奨は「マージ可」にする

## 出力形式

判定（手順1〜6）は最初に全部済ませ、表示は次の3段に分けて**この順に1段ずつ**出す。判定の表（形式チェック・C1〜C8）とカリキュラム側の修正候補は出さない。判定の結果は「気になる点」にだけ反映する。

進め方:
- 1回の返答で出すのは1段だけ。段の最後は「次は〈次の段の名前〉です」の1行で止める（どれを出すかは聞かない）
- ユーザーが質問・反論したら、その段のまま答える。答えで判定が変わったら（指摘を取り下げる、依頼を任意にする等）以後の段に反映する
- 「ok」「次」など先へ進む返事が来たら、次の段を出す
- 3段目の返す内容は、1・2段目でのやり取り（取り下げた指摘・足した補足・決めた言い回し）を反映して作る

### 1段目: Issue と PR の内容

- `| Issue の要件 | PR の対応 | 判定 |` の表。Issue の内容要件1つにつき1行（C1）
  - Issue で太字の語は、要件の文の中で同じ語を太字にする（C2。例: 「写経で書いた Runnable 合成1本（**手書き**）」）
  - 「PR の対応」は30字程度の1文。「判定」は `できている` / `一部` / `無い`
- PR の中身: 追加・変更したファイルと、`| 節 | 内容 |` の表（節ごとに1行、最大6行）
- 推奨を1行: マージ可 / 修正依頼後マージ / 差し戻し と、理由を一言

### 2段目: 良い点と気になる点

- 良い点: 1〜2点。どの節の何が良いかを具体的に（3段目のコメントの書き出しになる）
- 気になる点: 「指摘の重さ」（criteria.md）で `依頼` / `任意` になった点を、1点につき1〜2行で**理由と一緒に**書く。頭に `依頼` / `任意` を付ける
- 形式チェックの FAIL / WARN / UNKNOWN、内容判定の 部分 / 未達 / 不正確 もここに理由付きで入れる
- 原因がカリキュラムや配布物の側にあるなら（例: Issue が求める物の題材がどこにも無い）、その旨を理由に添える
- 「返さない」に分けた点は書かない。気になる点が無ければ「気になる点はなし」の1行

### 3段目: 返す内容

`references/criteria.md` の「コメントの型」に沿ったPRコメント案を、コードブロックで1つ出す。

- 良かった点 → 依頼 → 質問への回答（C7。質問があるときだけ）の順。1文1行の地の文で書き、箇条書きにしない
- 良かった点は、1・2段目でユーザーが同意した点から取る
- 任意の指摘はコメントに入れない。コードブロックの外に「入れるなら」として1行ずつ添える
- 自己評価（C6）はコメントに入れない。コードブロックの外に、口頭用の一言と、本人がやったことを材料にした理由の例（2〜3行。Issue の何に応えるつもりで書いたか・どう書いたか・何を確かめたか）を添える
- 末尾に「投稿はしていません」

## 判定の注意

- **F03 が FAIL なら内容レビューに進まず止める**（`docs/pr-checklist.md`: 確認事項に全部チェックが無いPRはレビューしない）。出すのは、該当行を引用して「確認事項にチェックが無いのでレビューしない」とする1段落と、その旨のコメント案だけ
- F03 が UNKNOWN（`* task: :` 表記）なら、PRの画面で確かめてもらう。PASS 扱いにしない
- 裏取りしていない推測を「未達」「不正確」にしない。「誤解しているかもしれない」は依頼の根拠にならない
- 受講者やメンターの `settings.json` など、トークンを含みうる設定ファイルは読まない。提出物に書かれた内容だけで判定する
- 受講者は「玉木さん」のように名前で呼ぶ。名前から推測した代名詞（彼・彼女）は使わない
- AskUserQuestion は使わない
