# PRレビューコメント作成

レビュー済みPRに対するコメント文章を生成し、GitHub なら `gh pr review` で投稿、GitBucket ならクリップボードに入れてユーザーに渡すスキル。
ユーザー本人がこれまで書いてきたレビューの文体（`@作成者` で始まり、1文1行の地の文で書く）に合わせる。

## 重要な制約

- Step 4 のユーザー確認は絶対にスキップしない。コメント本文を一度も提示せずに投稿するのは禁止
- レビュー種別（Approve / Comment / Request Changes）・重大度タグ（Critical / Important / Nit 等）は AI が独断で決めず、必ずユーザーに確認する
- AskUserQuestion は使わない。直前の本文が描画されず消える不具合（claude-code#74260 系）があるため。確認は本文末尾の質問文で行い、返事を待って止まる

## 引数

$ARGUMENTS

- PR番号のみ: `234`
- PR番号＋リポジトリ: `234 owner/repo`
- 引数なし: カレントブランチのPRを自動検出。見つからなければ本文の質問文で PR 番号を聞く
- GitBucket の PR の URL

## ワークフロー

### Step 1: PR情報の自動取得

先に `git remote -v` でリモートを見る。GitBucket なら `gh` の代わりに `mcp__gitbucket__gitbucket_get_pr`（author は本文1行目の @メンションに使う）と `git fetch` / `git diff origin/<base>...origin/<head>` を使う（ToolSearch で読み込んでから呼ぶ）。

```bash
# PRメタ情報（author.login は本文1行目の @メンションに使う）
gh pr view <PR番号> --json title,body,number,baseRefName,headRefName,author

# 変更の概要（git diffで取得）
git diff origin/<base>..HEAD --stat

# コミット履歴
git log origin/<base>..HEAD --oneline
```

認証エラーが出た場合は `gh auth switch` でアカウントを切り替える。

取得した情報から以下を整理し、ユーザーに簡潔に提示する：
- PR番号・タイトル
- 変更ファイル数・行数
- 主な変更領域

### Step 1.5: ユーザーの直近のレビューを読む

文体（長さ・言い回し・締め方）を合わせるため、ユーザー本人が最近書いたレビュー本文を5件ほど読む。
読んだ内容はユーザーに提示しない（文体を合わせる材料にするだけ）。

```bash
me=$(gh api user -q .login)
gh search prs --reviewed-by "$me" --owner <owner> --sort updated --limit 8 \
  --json number,repository -q '.[] | "\(.repository.nameWithOwner) \(.number)"' |
while read -r repo num; do
  gh api "repos/$repo/pulls/$num/reviews" \
    -q ".[] | select(.user.login==\"$me\" and .body!=\"\") | \"=== $repo#$num \(.state)\n\(.body)\n\""
done | head -200
```

GitBucket では、`mcp__gitbucket__gitbucket_list_prs` で同じリポジトリの最近の PR を出し、`mcp__gitbucket__gitbucket_list_comments` で author がユーザー本人（GitBucket のログイン名。`mori.a`）のコメントだけを読む。付録（`---` より下）は読み飛ばし、本文の長さと言い回しだけを見る。

取得できない（認証エラー・0件）ときは references/style-examples.md の例文だけで進める。

### Step 2: ユーザーの所感を収集

同一会話内で /review-pr を実行済みの場合、サマリー内容を引き継ぐ。ユーザーに「サマリーの内容で進めるか、修正があるか」を確認し、修正がなければそのまま Step 3 に進む。
指摘のうちどれをコメントに入れるか（Nit を入れるか、付録だけにするか）は、ユーザーと決めてから書く。

/review-pr を実行していない場合は、本文の質問文で以下を確認する。**1メッセージ = 最大4項目**。

1. **レビュー種別**: Approve / Comment（確認をお願いしたい点がある） / Request Changes
2. **良いと感じた点**: 自由記述（必須）
3. **気になった点・質問**: 自由記述（任意）
4. **確認した点**: 手を動かして確認した内容を自由記述（任意。例: 「〜の動作を確認」「〜のテストを実行」等）

### Step 3: コメント生成

diff分析とユーザーの所感を組み合わせてMarkdownコメントを生成する。

**型**: 下の「出力フォーマット」から1つ選び、その部品を順に埋める。例文は references/style-examples.md。
**言い回し**: references/tone-guide.md の表現変換表と、Step 1.5 で読んだ直近のレビューに合わせる。

#### 判定の主導権（AIが独断で決めない項目）

以下は Step 2 でユーザーから明示的な指定がない限り、**AI が独断で付けない**。必要なら本文の質問文で確認してから反映する:

- レビュー種別（Approve / Comment / Request Changes）
- 重大度タグ（Critical / Important / Nit 等）
- 「修正をお願いしたい点」として強制力を持たせる項目の選定

#### 生成ルール

1. **良いと感じた点**: ユーザーの所感を軸に1〜2文。変更前→変更後の構造変化や、助かる理由を書く。特定の関数名・変数名等の実装詳細には言及しない
2. **確認した点**: Step 2 でユーザーが申告した内容だけを「〜を確認しました！」の1文で書く。申告がなければ書かない。AIがdiffから推測した確認事項を勝手に追加しない
3. **気になった点・質問**: 数を先に言い（「N点気になる場所がありました。」）、1点ごとに「1つ目が〜です。」で始まる段落にする。各段落は2〜3文で、何が気になるか → どうすると良さそうか、の順。1点だけなら「〜だけご確認お願いしたいです。」
   - 本文に段落で書くのは2点まで。3点以上あるときは型C'（短縮）にし、本文には一番大きい論点だけを抽象的に書いて、残りは付録に回す。本文は読み手が1分で読める長さに収める
4. **範囲外・今後の提案**（マージを止めない話）: 「このPRの範囲外ですが、今後について N点あります。」に続けて、1点ごとの段落で書く
5. **詳しい根拠**: 段落に収まらない根拠は本文に入れず、「以下Claudeの調査結果です。」と `---` の下の付録に置く。付録は薄くしない。下の「付録の書き方」に従う
6. **ユーザーが書いた文面を見せられたとき**: 「良いと思います」と返す前に、references/tone-guide.md の「避ける表現」に当たる語がないかを照らす。特に上司への再レビューで、相手の修正を「適切」「正しい」と評価する言い方は避け、「確認しました」とお礼に置き換える案を出す

#### 付録の書き方

本文を短くする代わりに、付録は作者がそれだけ読んで直せる厚さにする。行番号だけの表で済ませない。

1. 冒頭に対象（ブランチ名と commit の sha）を書く。再レビューでこの sha から先の差分を読むため
2. 必要なら「前提」: PR が挙げている根拠・実例と、その本当の原因（表にしてよい）
3. 指摘ごとに見出しを立て、次の順で書く
   - **該当箇所の引用**: 追加・変更された文やコードをそのまま引く（ファイル:行）
   - **問題**: 何が起きるか。PR 自身の記述と食い違う場合はその記述も引く
   - **根拠**: 確かめたコード片・grep の結果・実測値。他リポジトリを調べたならそのパス
   - **修正案**: 差し替える文言やコードの方針まで具体的に書く
4. 範囲外の提案は別の見出しにし、マージを止めないと分かるように書く
5. 最後に「確認したこと」: 問題がなかった点と、確認できなかったこと（テスト未実行など）を分けて書く

### Step 3.5: yomiyasu で推敲

Step 3 で生成したコメント本文（`---` より上だけ。付録は渡さない）を、Skill ツールで `yomiyasu:yomiyasu` を起動して推敲する。
プラグインが使えない環境では本ステップを飛ばし、Step 4a で「yomiyasu 未適用」と添える。

yomiyasu に渡す指示（コメント本文の前に付ける）:

```text
ドメイン: business
文書の立場: PRへのレビューコメント。感謝・感想・確認報告・依頼・質問の行が混在しており、行ごとの働きを保つ
推敲の範囲: 各行の中身だけを直す。1文1行の改行・段落の数と順序は元のまま残す。箇条書きや見出しに変えない
固定表現（変えない）: 1行目の @メンション、「実装ありがとうございます」「対応ありがとうございます」「素早い対応ありがとうございます！」「〜だと思いました」「非常に助かります」「〜を確認しました！」「N点気になる場所がありました。」「何点か気になる場所がありました。」「1つ目が」「一つは、」「ほかに気になった点も含めて、下にまとめています。」「このPRの範囲外ですが」「お手数ですが、ご確認お願いします。」「以下Claudeの調査結果です。」「LGTMです！」
優先順位: 上の固定表現・構成と yomiyasu の規則が食い違う場合は、固定表現・構成を優先する
```

推敲結果の扱い:

- Step 4a と Step 5 で使うのは yomiyasu の「書き直した本文」だけ
- 「変えたところ」「書き手に確かめたい点」は Step 4a でコメント本文の下に添えて提示する
- 固定表現・行構成が崩れていたら、崩れた箇所を Step 3 の生成結果に戻す

### Step 4: コメント提示とユーザー承認

Step 4 は Step 5 への前提条件。以下を順に実行する。**この順序を崩して Step 5 に進むことは禁止**。

#### Step 4a: コメント本文の提示（投稿しない）

本文は Markdown ブロックで提示する。付録は長いので、構成（見出しの一覧）と、全文を保存したファイルのパス（scratchpad）を示す。この時点で投稿は**絶対にしない**。PR コメントは他者に見える操作であり取り消しが困難なため、ユーザー承認前の投稿は禁止。

#### Step 4b: ユーザー承認の取得

本文末尾の質問文で、次のどれにするかを聞いて止まる：

- クリップボードに入れる（GitBucket の既定。ユーザーが手直しして自分で投稿する）
- このまま投稿（GitHub のみ）
- 修正する（修正内容を書いてもらう）
- キャンセル

#### Step 4c: 承認結果の判定

- 「クリップボードに入れる」→ Step 5 の GitBucket の手順へ
- 「このまま投稿」→ Step 5 の GitHub の手順へ
- 「修正する」→ コメントを更新し、Step 4a から再実施。ユーザーが指定した文言はそのまま使い、AI が新たに書き直した行だけ Step 3.5 で推敲する
- ユーザーが手直しした文面を貼ってきた → 感想を聞かれているのか、反映を頼まれているのかを読み分ける。感想なら生成ルール 6 に従って見て返すだけにし、ファイルやクリップボードは触らない
- 「キャンセル」→ 処理終了（Step 5 を実行しない）

### Step 5: 投稿・受け渡し

**前提**: Step 4c で投稿か受け渡しが選択されていること。未確認の場合は Step 4 に戻る。

#### GitBucket: クリップボードに入れる

全文（本文＋付録）を scratchpad のファイルに書き、制御文字が無いことを確かめてからクリップボードに入れる。末尾の改行は残してよい（コマンドではないので貼り付けで実行されない）。

```bash
F=<scratchpad>/pr<番号>-review.md
grep -nP '[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]' "$F" && echo "制御文字あり" || win32yank.exe -i < "$F"
win32yank.exe -o | head -1   # @作成者 で始まるかを確かめる
```

`win32yank.exe` が OS error 5 で失敗したら、Windows 側でクリップボードが使用中。ループで叩き続けず、ファイルのパスを伝えて止まる。
GitBucket の PR にレビュー状態は無い。ユーザーが明示的に頼んだときだけ `mcp__gitbucket__gitbucket_add_comment` で投稿する。

#### GitHub: `gh pr review` で投稿する

確認後、`gh pr review`コマンドを生成・実行する：

```bash
# Approve
gh pr review <PR番号> --approve --body "$(cat <<'EOF'
（コメント本文）
EOF
)"

# Comment（確認をお願いしたい点がある）
gh pr review <PR番号> --comment --body "$(cat <<'EOF'
（コメント本文）
EOF
)"

# Request Changes
gh pr review <PR番号> --request-changes --body "$(cat <<'EOF'
（コメント本文）
EOF
)"
```

投稿成功後、PRのURLを表示する。

## 出力フォーマット

本文（`---` より上）は、1行目の `@作成者` から始まる **1文1行の地の文** で書く。話の切れ目は空行で区切る。
本文に見出し（`##`）・ラベル行（「良いと感じた点」等）・箇条書き（`- `）は置かない。
次の型から1つ選び、部品を上から順に埋める。

### 型A: Approve（指摘なし）

1. `@作成者`
2. 「実装ありがとうございます。」（修正後の再レビューなら「対応ありがとうございます。」）
3. 良いと感じた点を1〜2文
4. 確認した点を1文（申告があるときだけ）
5. 「LGTMです！」

### 型B: Approve＋今後の提案（マージは止めない）

1〜4. 型Aと同じ
5. 空行のあと「このPRの範囲外ですが、今後について N点あります。」
6. 1点ごとに空行で区切った段落（2〜3文）
7. 空行のあと「LGTMです！」

### 型C: Comment / Request Changes（確認をお願いしたい点がある）

1〜4. 型Aと同じ
5. 空行のあと「N点気になる場所がありました。」（1点なら「〜だけご確認お願いしたいです。」）
6. 「1つ目が〜です。」で始まる段落を1点ずつ（2〜3文。何が気になるか → どうすると良さそうか）
7. 空行のあと「お手数ですが、ご確認お願いします。」
8. 詳しい根拠があるときだけ「以下Claudeの調査結果です。」→ `---` → 付録（「付録の書き方」に従う）

### 型C': Comment / Request Changes の短縮（指摘が3点以上）

1〜4. 型Aと同じ
5. 空行のあと「何点か気になる場所がありました。」
6. 「一つは、〜点です。」で一番大きい論点を1文、その理由を1〜2文
7. 「ほかに気になった点も含めて、下にまとめています。」
8. 空行のあと「お手数ですが、ご確認お願いします。」→「以下Claudeの調査結果です。」→ `---` → 付録（必須）

### 型D: 再レビューで承認する（指摘への修正を確認した後）

1. `@作成者`
2. 「素早い対応ありがとうございます！」（急ぎでなければ「対応ありがとうございます。」）
3. 「修正いただいた内容を確認しました。」（指摘の数が分かるなら「2点とも〜」）。相手の修正を「適切」「正しい」と評価しない
4. 任意で1文: 指摘以上に手厚くしてくれた点へのお礼、または見送られた点への返事（「〜は別でご検討いただければ大丈夫です」）
5. 「LGTMです！」
