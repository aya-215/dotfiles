# レビューコメントの例文

型A〜D（SKILL.md の「出力フォーマット」）の例。固有名は架空。
このリポジトリは公開なので、実際のレビューから社内の固有名（人名・IP・案件名）を写さない。

## 型A: Approve（指摘なし）

```markdown
@author-login
実装ありがとうございます。
ログイン状態の判定を1か所にまとめていて、きれいな変更だと思いました。
実機でログアウト後に再ログインできることを確認しました！
LGTMです！
```

## 型B: Approve＋今後の提案

```markdown
@author-login
実装ありがとうございます。
影響範囲が小さく収まっていて、きれいな変更だと思いました。

このPRの範囲外ですが、今後について2点あります。
1つ目は、同じ確認をほかのブランドにも入れてよいと考えています。未ログインでも呼べる状態のものが残っているためです。
2つ目は、設定の付け忘れを防ぐため、ログイン必須のブランドでは自動で有効になる形にしてもよいと思いました。

LGTMです！
```

## 型C: Comment（確認をお願いしたい点がある）

```markdown
@author-login
実装ありがとうございます。
検索の仕組みがすごく便利そうだと思いました！
権限での制限もしっかり用意されていて、安心な検索になっていると思います。

2点気になる場所がありました。
1つ目が接続先を環境変数で指定している点です。
接続先が増えるたびにデプロイが要るので、リクエストのヘッダーから割り出せると汎用的になるかなと感じました。

2つ目が重複の除去です。
データを作る側で除けるなら、そちらに移したほうが責務がわかりやすいと思いました。

お手数ですが、ご確認お願いします。
以下Claudeの調査結果です。

---

対象はブランチ `feat/search-endpoint`（a1b2c3d）です。行番号はこのブランチの時点のものです。

### 1. 接続先を環境変数で指定している（src/search/client.ts:12）

**該当箇所**
> const endpoint = process.env.SEARCH_ENDPOINT

**問題**
接続先が増えるたびに環境変数を足してデプロイし直す必要があります。

**根拠**
リクエストヘッダー `X-Tenant` に接続先の識別子がすでに入っています（src/middleware/tenant.ts:30）。

**修正案**
`X-Tenant` から接続先を引く関数を1つ作り、環境変数は既定値だけに使う形です。

### 2. （同じ構成で続ける）

### 確認したこと

- 既存の検索 API の応答形式は変わっていません
- テストはこちらの環境では実行できていません
```
